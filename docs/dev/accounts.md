# 账号表和三种工具

第三方 API 账号的 key 见 secrets.md；设备标识和共享的资料见 isolation.md；Team 给的账号怎么并进账号表、固定节点、收起来见 team.md「账号表照配置改」。

- 账号表的值是字符串（官方账号，值是节点）或对象（第三方 API 账号：`base_url`/`model`/`node`/`env`/`key`/`id`，Codex 的没有 `env`）。读值一律用 `is_api`/`node_of`，不要假设是节点字符串；端口表（`T.state(c)['ports']`）里只有走节点的账号（直连的 API 账号没端口），要端口时用 `routed(c, t, tool)`，跨工具用 `pool(c)`。第三方 API 账号按 `id` 认（各工具的 `tool.ids`，派发子命令前 `load_ids()` 读好；config.json 的 `api_ids` 记着上次的 键 → 账号目录名，改几次别名端口和"上次使用"都认得出；跨工具时用 `acct_id(key, tool)`），改别名时目录、key、端口不变
- 账号表的顺序只管显示（菜单、编号、App 的列表）。端口池（`routed` / `pool`）、路由器的摘要、本机 Clash 的端口池、启动器和头像的颜色都按 `base_order`：没调整过时就是账号表的顺序（和以前逐字节一样），第一次 `cca reorder` 之前把原来的顺序记进 `order_base`（在 `T.state(c)` 里，记账号目录名），之后新加的账号排在后面。新写依赖账号先后的逻辑时用 `base_order`，不要直接遍历账号表：不然调整一次顺序就要同步路由器、重新加载本机 Clash、账号换颜色

## 三种工具的差异
- 工具差异集中在两处：辅助程序的 `Tool`（`cli/src/core/tool.rs`：Claude 的那一份取值和只支持 Claude 时一样，另有 Codex、agy 的；原来 Python 里是 `Tool` / `CodexTool` / `AgyTool` 三个类），按 `CCA_TOOL` 选出当前的 `t()`（原来的 `T`）（`TOOLS` 的顺序 claude、codex、agy 不能变：端口池按它分）；bash 的 `TOOL`（`use_tool codex` 切换，账号表、命令前缀 `CMD`、文案变量由 `py tool-env` 给，`py` 自动带上 `CCA_TOOL`），不同的步骤写成成对的 `claude_xxx` / `codex_xxx`，用 `tool xxx` 调用。`cca codex <子命令>` 复用同一套 `dispatch`；提示里的命令前缀用 `${CMD}`。再加工具：照 `CodexTool` 加子类、补同名前缀的函数，再查一遍只是文案不同的 `case "$TOOL"` / `[ "$TOOL" = codex ]`（添加账号的问答、`cmd_key`、`cmd_rm`、`settings_warn` 等）和 `cmd_restore` 里的 `for t in claude codex agy`；工具有没有桌面 App、第三方 API 账号、查用量的接口看 `has_app` / `has_api` / `has_usage`（`_gui state` 的 `features`）
- `cxa` 是 `cca codex` 的简写，`aga` 是 `cca agy` 的（`CODEX_ALIAS`、`AGY_ALIAS`）：`~/.local/bin/cxa`、`aga` 是指向同目录 `cca` 的相对链接（`tool_alias_ensure 工具`：`cca install` 和添加这个工具的账号时建，不覆盖别人的同名命令；平时每次运行，用着这个工具（有 codex.json / agy.json，或者这次是 `cca codex|agy …`）时也查一下，缺了就补，用 quiet：那里有东西、PATH 里有别的同名命令时不动也不说，免得每次都提示；`cmd_restore` 只删指向 `cca` 的那两个）。`main` 开头按调用名（`$0`）把参数换成 `codex …` / `agy …`，必须在 `update_hook` 之前：自动更新后 `exec "$SELF" "$@"` 重新执行时参数里得带着工具，否则 `cxa @工作` 会去启动 Claude
- Codex 账号表是 `~/.cca/codex.json`（格式同 accounts.json），账号目录在 `~/.cca/codex/accounts/<acct_id>/`（`acct_id` 算法不变，同一个邮箱的 Claude 账号不会撞），config.json 里它的 ports / last / api_ids / api_keys 放在 `"codex"` 子对象（空了 `cfg_clean` 会删掉）。读写这些一律经 `T.state(c)`，不要直接碰 `c['ports']`
- 两张表共用一个端口池：`reconcile_all` 一起对账（各自已有的端口不动，新端口避开对方的），`pool(c)` 先 Claude 后 Codex。路由器和本机 Clash 的端口池、摘要都按 `pool`；只有 Claude 账号时输出必须和以前逐字节一样（回归里有 accounts.yaml 的固定对照）。钥匙串前缀 `cca-codex-api-`、路由器账号名前缀 `codex-`、启动器「ChatGPT 别名」（bundle id `local.cca.launcher.codex.…`，标记里带 `"tool": "codex"`；各工具的启动器同步只动自己的）

## Codex
- `CODEX_HOME` 共享是白名单（`CODEX_SHARED`，以及新版 `*.config.toml` profile）：~/.codex 里有登录、按账号的缓存、installation_id、桌面 App 和后台进程的状态，新文件默认不共享。profile 同样记录配置基线，启动检查遍历全部共享 profile，避免 `--profile` 选中未检查的账号/接口设置。`worktrees/`、`visualizations/` 是 macOS 沙箱的可写目录，路径里不能有链接。数据库不靠链接：`CODEX_SQLITE_HOME` 指向 ~/.codex；会话库 threads 表里经账号目录的 `rollout_path` 每次 `py link` 都改写成 ~/.codex 下的（`codex_fix_rollouts`），否则删账号后会话从 `codex resume` 的全部列表里消失
- 启动 codex 一律加 `--no-daemon` 和关掉 `system_proxy_fallback`、`respect_system_proxy` 的 `--disable`（都会让请求换出口）；codex 不认识的开关会直接报错，所以按 codex 程序文件缓存探测结果（`codex_probe`，`~/.cca/codex/probe.json`），只加它认识的（同一次探测还问认不认推通知的那几个 -c，记在 `notify`：交互的会话做完了、在等你时推通知，见 remote.md「Codex、Antigravity 的通知」）。ChatGPT App 自己启动 codex，只能征得同意后用 `codex features disable system_proxy_fallback` 写进共享的 config.toml；拒绝、失败或无法关闭时停止打开 App
- Codex 登录和查用量都经 codex 自己的 app-server（`Rpc`：`account/login/start` 拿到网址后回调 `cca _browser` 在账号的 Chrome 里开，`cmd_login_url` 按 `T.login_hosts` 补 `login_hint`；`account/rateLimits/read`），客户端名用 `codex_cli_rs`（和 `codex login` 一样，登录页认这个 originator）。登录身份只从 auth.json 的 id_token 读邮箱/套餐/工作空间（`codex_claims`），不碰 access/refresh token
- Codex 子进程不带继承来的 `CODEX_*`、`OPENAI_*`（`CODEX_INHERITED_RE`，只留 `CODEX_CA_CERTIFICATE`）；共享 config.toml / .env 里会串号的设置见 `codex_settings_problems`（TOML 由辅助程序自己解析，`cli/src/py/toml.rs`，照 tomllib 的行为、有对照数据；禁止退回粗扫描，解析失败必须阻止启动）。Codex 新增会改地址、换凭证的设置或环境变量时两边一起补
- Codex 的第三方 API 账号只能用 Responses 接口：`-c model_provider="cca"` + `-c model_providers.cca={…auth={command=cca, args=["_api-key","codex",账号目录名]}}`，key 不进命令行；没有 `env` 字段

## Antigravity
- Antigravity（`cca agy …`，Google 的 `agy` 命令，`AgyTool`）：账号表 `~/.cca/agy.json`（值只能是节点名：`has_app` / `has_api` 都是 False（`has_usage` 3.6.11 起是 True：App 显示它的几组额度，docs/dev/usage.md；`has_cost` 3.7.2 起是 True：折合金额读共享的会话库、按 cca 记下的运行认账号，docs/dev/cost.md），`api_problems` 拒收对象；`add api`、`app`、`billing`、`limit-resets` 用 `FAIL_CODE=unsupported` 说清楚、不动），账号目录 `~/.cca/agy/accounts/<acct_id>/`，数据目录是它下面的 `gemini`，启动时 `--gemini_dir=` 写在用户参数前面（`run_args`；用户参数里另给 `--gemini_dir` 拒绝启动）；config.json 里是 `"agy"` 子对象，路由器账号名前缀 `agy-`，Team 的配置里是 `"agy"` 一节（`accounts.agy`、`tool_aliases.agy`）
- agy 不管数据目录在哪都把登录存进 macOS 钥匙串（各账号会共用一份）。要它存成数据目录里的文件（`AGY_TOKEN`）：1.5.5 看到 SSH 会话（设了 `SSH_CONNECTION`）就这样（日志说 Using file-based token storage because SSH session detected）；1.5.16 在 macOS 上只有钥匙串锁着时才认 SSH 会话，另有自己的开关 `AGY_CLI_FORCE_FILE_TOKEN_STORAGE`（`1` 或 `true`，日志说 …because AGY_CLI_FORCE_FILE_TOKEN_STORAGE is set；钥匙串最近超时过、调用方要求的那两种原因不算，下次不一定还这样）。cca 启动、登录、探测、查额度时两样都设（`AGY_FILE_ENV`：`SSH_CONNECTION=AGY_SSH` 是本机地址，不带出真实 IP；bash 的 `agy_env` 是同一份，一起改），环境里继承来的开关不算（`agy_env` 的赋值在后面，探测先去掉 `AGY_` 开头的再设）。`agy_probe` 按 agy 程序文件（路径、大小、修改时间）在临时数据目录里跑一次 `acp --login`（stdin 是空的、代理指向关着的端口，不联网），从它的日志里认那两句之一（`AGY_FILE_TOKENS`），结果缓存在 `~/.cca/agy/probe2.json`（`PROBE_FILE`）。以前的 cca 只设 `SSH_CONNECTION` 探测、记在 `probe.json`，读的时候只核对程序文件：设着开关的新结果要是写进那一份，降级回去（或者仓库里的新 cca 和装着的旧 cca 用同一个 `~/.cca`）时旧版会以为可以启动，而它启动 agy 时不设开关，各账号就会共用钥匙串里的登录。所以新版换了文件名，`probe.json` 不读也不动（旧版读到的还是它自己记下的 false，照旧停下）；以后探测的做法再变，同样换文件名；`agy_guard`（登录、每次启动前、`cca agy usage`）认不出就以 `login_unsupported` 停下，不能退回钥匙串。cca 只读 token 文件里的 `id_token_email`、`user_tier`（`agy_claims`；1.5 的里面没有 `user_tier` 了，套餐见下一条），读不出邮箱时用 `agy-login.json`（agy 登录成功时说的 Logged in as）；token 在 `CCA_DIR_PRIVATE` 里，restore 的备份不打包。副作用：agy 当自己在 SSH 会话里运行
