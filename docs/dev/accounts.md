# 账号表和三种工具

第三方 API 账号的 key 见 secrets.md；设备标识和共享的资料见 isolation.md。

- 账号表的值是字符串（官方账号，值是节点）或对象（第三方 API 账号：`base_url`/`model`/`node`/`env`/`key`/`id`，Codex 的没有 `env`）。读值一律用 `is_api`/`node_of`，不要假设是节点字符串；端口表（`T.state(c)['ports']`）里只有走节点的账号（直连的 API 账号没端口），要端口时用 `routed(c, t, tool)`，跨工具用 `pool(c)`。第三方 API 账号按 `id` 认（各工具的 `tool.ids`，派发子命令前 `load_ids()` 读好；config.json 的 `api_ids` 记着上次的 键 → 账号目录名，改几次别名端口和"上次使用"都认得出；跨工具时用 `acct_id(key, tool)`），改别名时目录、key、端口不变
- 账号表的顺序只管显示（菜单、编号、App 的列表）。端口池（`routed` / `pool`）、路由器的摘要、本机 Clash 的端口池、启动器和头像的颜色都按 `base_order`：没调整过时就是账号表的顺序（和以前逐字节一样），第一次 `cca reorder` 之前把原来的顺序记进 `order_base`（在 `T.state(c)` 里，记账号目录名），之后新加的账号排在后面。新写依赖账号先后的逻辑时用 `base_order`，不要直接遍历账号表：不然调整一次顺序就要同步路由器、重新加载本机 Clash、账号换颜色

## 三种工具的差异
- 工具差异集中在两处：PY_SRC 的 `Tool`（Claude，取值和只支持 Claude 时一样）/ `CodexTool` / `AgyTool`，按 `CCA_TOOL` 选出 `T`（`TOOLS` 的顺序 claude、codex、agy 不能变：端口池按它分）；bash 的 `TOOL`（`use_tool codex` 切换，账号表、命令前缀 `CMD`、文案变量由 `py tool-env` 给，`py` 自动带上 `CCA_TOOL`），不同的步骤写成成对的 `claude_xxx` / `codex_xxx`，用 `tool xxx` 调用。`cca codex <子命令>` 复用同一套 `dispatch`；提示里的命令前缀用 `${CMD}`。再加工具：照 `CodexTool` 加子类、补同名前缀的函数，再查一遍只是文案不同的 `case "$TOOL"` / `[ "$TOOL" = codex ]`（添加账号的问答、`cmd_key`、`cmd_rm`、`settings_warn` 等）和 `cmd_restore` 里的 `for t in claude codex agy`；工具有没有桌面 App、第三方 API 账号、查用量的接口看 `has_app` / `has_api` / `has_usage`（`_gui state` 的 `features`）
- `cxa` 是 `cca codex` 的简写，`aga` 是 `cca agy` 的（`CODEX_ALIAS`、`AGY_ALIAS`）：`~/.local/bin/cxa`、`aga` 是指向同目录 `cca` 的相对链接（`tool_alias_ensure 工具`：`cca install` 和添加这个工具的账号时建，不覆盖别人的同名命令；平时每次运行，用着这个工具（有 codex.json / agy.json，或者这次是 `cca codex|agy …`）时也查一下，缺了就补，用 quiet：那里有东西、PATH 里有别的同名命令时不动也不说，免得每次都提示；`cmd_restore` 只删指向 `cca` 的那两个）。`main` 开头按调用名（`$0`）把参数换成 `codex …` / `agy …`，必须在 `update_hook` 之前：自动更新后 `exec "$SELF" "$@"` 重新执行时参数里得带着工具，否则 `cxa @工作` 会去启动 Claude
- Codex 账号表是 `~/.cca/codex.json`（格式同 accounts.json），账号目录在 `~/.cca/codex/accounts/<acct_id>/`（`acct_id` 算法不变，同一个邮箱的 Claude 账号不会撞），config.json 里它的 ports / last / api_ids / api_keys 放在 `"codex"` 子对象（空了 `cfg_clean` 会删掉）。读写这些一律经 `T.state(c)`，不要直接碰 `c['ports']`
- 两张表共用一个端口池：`reconcile_all` 一起对账（各自已有的端口不动，新端口避开对方的），`pool(c)` 先 Claude 后 Codex。路由器和本机 Clash 的端口池、摘要都按 `pool`；只有 Claude 账号时输出必须和以前逐字节一样（回归里有 accounts.yaml 的固定对照）。钥匙串前缀 `cca-codex-api-`、路由器账号名前缀 `codex-`、启动器「ChatGPT 别名」（bundle id `local.cca.launcher.codex.…`，标记里带 `"tool": "codex"`；各工具的启动器同步只动自己的）

## Codex
- `CODEX_HOME` 共享是白名单（`CODEX_SHARED`，以及新版 `*.config.toml` profile）：~/.codex 里有登录、按账号的缓存、installation_id、桌面 App 和后台进程的状态，新文件默认不共享。profile 同样记录配置基线，启动检查遍历全部共享 profile，避免 `--profile` 选中未检查的账号/接口设置。`worktrees/`、`visualizations/` 是 macOS 沙箱的可写目录，路径里不能有链接。数据库不靠链接：`CODEX_SQLITE_HOME` 指向 ~/.codex；会话库 threads 表里经账号目录的 `rollout_path` 每次 `py link` 都改写成 ~/.codex 下的（`codex_fix_rollouts`），否则删账号后会话从 `codex resume` 的全部列表里消失
- 启动 codex 一律加 `--no-daemon` 和关掉 `system_proxy_fallback`、`respect_system_proxy` 的 `--disable`（都会让请求换出口）；codex 不认识的开关会直接报错，所以按 codex 程序文件缓存探测结果（`codex_probe`，`~/.cca/codex/probe.json`），只加它认识的。ChatGPT App 自己启动 codex，只能征得同意后用 `codex features disable system_proxy_fallback` 写进共享的 config.toml；拒绝、失败或无法关闭时停止打开 App
- Codex 登录和查用量都经 codex 自己的 app-server（`Rpc`：`account/login/start` 拿到网址后回调 `cca _browser` 在账号的 Chrome 里开，`cmd_login_url` 按 `T.login_hosts` 补 `login_hint`；`account/rateLimits/read`），客户端名用 `codex_cli_rs`（和 `codex login` 一样，登录页认这个 originator）。登录身份只从 auth.json 的 id_token 读邮箱/套餐/工作空间（`codex_claims`），不碰 access/refresh token
- Codex 子进程不带继承来的 `CODEX_*`、`OPENAI_*`（`CODEX_INHERITED_RE`，只留 `CODEX_CA_CERTIFICATE`）；共享 config.toml / .env 里会串号的设置见 `codex_settings_problems`（Python 3.11+ 用 tomllib，旧版用内嵌的 MIT 许可 tomli；禁止退回粗扫描，解析失败必须阻止启动）。Codex 新增会改地址、换凭证的设置或环境变量时两边一起补
- Codex 的第三方 API 账号只能用 Responses 接口：`-c model_provider="cca"` + `-c model_providers.cca={…auth={command=cca, args=["_api-key","codex",账号目录名]}}`，key 不进命令行；没有 `env` 字段

## Antigravity
- Antigravity（`cca agy …`，Google 的 `agy` 命令，`AgyTool`）：账号表 `~/.cca/agy.json`（值只能是节点名：`has_app` / `has_api` / `has_usage` 都是 False，`api_problems` 拒收对象；`usage`、`add api`、`app`、`billing`、`limit-resets` 用 `FAIL_CODE=unsupported` 说清楚、不动），账号目录 `~/.cca/agy/accounts/<acct_id>/`，数据目录是它下面的 `gemini`，启动时 `--gemini_dir=` 写在用户参数前面（`run_args`；用户参数里另给 `--gemini_dir` 拒绝启动）；config.json 里是 `"agy"` 子对象，路由器账号名前缀 `agy-`，映射里是 `"agy"` 一节（`policy.sh lock … agy …`；`policy summary` 只在映射里有 agy 账号时提它）
- agy 不管数据目录在哪都把登录存进 macOS 钥匙串（各账号会共用一份）。设了 `SSH_CONNECTION` 时 1.5.5 改存成数据目录里的文件（`AGY_TOKEN`，日志说 Using file-based token storage because SSH session detected）：cca 启动、登录、探测时都设 `SSH_CONNECTION=AGY_SSH`（本机地址，不带出真实 IP）。这不是公开的做法：`agy_probe` 按 agy 程序文件（路径、大小、修改时间）在临时数据目录里跑一次 `acp --login`（stdin 是空的、代理指向关着的端口，不联网），从它的日志里认那一句，结果缓存在 `~/.cca/agy/probe.json`；`agy_guard`（登录和每次启动前）认不出就以 `login_unsupported` 停下，不能退回钥匙串。cca 只读 token 文件里的 `id_token_email`、`user_tier`（`agy_claims`），读不出邮箱时用 `agy-login.json`（agy 登录成功时说的 Logged in as）；token 在 `CCA_DIR_PRIVATE` 里，restore 的备份不打包。副作用：agy 当自己在 SSH 会话里运行
- agy 登录（`agy_login` → `py agy-login`）：agy 自己打出 Google 的登录网址（`agy_login_target`：`accounts.google.com`、PKCE、`redirect_uri` 是 `AGY_REDIRECT`、state），从 stdin 读授权码（登录后页面上显示，不回本机）。cca 起 `acp --login`（三个管道），补上 `login_hint` 在账号的 Chrome 里打开（服务器上给出 `cca agy login-page` 那一行，Mac 上的 `login-page` 只打开网址、不占回调端口），授权码照规矩从 fd 3 问（`read_answer`，收授权码或整个回调网址：state 对不上不交给 agy、重问），写进 agy 的 stdin；agy 说换不到 token 时原话转述、再问；空行、读到头算取消（停掉 agy）。agy 的输出 cca 转述，不原样打出来
- agy 的设备标识：`installation_id`（正好 36 个字符、不带换行，否则 agy 换新的）和 `jetski_state.pbtxt` 顶层的 `installation_uuid`（另一个值，只换这一行），`prepare_device` 照 Codex 的规矩添加账号时生成、之后不变。共享是白名单 `AGY_SHARED`（`AGY_NESTS` 里的 `antigravity-cli`、`antigravity-cli/cache`、`config` 在账号里是真目录，白名单上的条目才链接；`AGY_PRECREATE` 先建好会话、记忆这些目录；`AGY_SHARED_CONFIG` 照 Claude 的记配置基线、原子保存后合并回去）。会话摘要的索引（`conversation_summaries.db`、`jetbox_summaries_proto.pb`）各账号一份，agy 在后台按共享的会话重建
- agy 子进程不带继承来的 `AGY_*`、`ANTIGRAVITY_*`、`GEMINI_*`、`GOOGLE_API_KEY` / `GOOGLE_APPLICATION_CREDENTIALS` / `GOOGLE_CLOUD_*` 等（`AGY_INHERITED_RE`），`INHERITED_KEEP` 留 `AGY_CA_CERT` 和界面开关 `AGY_CLI_*`；共享的 `antigravity-cli/settings.json` 和这次的 `--settings` 里写了 `gcp`（企业版的 Google Cloud 项目，`AGY_SETTINGS_BAD`）拒绝启动。出口检测的 trace 看 `www.cloudflare.com`（Google 没有 `/cdn-cgi/trace`）。agy 用的项目目录 `.agents/` 里没有换账号、出口的设置，不查
- agy 还没在真实账号上核实的：token 文件的格式（只按 1.5.5 的 `StoredToken` 字段读）、`AGY_TIERS` 的档位 ID（认不出的不显示）；agy 的 authstore 另有一份 credential user scope，之前的分析认为它不在 `--gemini_dir` 里，会不会让账号互相影响还没验证。agy 升级后先看 `agy_probe` 还认不认，再看这几样

## 测试
- Codex：假 `codex` 把参数和环境记在 `$T/codex.log`（`ARGS:` / `ENV:`），前面带 cca 的参数时是启动会话（模拟写 CODEX_HOME 和会话库，退出码 3）；`app-server` 由 `$T/fake_codex_server.py` 扮演，登录时等登录网址出现在 open.log 里再写 auth.json（邮箱取 `CCA_ACCOUNT`，一次性的 `$T/codex_login_as` 模拟登错号），用量回 `$T/codex_usage/<邮箱>.json`（`unsupported`、`hang` 同 Claude）；`codex_usage/rpc_error` 里的话当 app-server 的出错说明回（登录凭证失效之类），`$T/codex_rpc_off` 模拟不支持 app-server，`$T/codex_noflags` 模拟不认识那两个开关（记得删 `~/.cca/codex/probe.json`）；假 ChatGPT App 用 `CCA_CODEX_APP`
- Antigravity（regress.sh 10f2，最后删掉 agy.json 和 `~/.cca/agy`，后面的用例照没用过 agy 写；12 的还原自己写一份 agy.json 和登录 token）：假 `agy` 把参数和环境记在 `$T/agy.log`（`ARGS:` / `ENV:`，ENV 里有 `fd3=open|closed`），`$T/fake_agy.py` 扮演它：带 `--gemini_dir` 的都在那个数据目录里做；`acp --login` 在设了 `SSH_CONNECTION` 时往日志写那一句（`$T/agy_keychain` 模拟不再这样的新版本），打印登录网址（state 取 `$T/agy_state`，默认 `st-agy`）和不带换行的提问，从 stdin 读授权码：`good` 开头算成功、写 token（邮箱取 `CCA_ACCOUNT`，一次性的 `$T/agy_login_as` 模拟登错号，`$T/agy_noemail` 不写邮箱，档位取 `$T/agy_tier`），换 token 时的代理记 `AGY-EXCHANGE`；其余（包括带着 `--gemini_dir` 的 `--version`）是一次会话：记 `AGY-DEVICE 两个装机标识 @ 数据目录`，写共享的会话、历史、技能、`--continue` 的记录，设置用临时文件 + 改名保存，退出码 3（`$T/hold` 在时一直开着）。`alast ARGS|ENV` 取最后一次，`alk 路径` 断言账号里这一项是指向 `~/.gemini` 同名项的链接
