# 本机出口：内置代理

在家还是在外的判断、泄露检测见 network.md；界面 App 托管内核的那一半（`CoreHost`）见 macos/CLAUDE.md。

- 出门在外（连不上路由器）或者没有路由器时，账号走内置代理：本机出口只剩它（config.json 的 `local.client` 是 `builtin`）。Clash Verge 和手动配置的客户端 3.3.0-beta.8 删掉了：旧配置里的 `clash-verge` / `manual` 当作没配置（`py local-env` 给空的 `LOCAL_CLIENT`，下次 `cca local setup` 配成内置代理）。端口池和路由器上的一样：127.0.0.1 上的入站 `cca-n`（端口 7900+n）直通选择组 `CCA-n`；启动账号前经内核的控制接口（Unix socket，`lctl`）把各个槽位切到账号的节点、GET 回读（`local_select_all`，节点名用内置代理里的叫法），核实不了就把那个组切到 REJECT、停下：宁可断开，也不把切换失败当成就绪
- 内置代理（config.json 的 `local.client` 是 `builtin`）：没有路由器、或在外面连不上路由器时，账号经 cca 自带的 mihomo 内核走各自的节点（3.3.0-beta.8 起本机出口只有它）。在外面还没配置时（`local_offer`；没有这个架构的内核时 `local_unavailable`）：终端里走 `cca local setup`（只问一句用不用内置代理，`local.builtin`）；界面 App 里（有 `CCA_EVENTS` 或已授权）问 `builtin_core`（`core_offer`）；别的非交互（Dock 上的启动器、脚本）说清楚并交给终端。不再用它时（`cca local off`）先 `core_retire`：删掉配置和拷来的节点（本机 UDP 走节点的开关文件一起删）、等内核停下（托管它的看到配置没了会停；没在托管或 10 秒还没停就按 pid 文件停），免得它还占着端口。端口池、切换节点、端口检查、泄露检测都走 `local_*` 那一套（`local_ensure` → `core_ensure`）。macOS 26 起内核由界面 App 托管：App 读到 state 里是 builtin 就运行 `cca _core run`（在 `main` 最前面分派；生成 `core/config.yaml` 后 exec 内核），退出了退避重启，App 退出就停；cca 要内核又没开 App 时 `open -g <App> --args --core`（不弹主窗口、不占 Dock），App 开着时不再 open（会弹出主窗口），只写 `core/config.yaml`（App 的 `.core` 信号，隐藏时也读 state）；还没装 App 时终端里问过后装上（`cmd_gui`），非交互的交给终端。内核文件第一次用时从 MetaCubeX/mihomo 官方 Release 下载，版本和 macOS、Linux 各两个架构的 SHA256 写死在开头（`CORE_VERSION`、`CORE_SHA256_*`，换版本时四个一起换，取 GitHub 资产的 digest；mkver 的 sed 按整行换 macOS 的两个，那两行后面别加注释）。Linux 和 macOS 26 以下没有界面 App（`core_headless`）：内核由 cca 自己的后台进程 `cca _core-keep`（辅助程序的 `cmd_core_keep`，照 App 的 CoreHost：1、2、4…秒退避、最多 60 秒，跑够 60 秒从头算，等的时候配置文件变了马上重启；本机客户端不是内置代理了、`core/config.yaml` 没了就停内核、退出）托管，`core_launch` 经 `POSIX::setsid` 起它（`keep.lock` 保证一个），不用 root、不靠 systemd，退出登录后还在（logind 默认不杀）。机器重启后：配置好内置代理时问过（`core_boot_offer`：后台托管时才问，已经有了不问）在用户自己的 crontab 里加一行 `@reboot <cca> _core-keep >/dev/null 2>&1 # cca-core`（`core_boot has|on|off` 只动带 `CORE_BOOT_TAG` 的那一行；读 `crontab -l` 时 `no crontab` / `No such file` 算空的，别的错误不写），`core_retire`（`cca local off`）和 `cca restore` 删掉它（和加的时候一样看 `core_headless`：Linux、macOS 26 以下；回归 12 节用假的 crontab（`$T/crontab`）、`CCA_GUI_OS=15` 测 restore 删掉这一行、别的行留着）；没有 crontab 命令、没加的，下次在外面启动账号时再起；输出在 `core/core.log`；Linux 上 socket 在 `core/cca-core.sock`（不放 `XDG_RUNTIME_DIR`：退出登录会被删掉；路径超过 Unix socket 的长度上限时才放那里）；`core_possible` 只看有没有这个架构的内核（x86-64 用 amd64-compatible、arm64）。实测（2026-11-11，`tests/linux.sh`）：Ubuntu 22.04 / 24.04 / 26.04、Debian 12 / 13、Rocky 9、AlmaLinux 10、Fedora 43、Amazon Linux 2023、Alpine 3.22（busybox）、Arch、openSUSE Leap 16.0 都过；Linux 上从路由器拷节点不用 ruby（路由器端写好 JSON），连不到路由器的服务器上的节点靠 Team 的配置带的节点（参考节点）或者自己粘贴的自定义节点。配置用 JSON 写（mihomo 照 YAML 读），只有 127.0.0.1 的 listeners、`CCA-n` 选择组、节点、`MATCH,REJECT`；别的程序开着 TUN（Clash 客户端的虚拟网卡模式、VPN：去节点的流量会被它截走、照它的规则再套一层代理，实测出口检测拿不到 IP）时出站绑定物理网卡（辅助程序的 `core_bind`，只在 macOS 上：看节点里第一个公网 IP、都是域名时看 `CORE_ROUTE_PROBE` 走不走虚拟网卡，是就加 `interface-name`，macOS 照这块网卡自己的路由走、绕开 TUN；实测修好了。系统的 DNS 经物理网卡到不了（TUN 自己的地址、本机的）时另配 `dns`，用物理网卡从 DHCP 拿到的（`core_dns`，`ipconfig getpacket`）；没开 TUN 时配置逐字节不变），绑定的网卡和 DNS 进 `local_want`（开关 TUN 后下次启动重新加载一次，`_gui state` 的 `local_sync` 这时是 pending），`cca local` 和重新加载时说一句（`bind_note`）；config.json 的 `core_bind: false` 关掉（要经 VPN 才连得到节点的网络）。辅助安装的临时内核同样绑定（`core_bind_apply`）。不写死代理的地址：网卡、DNS 都现查；控制接口只开 Unix socket，放在 `DARWIN_USER_TEMP_DIR`、名字带 `~/.cca` 的摘要（`~/.cca` 下的路径可能超过 macOS 的 104 字节上限，真内核会绑定失败）；`PUT /configs` 的 path 必须在内核主目录（`-d ~/.cca/core`）里；`store-selected: false`，重新加载后选组里第一个，所以账号的节点排第一
- 内置代理的节点：在家启动账号后 `core_nodes_hook` 看缓存（`core/nodes.json`）不在、超过 12 小时、可选节点变了，就在后台（`cca _core-nodes`）用路由器端的 `defs` 拷一份（路由器上本来就有 ruby，`defs` 自己写 JSON：OpenWrt 的 ruby 不一定带 json 库，拷的那台机器（Linux 服务器）也不一定有 ruby；字符串的引号、反斜杠、控制字符写成 `\u` 转义，日期这类照字符串，NaN、无穷大写 null。`py core-nodes-save` 只留可选节点和它们经 dialer-proxy 用到的；指向策略组的不要，带上会让整份配置加载不了），用的时候再加上自定义节点、按 `fill_plan` 补 Team 的配置带的节点（参考节点，`core_defs`），节点名按摘要换算（`core_names`；`local_names` 就是它）。只有会走内置代理的机器才拷（`core_eligible`：client 是 builtin；或者没配置、没 `cca local off` 过（`local.core_off`））。`core/nodes.json`、`core/config.yaml` 有节点密钥：600、在 `CCA_DIR_PRIVATE` 里，`cca local off` 删掉（没配置本机客户端时 `cca local off` 也记下 `core_off`，在家不再拷），restore 的备份不打包（bsdtar 的 `--exclude` 不锚定开头，写具体文件名）。拷的时候全程走管道、不落盘：路由器端 `defs` 的最后一行是 `# cca-defs-end`，`py core-nodes-save` 没读到它就不写（没拷完整）。在家启动时只跑轻量的 `py core-stale`（只读 config.json、节点缓存：每次在家启动都跑，不能慢；不跑 `local-env`），要做的交给后台的 `cca _core-nodes [nodes] [bin]`：已经用内置代理、内核文件不在（第一次、cca 升级换了内核版本）时也在家先下好，在外面直连 GitHub 可能很慢。等内核超时、界面 App 和 cca 版本不同时说清楚是旧版 App
- 自定义节点（`cca [codex|agy] node [ls | add [链接] | use 账号 [链接] | rm 节点]`，bash 的 `node_add` 那一节、辅助程序的 `node-check` / `node-testconfig` / `node-save` / `node-ls` / `node-rm` / `node-assign`）：能用内置代理的机器都能加（`node_custom_ok` 就是 `core_possible`：拿它的内核先校验）。配置了路由器的，同步时照参考节点那一套写进路由器的配置文件（fill.md「自定义节点」；在外面时等回家后的下次启动）。粘贴一条代理链接或一段 Clash 节点配置（终端里单独一行 `.` 结束；App 的表单 `node.custom` 只收一行的链接）：分享链接（vmess、vless、ss、trojan、hysteria2、tuic），或者买的静态 IP 这类 `socks5://用户:密码@主机:端口`（`socks5h://`、v2rayN 那种用户名密码 base64 的 `socks://` 也认）、`http://用户:密码@主机:端口`（`https://` 带 `tls: true`）——辅助程序的 `link_plain`，用户名密码按网址转义还原，`#` 后面是名字，没写端口的 socks 是 1080、http 80、https 443。`py node-check [要避开的名字…]` 解析、起一个不重名的名字（可选节点、拷来的、参考节点、内置出站都不撞；在家时还避开路由器上全部节点和策略组的名字，`node_taken` 经 `sh -s nodes` 取：同名的写不进路由器的配置），再拿只含它的最小配置让内核 `-t` 校验（不起内核、不联网），过了才 `py node-save`：在 `Lock` 里存进 `core/custom-nodes.json`（`CORE_CUSTOM`；600，在 `CCA_DIR_PRIVATE` 里，restore 的备份不打包），名字加进可选节点、摘要记进 `node_ids`。内核的配置里和拷来的节点定义一起用（`core_defs`，同名时自定义的优先）。加账号选节点时是「自定义代理…」（`add.node` → `node.custom`；没有路由器、还没有可选节点时只有这一项）；已有的账号用 `node use 账号 [链接]` 换过去（App 账号页「网络出口」一节的「自定义代理…」，`can.custom_proxy`，提问会话）：`py node-assign 键` 先查 Team 的配置——固定了这个邮箱的节点就退出码 3（`FAIL_CODE=node_pinned`，不问链接、什么都不存；`node_free` 和 `can.custom_proxy` 同一条规则，第三方 API 账号都能换），加好节点后 `py node-assign 键 节点` 改账号表（官方账号的值换成节点名，第三方 API 账号改它的 `node`），接着 `router_sync_soon`（要重启 OpenClash / ShellCrash 时先问；提问会话里是 `consent.router_restart`），做完 `result` 是 `saved`、带账号的键。还有账号在用的 `node rm` 不删，说是哪几个账号；写进路由器配置文件的不跟着删。几台设备共用路由器时，同步前和别的设备正用着的同名节点不是同一个的，这台的自动换个名字（`custom_clash_rename` → `node-rename`，见 fill.md「自定义节点」）。订阅链接没做

- 本机 UDP 走节点给别的 VPN 让开（`UDP_HELPER` 2 起）：root 那边的启动脚本 `cca-udp`（bash 的 `udp_run_sh`）每 2 秒看一次 `netstat -rn -f inet`：有经别的虚拟网卡（utun / ipsec / ppp / tun / tap，不是自己的 `utun233`）、不限定网卡（Flags 里没有 `I`）的默认路由或者 0/1、128.0/1、1.0.0.0/8 … 64.0.0.0/2 这几大段，就是别的 VPN、代理客户端的 TUN 接管了这台 Mac 的流量（Shadowrocket、Clash 的 TUN 模式、系统设置里全局的 VPN）：停下内核让开，网卡名写进 root 那边的 `other-vpn`、日志记一行；那些路由没了再起内核、删掉它（退出时也删）。为什么：两个 TUN 一起开会抢路由。实测（2026-11-20，报的是「开了本机 UDP 走节点，微信打不开」）：Shadowrocket（NE 的 VPN，utun5，198.18.0.1/24，加 198.18.0.0/15，DNS 198.18.0.2）后开时，cca 的 TUN（当时是 198.18.0.1/30、按排掉的合并出的大段）系统栈回包发往的 198.18.0.2 被它截走，经 cca 的 TUN 的 TCP 全断（cca 的段更细，直接连 IP 的微信正好都进 cca 的 TUN）；先开 Shadowrocket 时 cca 加路由 `1.0.0.0/8: file exists`，TUN 起不来、内核却还在跑（看着像在运行）。辅助程序的 `udp_other`（`other-vpn` 只在启动脚本在跑时算数，只认网卡名）给 `udp-env` 的 `UDP_OTHER`、`_gui state` 的 `config.local.udp.other_vpn`（PROTOCOL 2.2、7.1）；`cca local udp`、`on` 说先让给了它（`udp_wait up` 遇到让开也算起来了，不算失败），STUN 看到大陆地址时说照它的规则出去，`udp_leak_hint` 也这么说；App 不提示重新打开
