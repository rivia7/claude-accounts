# Team

目标：把「维护者共享的账号」（policy.md）和「自己的同步服务器」（hub.md）合成一个概念。一个 Team 是一组设备加一份配置（哪些账号、各走哪个节点、节点的定义），
配置由管理员的设备维护、存在这个 Team 的同步服务器上；管理员给每台设备发邀请、定它能用哪些账号。一台设备可以在几个 Team 里。分阶段做，这一份跟着写：

| 阶段 | 内容 | 状态 |
|---|---|---|
| M1 | 线上格式和服务端：服务器的 `--mode team`、管理员和设备的 op、邀请链接、每台设备的配置（加密、签名），照文档独立实现一遍来测 | 做完了 |
| M2 | 辅助程序和命令：Team 在本机的状态（`~/.cca/teams/<编号>/`）、`cca team` 的建立、邀请、加入、取配置、看设备、移除、退出；管理员这边的账号、节点、每台设备的授权 | 做完了；服务器要自己起（安装脚本是 M6） |
| M3 | Team 成为唯一的概念：一个地方回答「这个账号属于哪个 Team」，代替 `HubKind`、`route` 和映射的读取；对账、收起账号、三条同步管线都按 Team；现在的维护者映射、自己的同步服务器当作旧式的 Team 接进来 | 做完了：账号表照 Team 的配置改，设备统计、记下的 API key、折合金额经各个 Team 的服务器同步（见「账号表照配置改」「同步经 Team 的服务器」）。旧的两套（维护者的映射、自己的同步服务器）照旧并着用，迁成 Team 是 M4 |
| M4 | 迁移：导入现有的映射和参考节点；用着维护者映射的机器自己迁过来；自己的同步服务器升级成 Team | 做完了（见「迁移」）：`cca team import`、`./policy.sh team` + 机器拉到映射后自己加入、`cca team import Team --mine`。自己的同步服务器是照步骤手动换，不自动 |
| M5 | 界面：`_gui state` 的 `teams`、账号的 `team`；侧栏、总览、菜单栏面板按 Team 筛选；管理员的管理页 | 没做 |
| M6 | 部署：安装脚本在一台服务器上装几个 Team（各是一个服务）、托管平台 | 没做 |
| M7 | 删掉旧通道：GitHub 上的映射仓库、手工登记 deploy key、`policy.sh` 的发布 / `key` / `lock`（至少两个正式版以后） | 没做 |

定下来的（用户 2026-11-21、22 定的，照它做，别重新讨论）：

- 照「干净架构」做：Team 是一等概念，旧的两套（`HubKind` 的 maintainer / own、`policy_*`、`own.` 开头的文件）只留作迁移用的垫片，写明什么时候删。
- 授权是**每台设备一个邀请链接**：管理员生成时勾好这台设备能用哪些账号（以后能改），对方粘贴就行，没有「申请—批准」的来回。
- 一台服务器可以放几个 Team，**每个 Team 一个服务**（容器）：服务端进程还是只管一个 Team。
- 弃用公钥授权：不再手工加 deploy key、不再从 GitHub 拉映射；维护者的 `policy.json` + `custom.yaml` + `./policy.sh` 换成管理员设备上的 `cca team` 和 App 的管理页，
  现有的映射和参考节点导入一次。锁定请求不要了。
- 界面上按 Team 筛选的是侧栏、总览、菜单栏图标点开的面板；筛选只管显示，`~/Applications` 里有哪些启动器不跟着变。
- 不经 Team 共享第三方 API 账号（等于把 key 发给别人）。

## 信任

- **Team 的根密钥**（ed25519）在管理员的设备上。服务器只配置根公钥（公开的），所以服务器上没有要保密的东西：被攻破了、放在托管平台上，
  都读不了、改不了配置。Team 的编号是根公钥的 SHA-256 的前 32 个十六进制字符；它只是个名字（目录名、认证里的一项），认一个 Team 比的是整把根公钥。
- **管理员 = 拿着根密钥的设备**：管理员的请求拿根密钥签名，服务器不另记谁是管理员。几台设备都当管理员就是都有这把密钥（M2 以后做）；
  所以没法单独撤掉一个管理员，只能换一个 Team。
- **每台设备一把配置的密钥**：邀请链接里那串随机数 `k` 派生出加入用的令牌、设备的编号和这台设备那份配置的密钥。只有管理员和这台设备知道 `k`，
  所以别的设备、服务器都读不了这一份。辅助程序没有非对称加密（依赖是白名单），这样不用加依赖。
- **配置防伪造、防调包**：密文带认证（Team、设备、序号都在里面），外面再有根密钥的签名；设备照邀请链接里钉住的根公钥验。两层各管一头：
  签名挡的是拿到了链接（有 `k`）的人伪造配置，认证挡的是挪到别的设备、别的序号上。
- **设备的公钥要过认证码才记**：设备加入时拿 `k` 给自己的公钥算一个认证码（`proof`），服务器原样存着、回给管理员；管理员照自己算的 `k` 核对，
  对得上才把这把公钥记成这台设备的，记下以后服务器再报别的公钥不照它的。服务器不知道 `k`，换不了公钥——不然它把公钥换成自己的，等管理员哪天
  搬到一台干净的服务器、照记下的公钥登记，那台干净的服务器上就多了一台它的设备。
- **管理员不把服务器的话当真**：名单、「存上了」「序号不够大」都没有签名，只当线索用。它说的序号要像话（不比记着的小、没到上限）才接着往上加；
  它那边某台设备的配置比发布过的旧就重新发布；回话里没提到的设备不当成不在了。
- **盐在配置里，不在邀请链接里**：账号摘要、API key 和折合金额的密钥都由它派生，整个 Team 一份。链接漏了、没用上的，带不出它。

做不到的，文档和界面里要照实说：

- 邀请链接就是那台设备的解密密钥，要当密码传；只能用一次，默认几天过期。**用之前**被别人拿到：别人冒充这台设备加入、取走给它存的配置
  （节点的凭证在里面），真的那台再用时服务器说用过了——管理员据此移除那个编号、换节点的凭证。这是「粘贴就加入、没有批准的来回」的代价
  （公钥的认证码挡不住它：拿到链接的人也有 `k`）。**用之后**被别人拿到：加入不了，但弄得到服务器上这台设备的密文的话解得开。
- 序号只增不减只挡得住「服务器拿旧的一份来换一台一直在用的设备手里的」。刚加入的、重装过的设备手里没有序号，服务器给哪一份它都只能认；
  服务器扣着新的不给，设备也看不出来，只能提示「多久没更新了」（明文里有管理员发布的时间）。管理员看名单时看得到各台设备手里是第几版（`have`）。
- 成员之间：盐是整个 Team 一份，所以知道邮箱的成员算得出别的账号的摘要（看得到它在哪些设备上在用、能往它的 API key 那一格里传东西——别的设备
  不认伪造的，只是白占一次同步）；API key、折合金额的内容要登录过那个账号才解得开，没给它这个账号的设备解不开。和现在维护者的服务器上一样。
- 服务器能让设备停在旧的配置上：扣着不给、对管理员谎称存上了、把设备从名单里藏起来（管理员会当它退出了，等它再出现才接着发布）。
  它也能让设备以为自己被移除了、或者以为服务器的记录没了（那个编号 `gen` 没有签名）：后果是说法不对，被说成移除了的设备拿新的邀请能直接换上。
- 移除一台设备收不回它已经看到的节点凭证，只能换节点的凭证。
- 根密钥丢了这个 Team 就得重建：建的时候提示导出备份。
- 管理员的设备不在线时，新的授权、老机器的迁移都等着；已经加入的设备照常用。
- 请求的签名里没有「发给哪台服务器」：同一个 Team 搬到新服务器时，旧服务器收到过的请求 5 分钟内能拿去新服务器重放一次。搬的时候等 5 分钟再用新的。

## 服务端（M1）

`server/cca-presence.py --mode team --team-root 根公钥`（`CCA_TEAM_ROOT`）。op、邀请链接、设备的配置的格式在 server/README.md「Team 的同步服务器」，
这里只写为什么这样：

- 管理员的 op（`team_enroll`、`team_invite`、`team_put`、`team_members`、`team_revoke`）拿根密钥签，`key` 是根公钥的指纹；设备的 op
  （`team_join`、`team_get`、`team_leave`，还有原来的上报、查看、API key、折合金额、中转）拿设备自己的密钥签。根密钥不是设备，别的 op 不认它。
- `team_enroll` 直接登记公钥，三处要用：管理员自己的那台设备（不用给自己发邀请）；服务器的记录没了以后把各台设备登记回去（`team_members`
  回过公钥，管理员留着）；迁移时登记老机器的 deploy key（服务器照旧认它们签的请求，那些机器上的旧版 cca 不用动）。
- `team_join` 先看有没有这个邀请（便宜），有才验签；没有这个邀请和签名不对回一样的 403。签名对了才说过期了还是用过了：拿着真的邀请的人
  才问得出来，而「这个链接已经在另一台设备上用过了」是最常见的要说清楚的情况。
- 配置按设备的编号存、不按密钥：管理员在设备加入以前就能存好，设备一加入马上取得到。存在状态文件旁边的 `team-docs.json`（心跳不用跟着重写它）。
- `team_put` 的序号一样、认证码也一样的算存过了（管理员没收到回复再发一次）；一样的序号、不一样的内容不存。
- 没有自己的同步服务器的入伙口令、盐的校验值、换口令那一套：邀请是一台设备一个，盐在设备的配置里。服务器的记录没了（`gen` 变了）以后，
  设备自己加不回来（邀请只能用一次），由管理员照留着的公钥登记回去、再存一次配置（M2；同一个序号再存一次服务器照收，设备手里就是这一份）。
- 根密钥不是设备：拿它登记、加入都不收（不然「别的 op 不认它」就不成立了）。
- 配置跟着编号走：移除设备、撤回邀请时删掉；邀请过期 30 天被清掉时，预先给它存的也删掉（`docs_prune`，启动时也清一遍：移除时先写状态文件、
  再写 `team-docs.json`，中间停了会留下没人认的）。过期、用掉的邀请在发邀请、存配置、看名单时顺带清（`invite_prune`）。
- `team_get` 记下设备说的 `have`（只在内存里），`team_members` 回给管理员：管理页据此说哪台设备还没用上新的配置。
- 状态文件手改坏了的：样子不对的邀请、设备在启动时去掉（`team_setup`），不让以后每个请求都出错。
- 管理员的请求（根密钥签的）另有一个限额：每秒 2 个、攒得下 120 个（设备的是每 2 秒一个、攒得下 30 个：管理员的一条命令要问两三次，
  连着发几个邀请、改几次授权就不够用了）。`team_enroll`、`team_put` 照样一次带一批（最多 64 台），不要一台一个请求。
- 换模式：状态文件是别的模式的（或者根公钥换了）就从头开始（`Store.reset`），三种模式互相都是这样；别的模式的服务器旁边不留空的 `team-docs.json`。
- `team_put` 的 1 MB 请求上限只在 Team 的服务器上放宽：别的模式里这个 op 不存在，照旧 64 KB。

还没做的（M6）：安装脚本、托管平台的预设（`CCA_HUB_HOSTED=1`）都还是自己的同步服务器那一种。

## 设备拿到的配置

明文就是这台设备的映射加参考节点，样子照现在的 `policy.json`、`nodes.json`（对账、补节点的规则不用重写），再加上盐和服务器在哪：

```
{"v": 1, "at": 管理员发布的时间, "name": Team 的名字, "salt": 盐,
 "server": {"u": 地址, "p": [证书公钥的指纹…]},
 "accounts": {"claude": {邮箱: 节点}, "codex": {…}, "agy": {…}},
 "aliases": {邮箱: 别名}, "install_node": 节点,
 "nodes": {"group": 组名, "proxies": [节点定义…]} | null}
```

只有给了这台设备的账号、这些账号要的节点（连同它们经 `dialer-proxy` 连着的、安装客户端用的那个）。Team 的编号、设备的编号、序号不在明文里：
它们在认证和签名里。管理员发布前、设备用之前都照 `doc_problems`（`cli/src/cmd/team/doc.rs`）查一遍：邮箱小写、节点的定义照 `fill_problems`，
不认得的项不管（以后加的旧版本照样用）。`name`、`server` 变了设备跟着改 team.json：管理员改名字、搬服务器、换证书都不用重新发邀请。

## 账号表照配置改（M3 的第一步）

映射原来只有一个来源（维护者的 `policy.json`、`nodes.json`），对账、补节点、固定节点都经 `core/policy.rs` 的那几个读取函数。现在它们给的是
**合起来的**：各个 Team 给这台设备的配置在前（照加入的先后），维护者的映射（旧的通道）在后，同一个账号先出现的算数。所以对账（`reconcile`）、
`policy_merge`、`fill_plan`、路由器端的 `--fill-source` 都没动，Team 给的账号和维护者映射里的账号走的是同一条路：

- `core/team.rs` 的 `grants()`：各个 Team 手里验过的那一份配置（一个进程只读一次）。还没取到的不算；被管理员移除了的（`sync.json` 是 `removed`）
  也不算——手里那一份不再算数。`lost`、`error` 的照旧用手里的。
- `core/policy.rs`：`mapping(tool)` 是合起来的 [(邮箱, 节点, 谁定的)]，`policy_raw` / `policy_map`（节点）、`policy_sources`（谁定的：Team 的编号，
  维护者的映射是空的）、`policy_names`（别名）、`policy_fill`（节点的定义：同名的先出现的算数，策略组照第一份有节点的）、`policy_install_node`
  都从它来。只有维护者的映射时和以前逐字节一样（`policy_fill` 的 `id` 也一样：路由器不会因此重新校验）。`legacy_raw` 是只看维护者的那一份：
  `cca policy off` 收起哪些账号、`_gui state` 的 `config.policy.accounts` 用它（Team 给的账号不归那个开关管）。
- 对账时说的话照是谁定的说（`by_whom`）：「按维护者的映射…」或者「按「Team 的名字」的配置…」。事件的代码不变（`policy_added`、`policy_alias`、
  `policy_pinned`、`nodes_filled`）。
- **Team 加进来的账号记着是它加的**（工具状态里的 `team_added`：{账号目录名: Team 的编号}，`policy_merge` 照 Team 的配置加的才记）。映射里没有它了
  ——管理员不再给这台设备、退出了那个 Team、被移除了——就收起来（`team_park`：记进 `parked`（带着 `team`：`_gui state` 的 `config.policy.parked`
  只数关掉共享时收起来的）、从账号表去掉，登录目录和钥匙串不动；事件 `team_parked`），再给回来时照原来的键加回去，不用重新登录。正开着命令行
  会话的先不收（`team_busy`），下一条命令再看。那个 Team 的目录还在、配置却读不出来时说不准还给不给（`grant_settled`）：不收。这台机器**本来就有**的账号
  Team 只管节点、不记成它加的：不再给了账号还在，只是节点不再被固定。
- 账号走哪一类同步服务器（`cmd/hub.rs` 的 `route`）看是谁定的：Team 给的是 `HubKind::Team(编号)`，维护者映射里的是 `Maintainer`，别的官方账号是
  `Own`（见下一节）。
- 配置什么时候取：`cca team join`、`cca team sync`；启动时 `team_hook`（在 Team 里、距上次超过一个小时就在后台 `cca _team-sync`，只换本机存的那一份）。
  账号表在下一条读它的命令里照新的改；`cca team join / sync / leave`、管理员的 `import / map / publish / attach` 之后马上做完（`team_settle`：
  没配置过路由器的把配置带的节点导入可选节点，`py team-apply` 对一遍，同步路由器，改启动器）。
- 管理员自己这台设备默认拿全部账号（`grants` 是 `all`）：导入映射以后那些账号都会加进它的账号表。不要的话 `cca team grant Team 自己这台 none`
  （或者只留几个）。

还没改、要知道的：`cca policy` 列出来的受约束的账号里也有 Team 给的，说法还是「维护者的映射」；别处说「被维护者的映射固定」的提示（改节点、
`cca edit` 时）对 Team 给的账号也是这句话。等维护者的映射迁成 Team（M4）一起改。

## 同步经 Team 的服务器（M3 的第二步）

设备统计、记下备查的 API key、折合金额三条管线本来就是「这台设备用得了的每台服务器一条线」（`hub.rs` 的 `hubs()`，见 hub.md）。现在 `hubs()` 里
多了各个 Team 的服务器（`HubKind::Team(编号)`，照加入的先后排在维护者的、自己的后面），所以三条管线不用改：

- 一个 Team 的服务器在这台设备上用得了（`cmd/team.rs` 的 `hub_cfgs`）：接上了服务器、这台设备在 Team 里的密钥在、手里有验过的配置（盐在配置里）、
  没被管理员移除，而且没关掉设备统计（`"presence": false`）。请求拿这台设备在这个 Team 里的密钥签名，盐是这个 Team 的那一份：别的 Team、
  别的服务器上的账号摘要和密文都对不上。
- 账号走哪台：`route` 照 `policy_sources`——某个 Team 给的走那个 Team 的；维护者映射里的走维护者的；别的官方账号走自己的。**同一个账号 Team 和
  维护者的映射里都有时是 Team 的算数**（节点、同步都是），所以它不再经维护者的服务器同步：那台服务器上别的设备看不到这台设备在用它。
- 状态文件各是各的：`presence/` 和 `cost/` 里 `team.<编号>.` 开头（`HubKind::file`）。退出、被管理员移除（取配置时知道的）以后把它们删掉
  （`drop_synced`）：不再读它们，而 `cost/` 里那一份是解开了的别的设备的折合金额，不该留在这台设备上。
  删的时候别的进程正好在同步（拿着 `team.<编号>.keys.lock` 之类的锁）时，它收尾写回的几个文件会留下来：服务器已经用不了了，没有害处，
  也不值得为它多做一遍清理。被说谎的服务器骗成「移除了」时丢的只有这些同步的状态和缓存，重新邀请、再同步一次就有了（key 本身在钥匙串里）。
  `cca restore` 的备份也不带 `cost/team.*.remote.json`（卸载时各个 Team 先退出、已经删了；排除清单是第二道：那个 Team 的目录不在了、
  退出时删不到的也不进备份。回归里放一份假的核对）。
- 上报进程每个 Team 一路（配置里的 `rev` 是 team.json 的修改时间：重新加入、配置里换了服务器以后算新的一路）。它一直开着，而各个 Team 的配置
  在一个进程里只读一次（`grants()` 记着）：所以每一圈先 `forget_grants()` 重读，并且盯着 `teams/` 和里面每个 Team 的目录——加入了、退出了、
  取到了新的配置、被移除了，马上醒来换各路（不只盯已经有一路的：刚加入、配置还没取到的也盯着）。`teams/` 是上报进程开着的时候才第一次
  建出来的（这台设备第一次加入）时要到下一圈才开始盯，最多晚一次心跳。
- **没有账号经它时一次都不报**（`Lane::quiet`）：加入了一个 Team、它给的账号却没在用（没登录，或者这个账号是另一个 Team 先给的）时，不必每分钟
  告诉它的服务器这台设备开着。这一路从「报过什么都没开」起步；有会话了照常报、心跳，都关了报一次 `end: none`，然后又不出声。算下一次什么时候
  醒时不算这几路（它们的 `due` 没人动，算进去就成了每秒醒一次）。维护者的、自己的那两路照旧（没有账号时也心跳）。
- 服务器不认这台设备时（被移除了、服务器的记录没了）不自己重新加入——等管理员（`own_recover` 只给自己的同步服务器用）；那一路隔 10 分钟再试，
  下一次 `cca team sync`（启动时每小时一次）以后知道是被移除了，这一路就停了。
- 没成的原因前面带着是哪个 Team（`hub_why`：「「名字」的同步服务器：…」）；`cca devices` 里账号不经服务器时的原因照 `hub_missing_why`。
  「服务器太旧」那两句（`COST_OLD`、`KEYSHARE_OLD`，让维护者更新服务器）只对维护者的服务器说（`is_maintainer`：配置里没有 `"hub"`）。
- 一个 Team 的密钥文件读不了只是它用不了（`hub_cfgs` 跳过它），别的服务器照常。没有 Team（或者都还没取到配置）的机器上 `hubs()` 只多两次
  落空的系统调用（`teams/index.json`、`teams/`），不多读 config.json。
- 给界面和脚本的输出里是哪个 Team 写在旁边（可能同时在几个 Team 里，`kind` / `hub` 都是 `team`）：`_gui state` 的 `config.hubs` 里 Team 的项带
  `team`（编号）、`team_name`；账号多一项 `team`——是哪个 Team 给的，不看它的服务器用不用得了，不是 Team 给的（第三方 API 账号也是）没有这一项（没有 Team 的机器
  输出和原来逐字节一样）；`devices --json` 的账号和 `hubs[]`、`cost sync --json` 的 `sync.hubs[]` 里 Team 的也带 `team`。现在的 App 不认识
  `team` 这个种类（账号当作不同步、`config.hubs` 里跳过那一项），页面等 M5——Swift 的 `HubKind` 到那时再加，不然现在的「共享与同步」页会把
  Team 的服务器照维护者的那一台来显示。

## 迁移（M4）

旧的两套在删掉之前（M7）照常用：迁移是往 Team 那边搬，搬的过程中两边并着。

### 维护者的映射 → Team

维护者（管理员）这边，在自己的 Mac 上：

1. `cca team new 名字`，部署服务器、接上（`cca team attach`；一键部署是 M6）。
2. `cca team import Team 映射仓库/policy.json 映射仓库/nodes.json`：账号 → 节点、别名、安装客户端用的节点、参考节点导进 Team 的配置。
3. `./policy.sh team Team [-C 映射仓库的目录] [-y]`：把各台机器迁过来（下面说）。以后仓库上加了机器、有的邀请过期了，再运行一次。

**各台机器怎么拿到邀请**：没有「申请—批准」的来回，也不用一台台发链接。映射仓库上每台机器有一把 deploy key；`./policy.sh team` 列出它们
（只读、启用的 ed25519），辅助程序的 `team-handoff` 给每一把发一个邀请（账号全给：以前每台机器拿到的也是整份映射），照指纹写进 policy.json 的
`team` 一节，然后照常检查、签名、推送：

```json
"team": {"v": 1, "invites": {"SHA256:<deploy key 的指纹>": "cca-team1.…", …}}
```

机器这边（`cmd/team.rs` 的 `adopt`）：拉到映射以后（`cca policy pull`、后台的 `_policy-fetch`、每小时的 `_team-sync` 都顺带看一次），里面有
自己 deploy key 的那一项、自己还不在那个 Team 里，就拿这个邀请加入——**设备密钥就拷原来的 deploy key**（`teams/<编号>/id_ed25519`），
不新生成。加入以后账号表照 Team 的配置改（同一个账号 Team 和映射里都有时是 Team 的算数），三条同步管线改走 Team 的服务器。

- 可信：映射验过发布密钥的签名才换上，里面的邀请和映射一样可信；共享关着的机器不看它。旧版本的 cca 不认识 `team` 这一节，照样用映射
  （客户端不查不认识的字段；维护者发布前的 `_policy-check` 认得它、查它的样子：`team_section_problems`）。
- **邀请写在映射仓库里，能读仓库的机器都看得到。** 这没有比现在多暴露什么（现在每台机器本来就读得到整份映射和参考节点），但一台机器可以
  拿给别的机器的邀请去加入。所以每个邀请指定了要拿哪把公钥加入（admin.json 里那台设备的 `expect`；`cca team invite --key` 也能手工指定）：
  对账时（`reconcile`）服务器报的公钥不是它，就记成 `mismatch`：这段时间一个账号都不给它（`build_doc` 看这个记号，授权本身不动），
  告诉管理员移除它（提示里带设备编号：同名的不止一项）；它已经取走的那一份收不回来（它本来就有）。服务器没报公钥不算，后来报的
  对上了记号就去掉——服务器一时说错，不该把一台好好的设备的账号永久拿掉。被抢了邀请的那台加入时服务器说用过了，记下不再试；
  管理员再运行一次 `./policy.sh team` 就给它新发一个。
- 幂等：那串随机数是照主密钥和序数算的，发过的链接能原样再算出来。拿指定的公钥加入了的不再发；发过、没用、离过期还有三天以上的照原来的；
  别的新发（30 天过期），同一把公钥以前没用上的那几项去掉、服务器上的邀请撤回。都加入了就把 `team` 一节从映射里去掉。管理员自己这台
  （它的 deploy key 多半也在仓库上）本来就在 Team 里，不发。服务器上还没用掉的邀请最多 64 个：机器更多时分几次（前面的加入了再运行）。
- **走了的不自己请回来**：自己退出了的（`left`）、管理员移除了的（`revoked`）那台机器，`./policy.sh team` 不再给它发（输出里列出来）——
  不然移除、退出都留不住：它的 deploy key 还在仓库上，下一次运行就又回来了。要它回来：管理员手工 `cca team invite Team 名字 --key '它的公钥'`
  （再运行 `./policy.sh team` 时这个邀请照原来的写进映射），退出过的那台还要自己 `cca team join`。设备这一头也一样：自己退出过这个 Team
  的（`teams/adopt.json` 的 `left`，按 Team 的编号记，`cca team leave` 时记）不再照映射里的邀请自己加入，手动加入成了才去掉这个记号。
  仓库上删掉了 deploy key 的机器不在这条命令看得到的范围里：它已经加入的不会被移除（要移除用 `cca team revoke`），给它发过、没用的
  邀请留在服务器上直到过期（占着 64 个名额里的一个，最多 30 天）。
- 不反复打扰：`teams/adopt.json` 的 `links` 记着每个邀请（存摘要，不存链接）试的结果——加入了、用过了 / 过期了 / 服务器不认的不再试；
  连不上、服务器出错、名额满了之类一时的原因过一个小时再试。同时只做一个（`teams/adopt.lock`：后台拉映射和取配置可能撞上）。
- 请求到了服务器、回话没收到：邀请已经用掉，本机却什么都没留下。下一次再试时服务器说用过了——拿的是同一把 deploy key，所以接着取一次
  配置，服务器认它是这个邀请的那台设备（回的编号对得上）就是已经加入了，把本机这一头补上（手动加入每次新生成密钥，没有这一步）。
- 管理员移除了这台设备以后，映射里换了新的邀请（管理员手工发的）才会再加入。
- 设备密钥沿用 deploy key，所以同一把密钥给三处签名：GitHub 的 ssh 登录（另一种签名）、维护者的设备统计服务器、Team 的服务器（后两处
  都是 `ssh-keygen -Y sign -n cca-presence`）。这是故意的，不串：请求里写着 op，服务器只认发到那个地址的那一种，`team_*` 这些 op 旧的
  服务器没有、Team 的服务器也不收别的；随机数 5 分钟内不重复。
- 加入不出声的地方：后台拉映射、后台取配置时（账号表在下一条命令读它时照新的改）。终端里 `cca policy pull`、App 的定时拉取会说一句
  「照维护者的映射加入了…」，接着 `team_settle`。这条命令启动时要是正好也起了后台的取配置（`team_hook`，每小时一次），后台那个可能先拿到
  `adopt.lock` 把加入做了：前台看到有人在做就让开，这一句不说（加入照样成；回归里测前台这一句时先 `touch teams/checked` 不让后台起）。
- 迁移期间：加入了的机器把这些账号的设备统计、API key、折合金额报给 Team 的服务器，没迁的还报给维护者原来那台，**两边各看各的设备**。
  都迁完以后维护者把账号从映射里删掉（或者整个停用映射）。

### 自己的同步服务器 → Team

自己的几台设备并成一个 Team，代替 `cca hub`。设备少、都是自己的，照步骤手动换，不自动：

1. 一台设备上 `cca team new 名字`，部署服务器、接上。
2. `cca team import Team --mine`：把这台设备上自己的官方账号（不是维护者共享的、不是别的 Team 给的、不是第三方 API 的）连同现在走的节点、
   别名加进 Team 的配置。节点的定义不带（各台设备自己有：同一个路由器，或者各自的内置代理）。
3. 给别的设备各发一个邀请（`cca team invite`），在那台上 `cca team join`。
4. 都换过来以后各台 `cca hub leave`，服务器上卸掉旧的那一个。

换过去以后这些账号的节点由 Team 的配置固定（管理员的设备上 `cca team map` 改），不再是各台设备自己选。折合金额、记下的 API key 各台设备
自己有一份，换了服务器会重新传上去，不丢。没换的设备还在旧的服务器上，两边各看各的，直到都换完。

## 本机的状态和命令（M2）

`~/.cca/teams/`（目录 700，密钥、配置、状态文件 600，`ssh-keygen` 生成的 `.pub` 是 644；整个在 `CCA_DIR_PRIVATE` 里；布局在 `cli/src/core/team.rs` 开头）：`index.json` 是加入的先后，每个 Team 一个目录
（名字是编号）：`team.json`（名字、服务器、根公钥、角色、这台设备的编号和它在服务器上的名字、`gen`）、`id_ed25519`（这台设备在这个 Team 里的密钥）、
`secret`（邀请里那串随机数）、`doc.json`（验过、解开的配置和它的序号）、`sync.json`（最近一次取配置的结果，变了才写）、`lock`；管理员的另有
`root_ed25519`（根密钥）和 `admin.json`。index.json 里没有、目录在的也算（排在后面：建到一半、加入到一半被打断留下的，`teams()`）。
**一个 Team 一把锁**（`team_lock`：`flock` 那个 `lock` 文件）：取配置、管理员的每条命令整条拿着——读 admin.json、联网、写回这一段别的命令插不进来，
不然两个邀请会用同一个序数、算出同一把密钥。锁着的时候会联网，所以不用全局的 `Lock`（index.json 才用它）；同一个进程里不能拿两次（已经拿着的调 `sync_locked`）。分层：`core/team.rs` 只读文件（以后对账用它，不碰密钥、不联网），格式和密码学在 `cmd/team/doc.rs`，
设备这一头的子命令在 `cmd/team.rs`，管理员的在 `cmd/team/admin.rs`；bash 的 `cmd_team` 只管问和说。

设备这一头：

- `cca team join [--stdin] [--name 名字]`（`py team-join`）：邀请链接经 `ask_secret`（`team.join`）或者 stdin 给，不进命令行。生成这台设备的密钥，
  拿邀请里的令牌加入，带上公钥的认证码；服务器回的设备编号要和自己照 `k` 算的一样。成了写 team.json、`secret`、记进 index.json，马上取一次配置。
  没成什么都不留——连不上时请求可能已经到了服务器（那样邀请就用掉了）：原因里说再试一次、说用过了就让管理员移除重发。已经在这个 Team 里的不换
  （免得一条旧链接把正用着的换掉），只有被移除了的（`sync.json` 是 `removed`）拿新的邀请直接换上；team.json 坏了、管理员的密钥还在的也不当成没有。
- `cca team sync [Team]`（`py team-sync`，`sync_one`）：`team_get` 带着手里的序号。回来的那一份先核对设备编号，再验根密钥的签名（`ssh-keygen` 用不了
  和验不过分开说，都不用它）、认证解密、查内容；序号比手里的小的不要，一样的什么都不动，大的才换上：**先**照它改 team.json（名字、服务器在哪）、
  **再**写 doc.json（中间断了下次接着做完）。结果记进 sync.json：`ok`；`removed`（403 `unknown_device`，`gen` 和记着的一样）；`lost`（`gen` 不一样：
  服务器的记录没了，等管理员登记回去，这台设备什么都不用做）；`error`（连不上、签名不对、内容不对……原因在 `error`，手里的那一份照旧用着）。
- `cca team leave [Team]`（`py team-leave plan | apply`）：先问（成员 `consent team_leave`，管理员 `team_delete`，范围是 Team 的编号）。请服务器移除
  这台设备（连不上也接着退），本机的目录删掉。管理员退出就是根密钥没了。
- `cca team [ls] [--json]`（`py team-list`）：只看本机记着的。状态另有 `local`（管理员还没接上服务器）、`pending`（还没取过）。

管理员这一头（`admin.json` 的样子在 `cmd/team/admin.rs` 开头）：

- `cca team new 名字`：生成根密钥、主密钥（32 个随机字节）和盐，这台设备是第 0 台设备。先在 `teams/.new.<进程号>` 里建好再改名（编号要有了根公钥才知道；
  以前建到一半留下的过一个小时清掉）。说下一步：服务器用这把根公钥运行，再 attach。
- **每台设备那串随机数不存**：`k = HMAC(主密钥, "cca-team-k-v1\0" 序数)` 的前 16 个字节，要用时重算（`device_secret`）。所以管理员这边要备份的只有
  根密钥和主密钥；序数发一个邀请用掉一个（没发成也不回收）。导出、交给第二个管理员的命令还没做。
- `cca team attach Team 地址 [指纹…]`：先 `team_enroll` 这台设备（服务器认不认这把根密钥、是不是 Team 的服务器，这一下就知道；认了才把地址写进
  team.json），再对一遍、发布。**换一台服务器**也是它：先在 admin.json 记下 `moved_from`（原来那台的地址、还没用掉的邀请），新的那台上把加入过的设备
  都登记回去、配置都发布一版（里面是新的地址），最后到原来那台上收尾（`finish_move`）——没用掉的邀请撤回（它们写的是原来那台的地址：不撤的话拿着的人
  会加入一台没人管的服务器；这边记成 `expired`，要重新发），同一个序号的配置也存一份上去：还连着原来那台的设备下次取配置时拿到它、照 `server`
  换过去，到新的那台上发现手里的就是它存的那一版。中途没做完的（`moved_from` 还在）下次 `attach`、`publish` 接着收尾；原来那台连不上时说一声
  （`fail_warn team_forward`：那些设备找不到新的服务器，要重新邀请）。
- `cca team invite Team 名字 [--accounts all|工具:邮箱,…] [--ttl 秒]`：取下一个序数算出 `k`，`team_invite` 登记令牌的哈希，记进 admin.json，
  马上把它的配置存上去（设备一加入就取得到）。邀请链接只打到 stdout 一行；在 Claude Code 的会话里不给。默认 7 天过期。
- **和服务器对一遍**（`reconcile`，`devices`、`grant`、`import`、`map`、`publish`、`attach` 都先做）：`team_members` 的名单和 admin.json 比——
  - 加入了的设备 `invited` → `joined`，名字照服务器的（样子不对的不要）。公钥第一次见到时过了认证码才记下（没过的照样给它发布配置，名单里的
    `problem` 说一声：服务器的记录没了以后它登记不回去）；记下以后服务器报的不一样就不照它的（`problem`）。管理员自己这台的公钥是本机的。
  - 邀请不在了、设备也没加入的记成 `expired`（管理员分不出是过期了，还是加入以后没等到对这一遍又退出了）。
  - `gen` 没变、服务器上却没有了的是自己退出了（`left`，不登记回去；它又出现了恢复成 `joined`）。
  - `gen` 变了（服务器的记录没了、换了一台）才照**记下的**公钥把 `joined` 的都登记回去、配置都重新发布。
  - 服务器上某台设备存着的那一版比发布过的旧（它的记录回滚了、丢了）：重新发布。
- **发布**（`publish`）：给每台 `invited` / `joined` 的设备照授权拼出明文，内容的摘要（发布时间不算）和上次发布的一样就不动；变了的序号加一、
