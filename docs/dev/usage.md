# 用量、套餐和额度

## 查用量
- cca 不用打印模式（`claude -p`、`agy -p`）和 Codex 的非交互模式（`codex exec` 这些；维护者明令禁止：怕被当成自动化、封号。2026-11-26 起）：Claude、Antigravity 的用量不查，只读 cca 启动的交互会话里记下的（`Tool::usage_passive`，`_gui hello` / `state` 的 `features.usage_passive`）；只有 Codex 还查（codex 的 app-server：`usage_one` → `py usage-query`）。`py launch-check` 也不让经 cca 用打印模式（`print_mode`：Claude Code 的 `-p`、`--print` 和几个短选项写在一起里有 p 的 `-cp`；agy 的 `-p`、`--print`、`--prompt`，Go 的 flag 一个横线两个横线都一样；Codex 的 `exec`（别名 `e`）、`review`、`cloud exec`：`CODEX_ONESHOT`，codex 0.172.0 的帮助里写着 non-interactively 的。codex 在开场白、选项后面也认子命令（`codex 修一下 exec hi` 跑的是 exec，真的 codex 上用 `--help` 核对过），所以还没遇到别的子命令时，不是选项的值的每一个都看；`--` 后面的、别的子命令后面的（`resume review` 的会话名）不算；Codex 的 `-p` 是 `--profile`，不是打印模式），说「是打印模式（Codex：非交互模式）……直接开会话」。3.7.5 及以前查 Claude 用的是 Claude Code 标为实验性的 SDK 控制请求 `get_usage`（`claude -p --safe-mode … --input-format stream-json`），查 agy 用的是打印模式的 `/usage`，都去掉了，别再加回来
- 怎么记下（`cli/src/cmd/statusline.rs`、`agy.rs`）：`py launch-args` 给交互的会话加一条只这一次有效的状态栏命令（Claude Code：`claude_launch_args` 的 `--settings` 里的 `statusLine`，和 hooks、第三方 API 账号的设置是同一份 `--settings`；agy：`agy_launch_args` 的 `--settings`，见 accounts.md「agy 的套餐」）。Claude Code / agy 每次状态变了都起它，从 stdin 交一份 JSON：Claude Code 2.1.332 的 `rate_limits.five_hour` / `seven_day`（`used_percentage` 是 0–100、`resets_at` 是 Unix 秒；订阅的账号收到第一个回应以后才有；`spend_limit` 是网关定的花费上限，不要；没有套餐、邮箱），agy 的 `quota`（以桶的 id 为键，真实账号上是 `gemini-5h`、`gemini-weekly`、`3p-5h`、`3p-weekly`：`remaining_fraction`、`reset_time` 或 `reset_in_seconds`、`disabled`；另有 `email`、`plan_tier`）。`cca _claude-statusline` / `cca _agy-statusline` 在脚本开头找到辅助程序就交给它（不读整个脚本），换成 usage.json 的样子（Claude：`claude_rate_limits`，和以前查到的窗口一样；agy：`agy_quota_rl`，换成打印模式的 `/usage` 给过的 `{groups: [{name, buckets}]}`：id 的后缀 `5h`、`weekly` 是窗口，前缀按 `AGY_GROUPS` 认组，一组里 5 小时排在本周前面），交给 usage.rs 的 `usage_note`：账号目录要对应账号表里的一个官方账号、登录的就是这个账号（agy 另拿 JSON 里的邮箱比）；同一个会话的请求计数（Claude Code 的 `cost.total_api_duration_ms`，agy 的 token 数和花费）没变就不记（重画状态栏时额度还是旧的，记下就把旧的数当成刚取到的了），usage.json 的 `seen` 记着最近 8 个会话；额度和记着的一样时 Claude 最多 `USAGE_NOTE_EVERY`（60 秒）刷新一次取到的时间（额度是每个回应带回来的），agy 不写（不知道它多久取一次）；连同每周用量写（`usage_write`），写了让配对的手机更新（`status_kick`）。自己什么都不输出，出什么错都不说
- 用户自己的状态栏：Claude Code 的照先后找（这个目录的 `.claude/settings.local.json`、`.claude/settings.json`，再是账号的 settings.json，也就是共享的那一份；先找到的算），找到了就照用户的那一份（padding、refreshInterval 这些都留着），命令换成 cca 的 + `--then '<用户的命令>'`（`run_then`：同一份 JSON 接着交给它，它的输出、退出码就是状态栏）；读不了、不是 JSON 对象的文件不加（不知道用户配了什么，别盖掉），`type` 不是 command 的不动。不加的（`claude_takes_statusline`）：打印模式、`--version`、`--help`、子命令（`CLAUDE_SUBCOMMANDS`：2.1.332 的程序里登记在最上一层的）、用户自己写了 `--settings`（Claude Code 只认后写的那个，cca 的那一份连同 hooks 一起没了）、第三方 API 账号。Claude Code 不起状态栏命令时记不下：还没信任这个目录、`disableAllHooks`、托管的设置里有 statusLine（比 `--settings` 先）
- `cca usage`（Claude、agy）不经出口、不起后台查询：`py usage-render ""`（tmp 空着就是全用记下的）。刚记下的（Claude 10 分钟、agy 30 分钟内）不说多久前，旧了备注写「N前记下」（`age_note`；Codex 查询失败拿缓存顶上的照旧写「缓存（N前）」）；还没记下的写怎么记下（「cca @账号 开一次会话、发一句话以后就有」），`--json` 里 `source` 是 `none`、`error_code` 是 null（不算出错）；表格下面一行说这些数是会话里记下的（`passive_note`，终端窄了换短的说法）；有一个登录着就是退出码 0。App 不定时跑它、不放「刷新用量」（`features.usage_passive`，macos/CLAUDE.md），usage.json 变了重读 state 就有
- 这样做丢了的（定下来的取舍，别再走回头路）：只有经 cca 启动、用过的账号有新数，别处（Claude App、直接运行的 claude / agy）用掉的要等下次经 cca 用时才知道，好久没用的账号显示上次记下的；Claude 的按模型每周额度（Fable 这类 `model_scoped`）和 Claude Code 登录时记下的套餐（`login_plan`）状态栏里没有，被动记下的就没有（Claude Code 自己用 `/usage` 查过、它的缓存 `cachedUsageUtilization` 比记下的新时 `usage_cached` 照样取那一份）；登录失效 cca 查不出来（会话里 Claude Code、agy 自己会说）。还没在真实账号上核实的：agy 的 `quota` 在会话里多久更新一次
- Claude 的重置次数（`/limit-reset`，内部代号 `cedar_ember`，2.1.319 核实）：`/api/oauth/usage` 不带 `cedar_ember=1` 时这个字段恒为 null，状态栏里也没有；不要用账号的 OAuth token 自己调（条款不允许第三方收集、转用登录凭证，也违背 cca 不碰登录凭证的约定），官方能看的地方是 `claude.ai/settings/usage`（`cca limit-resets 账号`，App 账号菜单的「在 claude.ai 查看重置次数」，`can.limit_resets`，走 `cmd_web` 的全部检查）
- `cca usage` 的表格一个账号一行，整行不超过 `term_cols - 2`（`usage_table`）：放不下时依次收起有别名的账号的邮箱、套餐那一列、两个重置时间；备注至少留 `USAGE_NOTE_FLOOR` 格，按「；」分项取舍（`fit_note`），用缓存的行原因在前；表格下面的提示太长就换短的说法。回归里要看备注全文、长提示的断言带 `COLUMNS=`（默认 80 列）；`tests/usage_view.rs` 逐个宽度核对（运行辅助程序的 `usage-render`；备注的取舍、重置时间的写法在 `cli/src/cmd/usage.rs` 的单元测试里）
- Antigravity 的额度（`cca agy usage`，`cli/src/cmd/agy.rs`）：usage.json 的 `utilization` 是打印模式的 `/usage` 给过的样子（`{groups: [{name, buckets: [{id, name, window, disabled, remaining_fraction, remaining_amount, reset_time}]}]}`，`reset_time` 是 UTC 的 RFC 3339；现在由 `agy_quota_rl` 从状态栏的 `quota` 换成这样，桶名就是 id，只有 `reset_in_seconds` 时重置时间按现在算、取整到分钟）。3.7.5 及以前是经账号的端口跑 `agy -p /usage` 查的（1.1.11 起它不经模型、直接回额度），去掉了。显示时才算用了多少（`quota_groups` 的 `utilization` = 100 × (1 − `remaining_fraction`)）、过没过重置时间：表格一个额度一行：组名 · 窗口（`window` 是 `5h`、`weekly` 时写成 5 小时、本周，和 Claude 的叫法一样；真实的桶名是 Five Hour Limit Remaining 这种，写在「已用」旁边会被看反，只在认不出窗口时用桶名；组名和名字一样、包含时只写一个），账号和套餐只写在第一行（都没有套餐时不要那一列）；菜单、`cca agy ls` 那一格和 Claude、Codex 一样写 `5h 13% · 周 41%`（`agy_cell`：各组里同一个窗口用得最多的那个，这个窗口的都过了重置时间时写已重置；窗口都认不出时写用得最多的那个额度）。agy 的额度不是 Claude 那样固定的两个窗口（`--json` 里没有 `five_hour`、`seven_day`），每周用量（`usage-weeks.json`）不记（`_gui state` 的 `usage_weeks` 是 null）。`--json` 的每个额度另有 `slot`（`five_hour` / `seven_day`，认不出是 null：`WINDOWS` 的最后一项），App 照它摆；`stale` 按 30 分钟算（`AGY_STALE`，菜单那一格的「（N前）」也是）。App 里显示（3.6.11 起 `features.usage` 是 true，`_gui state` 里 agy 账号的 `usage` 是记下的 `quota_groups`）：账号页一组一块、照 Claude 的样子画 5 小时和本周，小条写各组里用得最多的那个，算不算额度用完看用得最少的那个（一组一般是一类模型，一组用完了别的组照样能用）；App 里不放 agy 给的英文（组名译成“… 模型”，说明不显示，认不出窗口的叫“其他额度”），见 PROTOCOL 3.1、macos/CLAUDE.md
- 登录失效（改过密码、在别处退出过）：本地的登录信息还在，`login` 还是 `logged_in`，查用量时才知道。Codex 的 app-server 明确说（`Rpc.failure` 认 `access token could not be refreshed`、`401 Unauthorized`，`error_code` 是 `auth`，App 里 `Diagnosis.loginExpired`）；Claude、agy 的用量不查，cca 不知道（会话里它们自己会要你重新登录；以前 Claude Code 2.1.319 的 `get_usage` 查不到时一律回 `rate_limits: null`，分不清是登录失效还是网络问题，是 `nolimits`，App 在用量那一行放个重新登录的入口，旧版 cca 还会给）。重新登录是 `cca [codex] login 账号`（`AppModel.relogin`），要终端（`need_tty`）

## 额度
- 没有 5 小时限制的账号（Claude 的 Ultra 这类套餐、ChatGPT 的 Pro 500）：接口不给 `five_hour`（Claude 的 `limits` 里也没有 `session` 那一项，状态栏的 `rate_limits` 里也没有），cca 原样给 null：表格里是 —，`usage --json`、`_gui state` 里是 null。App 在查到了用量、`five_hour` 是 null 而 `seven_day` 有时（`UsageEntry.noFiveHourLimit`）不画 5 小时那一行（侧栏、菜单栏面板、总览卡片的 `UsageStack`，账号页的大块）。只看接口给没给这个窗口，不按套餐名猜（同样叫 Ultra 的也有 5 小时限制）。`limits` 里的 `is_active` 不是“这项限制生不生效”：每个账号只有一项是 true，是眼下用得最多的那一项（一样多时是排在前面的；2026-11-11 五个账号前后两次核对过），5 小时用得比本周或 Fable 少时 `session` 那一项就是 false；5 小时的窗口还没开始计时是 0%、没有重置时间，普通账号也这样。3.1.0-beta.12、beta.13 拿 `is_active: false` 当没有 5 小时限制，把 Max 账号的 5 小时用量藏掉了
- Claude 的按模型每周额度（`model_scoped`，例如 Fable）在 `usage_entry` 里另带 `allowance_percent_of_weekly` / `used_percent_of_weekly`（`weekly_shares`：`weekly_scoped_shares` 的 `limit_index` 指 `limits` 里那一项的 `scope.model`；没有 `limits` 而两边都只有一项时就是它，别的认不出就不写）。以前查到的才有（get_usage 照它自己的名单从 `limits` 里挑），会话里记下的没有（状态栏里没有），旧的 usage.json 里查来的那份留到下一次记下为止。Claude Code 自己的用量缓存（`.claude.json` 的 `cachedUsageUtilization`，/api/oauth/usage 的原样）也没有 `model_scoped`，以前每次查用量时又比 usage.json 早写几秒：`usage_cached` 取到它时照另一份的 `model_scoped` 有哪几个模型从它的 `limits` 补上（`usage_scoped_fill`：取不到照搬，名单外的不加），不然这几秒里 App 重读 state，侧栏的 Fable 那一行会一闪没了
- 周结算提醒（`use_first`，在 `usage_entry` 里，PROTOCOL 3.1）：Antigravity 没有 `seven_day`，看各组的本周额度里用得最少的那个（`agy_week`：停用的、认不出窗口的不算，过了重置时间的算 0，一样多时先重置的那个；和 App 判断用完的 `quotaLeast` 是同一条规则，3.6.15 起；App 的 `fiveHourPressed` 同样经 `pressureWindows` 看各组 5 小时里用得最少的那个）。本周窗口 24 小时内重置、按四舍五入后的百分比还剩至少 20%（`USE_FIRST_HOURS` / `USE_FIRST_LEFT`）时给 `[from_epoch, until_epoch)`，这次查询说明账号现在用不了（`USE_FIRST_BAD`）时是 null。App 只拿当前时间比；挡不挡由 `Diagnosis.blocksUseFirst` 定（没登录、登错号、登录失效、端口、节点、出口、纯净度、泄露都挡，5 小时额度 ≥90% 不看新旧也挡），没挡住时 `.useFirst` 排在最前（账号页那句话、总览卡片、侧栏和菜单栏的沙漏，强调色；不算“要处理”）。只给图形界面，终端不提示
- 每周用量（`_gui state` 账号的 `usage_weeks`，PROTOCOL 2.2；App 账号页的「每周用量」、侧栏的「用量统计」，终端不给）：Claude、OpenAI 都不给以前的用量，cca 每次查到、记下用量时（`usage_write`：Codex 的 `cca usage`、重置额度前后，Claude 在会话里记下时；agy 不记）先 `weeks_record` 记进账号目录的 `usage-weeks.json`（600，最多 `WEEKS_KEEP` 周），再写 usage.json（App 看到 usage.json 变了就重读 state，这时两样都是新的）。一周按 `seven_day` 的重置时间认（差不到 `WEEK_SAME` 算同一周），用到多少取这一周查到的最高的；比最高的低了超过 `WEEK_DROP` 个百分点算中间重置过（`carried` 加上重置前的、`resets` 加一，所以可能超过 100）；下一周在这一周结束前就开始了（重新计时）的截到下一周开始；结束前 `WEEK_PARTIAL` 里没查到的标 `partial`（用完了的不标）。统计只算列出的过完的周（四舍五入后的整数）。`_gui state` 只读：Claude Code 的缓存比记下的新时只在内存里并进来（`usage_weeks_view` 的 `cached`）。数字、哪周填灰色、统计都由 cca 给，App 只排版（`WeeklyChart`：账号页和用量统计页共用；统计页所有行同一个时间范围、同一个纵轴高度）
- 重置额度（只有 Codex 账号：`cca codex reset 账号 [--json]`，PROTOCOL 4.5）：先经账号的出口查（`usage_one` + `py reset-plan`，顺便存用量），`consent reset_credit <账号目录名>`（默认不同意），再经出口跑 `py reset-consume`（app-server 的 `account/rateLimitResetCredit/consume`，`creditId` 是最早过期的那一次，`idempotencyKey` 每次新生成；重置了再读一次用量）。`nothing_to_reset` 不扣次数、退出码 0；已经请求了、结果不知道（超时、出错）时说可能已经用掉了一次（`RESET_UNSURE`）。最早过期的那次由 cca 算好（`reset_credits_view` 的 `next_expires_epoch`），App 不自己挑。App 里它和 app / web / router sync 一样跑完为止（同意之后就会用掉一次）
- 额度用完、恢复的通知（3.7.5 起；Mac 上的 cca App 自己在本机弹，配对的 iPhone 经推送收：docs/dev/push.md「额度的通知」）：一个账号的 5 小时或本周的额度用完了马上弹「额度用完了」「5 小时的额度用完了，16:00 恢复」，同时把「额度恢复了」定在重置的时间交给系统（`UNTimeIntervalNotificationTrigger`：那时 App 没在跑也弹）；点它打开那个账号。算不算用完是 `Diagnosis.quotaPressure` 里用完了的那些（登录着、不是第三方 API、不是登录失效，四舍五入到了 100%、没到重置时间，数据旧不旧不看；Antigravity 看各组里用得最少的那个），和 cca 推给手机的（`status.rs` 的 `exhausted`）是同一条规则。同一轮只弹一次：`UsageAlerts`（CcaKit）照账号（`Account.stableID`：改别名不变）和窗口记下这一轮的重置时间（差不到一小时算同一轮，过了重置时间一天忘掉），存在 App 的设置里（`usage.notes.memo`）。`UsageNotifier`（CcaApp）在账号、用量可能变了的时候（`AppHooks.accountsChanged`：读完 state、查完用量、重置额度以后、每分钟的定时器）照现在的用量看要不要弹，头一次要弹时才问通知的权限；演示模式、cca 还没准备好时不弹。设置（⌘,）的「通知」里可以关（「额度用完、恢复时通知」，`usage.notes`，默认开着；关掉时把定好的「额度恢复了」也撤掉）。字和手机上的一样（`Texts.usageNote` ↔ CcaRemoteKit 的 `UsageText.note`）。终端里的 `cca` 不弹；测试：`macos/test.sh` 的 `UsageAlertsTests`

## 套餐和在用
- 套餐档位（`_gui state` 账号的 `plan_tier`：`entry` | `standard` | `advanced` | `premium`，不知道是 `""`）由 cca 算，App 不从 `plan` 的文字猜，也不进 `usage_entry`。Claude 的 `claude_plan_tier` 先看结构化信息（`claude_plan_parts`：organizationType + 额度倍数 Nx，`plan_label` 共用它）：free→entry，pro / enterprise / edu→standard，team 5x 起→advanced，max 20x 起→premium、其余 max→advanced；倍数缺失时 planDisplayName 在 `CLAUDE_TIER_NAMES` 里就用它，种类也认不出时只看名字，不在表里（如 "Ultra Plus" 没有倍数）就是 `""`；两边冲突时结构化赢。Codex 的档位和叫法在同一张表里（`cli/src/cmd/codex.rs` 的 `CODEX_PLANS`：原始值 → 叫法、档位；原来是 `CODEX_PLANS`、`CODEX_TIERS` 两张表），按原始值查（和 `plan` 同一个来源）。Antigravity 的在 `AGY_TIERS`（`cli/src/core/tool.rs`）：登录 token 里的档位 ID（1.5.5 的 `user_tier`）和 cca 的状态栏命令记下的叫法（`plan_tier`，1.5 起只有它）都按这张表认（usage.rs 的 `agy_plan_of`），认不出的叫法照原话、档位是 `""`（见 docs/dev/accounts.md「agy 的套餐」）。没登录、登错号、API 账号是 `""`（和 `plan` 同一个闸门）。Anthropic / OpenAI / Google 加了新套餐，叫法和档位一起补
- Claude Code 登录时记下的套餐（凭证里的 `subscriptionType`，`get_usage` / `claude auth status` 回的 `subscription_type`）之后不更新（2.1.322 核实：来源是 `sign_in` 的不拿 profile 覆盖，刷新 token 时资料齐全也不再读 profile）：升降级以后它按旧套餐显示（横幅、`/status` 写 Claude Pro）和处理，要重新登录；`oauthAccount` 照常更新，所以 cca 的 `plan` 是对的。3.7.5 及以前 cca 查用量时把它记进 usage.json 顶层的 `login_plan`（不放进 `utilization`：用量可能取 Claude Code 自己那份更新的缓存），按 `accountUuid` 认；不查以后没有来源了（状态栏里没有，cca 不读凭证），会话里记下用量时去掉 `login_plan`（留着旧的就会一直说过时），下面的提示只在旧的 usage.json 还没被记下的盖掉时出现，代码留着；`claude_login_plan_outdated` 和 organizationType 的种类比（只比 pro / max / team / enterprise，倍数不比），对不上时 `outdated_login_plan`（`usage --json`、`_gui state` 的 usage，PROTOCOL 3.1）、`cca usage` 表格下面、启动横幅（`py set-last` 顺带输出，不多起进程）都提示 `cca login 账号`；`claude_login` 之前 `py login-plan-forget` 作废。读凭证本身不行（cca 不碰登录凭证）
- 命令行会话登记（`_gui state` 账号的 `cli`：`{running, sessions, since_epoch}`）：`run_account` 在 `trap ':' INT TERM HUP` 之后、启动工具之前 `session_open`（`py session-open`）在账号目录（`adir`）写 `cli-<cca 的进程号>.json`（600：`{v, tool, id, pid, started, since}`，`started` 是 cca 进程的启动时间戳，`ps -o lstart` 固定 `LC_ALL=C` 换算；Linux 上从 /proc 读（`proc_scan`：btime + stat 的 starttime，busybox 的 ps 不认 `-p`、`-x`、`lstart`，`proc_starts`、`presence_procs` 都经它）），工具一退出马上 `session_close`（bash 自己 `rm -f`，早于任何输出）再 `trap -`；顺手清掉这个账号对不上的旧登记。`_gui state` 只读：`cli_marks` 列登记（格式、tool、id 不对的不算），`proc_starts` 只在有登记时跑一次 `ps -p`，进程没了或启动时间对不上（进程号被重用）就不算，**不删文件**（CCA_RO）；只有 cca 被 kill -9 / 断电才会留下旧登记。登录、查用量的 `app-server` 起的 claude / codex 不登记（不是在工作）。登记没有凭证，不进 `CCA_DIR_PRIVATE`；restore 的备份照样带着（还原后核对不上就不算；别为它加 `--exclude 'cli-*.json'`：bsdtar 不锚定，会把名字以 cli- 开头的账号目录里的 .json 全排掉）。App 看到 `accounts/*/cli-<数字>.json` 出现、消失就重读 state（`CcaWatcher`）

## API 额度
- 查看 API 额度（`cca [codex] billing 账号`，App 账号菜单的「在控制台查看 API 额度」，`can.billing`）：Claude Max / Ultra / Team、ChatGPT Pro / Business 附带的每月 API 额度，余额只显示在控制台的账单页（2026-11 核实：普通 API Key 没有余额接口，Admin Key 只能查花费），所以这里只给入口，不显示数字。走 `cmd_web` 的全部检查，用账号自己的浏览器实例和出口打开 `T.billing_url`（bash 的 `BILLING_URL`，App 不写死网址）。入口在账号页“用量”一节底部（`InfoRow` + `RowAction.web`「在控制台查看」，和「重置次数和到期日」各一行）和右键菜单。打开后把账号邮箱放进剪贴板（`cmd_web` 的第 4 个参数 `mail`）：实测控制台登录页不认网址里的 `email` / `login_hint`，claude.ai、OpenAI 的登录页对无界面浏览器有人机验证、测不了；浏览器扩展（品牌版 Chrome 137 起不认 `--load-extension`）、远程调试、模拟按键都会削弱账号浏览器的隔离，不用。这笔额度不覆盖 Claude Code 和经 API Key 的 Codex，别假设把这类 Key 加成账号就能花它
