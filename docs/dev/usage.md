# 用量、套餐和额度

## 查用量
- `cca usage` 用的 `get_usage` 是 Claude Code 标为实验性的 SDK 控制请求：`claude -p --safe-mode --no-session-persistence --strict-mcp-config --input-format stream-json --output-format stream-json --verbose`，stdin 写一行请求，拿到 `control_response` 之前别关 stdin；字段要宽松解析，不支持时返回 `error: Unsupported control request subtype`。查询必须经账号自己的端口（和启动一样），登错号、出口在受限地区时不查。Claude 的重置次数（`/limit-reset`，内部代号 `cedar_ember`，2.1.319 核实）不在 `get_usage` 里：它读的是不带 `cedar_ember=1` 的 `/api/oauth/usage`，这个字段恒为 null，别的控制请求也拿不到；不要用账号的 OAuth token 自己调（条款不允许第三方收集、转用登录凭证，也违背 cca 不碰登录凭证的约定），官方能看的地方是 `claude.ai/settings/usage`（`cca limit-resets 账号`，App 账号菜单的「在 claude.ai 查看重置次数」，`can.limit_resets`，走 `cmd_web` 的全部检查）
- `cca usage` 的表格一个账号一行，整行不超过 `term_cols - 2`（`usage_table`）：放不下时依次收起有别名的账号的邮箱、套餐那一列、两个重置时间；备注至少留 `USAGE_NOTE_FLOOR` 格，按「；」分项取舍（`fit_note`），用缓存的行原因在前；表格下面的提示太长就换短的说法。回归里要看备注全文、长提示的断言带 `COLUMNS=`（默认 80 列）；`tests/usage_view.py` 逐个宽度核对（运行辅助程序的 `usage-render`；备注的取舍、重置时间的写法在 `cli/src/cmd/usage.rs` 的单元测试里）
- Antigravity（`cca agy usage`，`cli/src/cmd/agy.rs`）：agy 1.1.11 起打印模式里的 `/usage` 不经模型、直接回额度（不开会话、不花额度；之前的版本把它当成一句话交给模型）。cca 经账号的端口跑 `agy --gemini_dir=<账号的数据目录> -p /usage --output-format json`（`agy_usage_query`）：环境里设好 `AGY_FILE_ENV`（不能读钥匙串里那一份，那是别的账号的登录）和 `AGY_CLI_DISABLE_AUTO_UPDATE=true`（查一下额度不该顺带换掉装好的 agy；这个开关只认 `true`），工作目录是一个空的临时目录（用完删掉：agy 把工作目录当成项目，别让它去看账号目录里的浏览器资料；离线核对过它不往工作目录里写东西），stdin 是空的，在新的会话里（setsid）起：打印模式要授权码时会去读控制终端，没有控制终端才读不到用户的键盘。回的 JSON 只有一行（1.5.16：`status`、`error`、`command: {name, data}`……），`command.data` 是额度（`{description, groups: [{name, description, buckets: [{id, name, description, window, disabled, remaining_fraction, remaining_amount, reset_time}]}]}`，agy 省掉空的字段，`reset_time` 是 UTC 的 RFC 3339），原样存进 usage.json 的 `utilization`。没登录、刷新不了 token 时 agy 在 stderr 打出 Google 的登录网址、等满 60 秒（没有终端也等）才回 `authentication failed or timed out`：cca 看到授权网址（`AGY_LOGIN_SAID`：`https://accounts.google.com/o/oauth2/` 开头，stdout 上的也算；额度说明里带个 Google 账号的链接不算）就停掉它的整个进程组，说登录已失效（`auth`）；没有 `command` 是不认 `/usage` 的旧版本（`unsupported`）；`status` 是 ERROR 时 `error` 是 agy 的原话；一组额度也没有算没查到。登录前先过 `agy_guard`（token 要在账号自己的目录里）。显示时才算用了多少（`quota_groups` 的 `utilization` = 100 × (1 − `remaining_fraction`)）、过没过重置时间：表格一个额度一行：组名 · 窗口（`window` 是 `5h`、`weekly` 时写成 5 小时、本周，和 Claude 的叫法一样；真实的桶名是 Five Hour Limit Remaining 这种，写在「已用」旁边会被看反，只在认不出窗口时用桶名；组名和名字一样、包含时只写一个），账号和套餐只写在第一行（都没有套餐时不要那一列）；菜单、`cca agy ls` 那一格和 Claude、Codex 一样写 `5h 13% · 周 41%`（`agy_cell`：各组里同一个窗口用得最多的那个，这个窗口的都过了重置时间时写已重置；窗口都认不出时写用得最多的那个额度）。agy 的额度不是 Claude 那样固定的两个窗口（`--json` 里没有 `five_hour`、`seven_day`），每周用量（`usage-weeks.json`）不记（`_gui state` 的 `usage_weeks` 是 null）。`--json` 的每个额度另有 `slot`（`five_hour` / `seven_day`，认不出是 null：`WINDOWS` 的最后一项），App 照它摆；`stale` 按 30 分钟算（`AGY_STALE`，菜单那一格的「（N前）」也是：App 查得慢）。App 里显示（3.6.11 起 `features.usage` 是 true，`_gui state` 里 agy 账号的 `usage` 是缓存里的 `quota_groups`）：账号页一组一块、照 Claude 的样子画 5 小时和本周，小条写各组里用得最多的那个，算不算额度用完看用得最少的那个（一组一般是一类模型，一组用完了别的组照样能用）；App 里不放 agy 给的英文（组名译成“… 模型”，说明不显示，认不出窗口的叫“其他额度”），见 PROTOCOL 3.1、macos/CLAUDE.md
- 登录失效（改过密码、在别处退出过）：本地的登录信息还在，`login` 还是 `logged_in`，查用量时才知道。Codex 的 app-server 明确说（`Rpc.failure` 认 `access token could not be refreshed`、`401 Unauthorized`，`error_code` 是 `auth`，App 里 `Diagnosis.loginExpired`）；Claude Code 2.1.319 的 `get_usage` 查不到时一律回 `rate_limits: null`，分不清是登录失效还是网络问题（`nolimits`），只在用量那一行放个重新登录的入口，不说失效。重新登录是 `cca [codex] login 账号`（`AppModel.relogin`），要终端（`need_tty`）

## 额度
- 没有 5 小时限制的账号（Claude 的 Ultra 这类套餐、ChatGPT 的 Pro 500）：接口不给 `five_hour`（Claude 的 `limits` 里也没有 `session` 那一项），cca 原样给 null：表格里是 —，`usage --json`、`_gui state` 里是 null。App 在查到了用量、`five_hour` 是 null 而 `seven_day` 有时（`UsageEntry.noFiveHourLimit`）不画 5 小时那一行（侧栏、菜单栏面板、总览卡片的 `UsageStack`，账号页的大块）。只看接口给没给这个窗口，不按套餐名猜（同样叫 Ultra 的也有 5 小时限制）。`limits` 里的 `is_active` 不是“这项限制生不生效”：每个账号只有一项是 true，是眼下用得最多的那一项（一样多时是排在前面的；2026-11-11 五个账号前后两次核对过），5 小时用得比本周或 Fable 少时 `session` 那一项就是 false；5 小时的窗口还没开始计时是 0%、没有重置时间，普通账号也这样。3.1.0-beta.12、beta.13 拿 `is_active: false` 当没有 5 小时限制，把 Max 账号的 5 小时用量藏掉了
- Claude 的按模型每周额度（`model_scoped`，例如 Fable）在 `usage_entry` 里另带 `allowance_percent_of_weekly` / `used_percent_of_weekly`（`weekly_shares`：`weekly_scoped_shares` 的 `limit_index` 指 `limits` 里那一项的 `scope.model`；没有 `limits` 而两边都只有一项时就是它，别的认不出就不写）。Claude Code 自己的用量缓存（`.claude.json` 的 `cachedUsageUtilization`，/api/oauth/usage 的原样）没有 `model_scoped`（get_usage 才照它自己的名单从 `limits` 里挑），每次查用量时又比 usage.json 早写几秒：`usage_cached` 取到它时照另一份的 `model_scoped` 有哪几个模型从它的 `limits` 补上（`usage_scoped_fill`：取不到照搬，名单外的不加），不然这几秒里 App 重读 state，侧栏的 Fable 那一行会一闪没了
- 周结算提醒（`use_first`，在 `usage_entry` 里，PROTOCOL 3.1）：本周窗口 24 小时内重置、按四舍五入后的百分比还剩至少 20%（`USE_FIRST_HOURS` / `USE_FIRST_LEFT`）时给 `[from_epoch, until_epoch)`，这次查询说明账号现在用不了（`USE_FIRST_BAD`）时是 null。App 只拿当前时间比；挡不挡由 `Diagnosis.blocksUseFirst` 定（没登录、登错号、登录失效、端口、节点、出口、纯净度、泄露都挡，5 小时额度 ≥90% 不看新旧也挡），没挡住时 `.useFirst` 排在最前（账号页那句话、总览卡片、侧栏和菜单栏的沙漏，强调色；不算“要处理”）。只给图形界面，终端不提示
- 每周用量（`_gui state` 账号的 `usage_weeks`，PROTOCOL 2.2；App 账号页的「每周用量」、侧栏的「用量统计」，终端不给）：Claude、OpenAI 都不给以前的用量，cca 每次查到用量时（`usage_save`：`cca usage`、重置额度前后）先 `weeks_record` 记进账号目录的 `usage-weeks.json`（600，最多 `WEEKS_KEEP` 周），再写 usage.json（App 看到 usage.json 变了就重读 state，这时两样都是新的）。一周按 `seven_day` 的重置时间认（差不到 `WEEK_SAME` 算同一周），用到多少取这一周查到的最高的；比最高的低了超过 `WEEK_DROP` 个百分点算中间重置过（`carried` 加上重置前的、`resets` 加一，所以可能超过 100）；下一周在这一周结束前就开始了（重新计时）的截到下一周开始；结束前 `WEEK_PARTIAL` 里没查到的标 `partial`（用完了的不标）。统计只算列出的过完的周（四舍五入后的整数）。`_gui state` 只读：Claude Code 的缓存比记下的新时只在内存里并进来（`usage_weeks_view` 的 `cached`）。数字、哪周填灰色、统计都由 cca 给，App 只排版（`WeeklyChart`：账号页和用量统计页共用；统计页所有行同一个时间范围、同一个纵轴高度）
- 重置额度（只有 Codex 账号：`cca codex reset 账号 [--json]`，PROTOCOL 4.5）：先经账号的出口查（`usage_one` + `py reset-plan`，顺便存用量），`consent reset_credit <账号目录名>`（默认不同意），再经出口跑 `py reset-consume`（app-server 的 `account/rateLimitResetCredit/consume`，`creditId` 是最早过期的那一次，`idempotencyKey` 每次新生成；重置了再读一次用量）。`nothing_to_reset` 不扣次数、退出码 0；已经请求了、结果不知道（超时、出错）时说可能已经用掉了一次（`RESET_UNSURE`）。最早过期的那次由 cca 算好（`reset_credits_view` 的 `next_expires_epoch`），App 不自己挑。App 里它和 app / web / router sync 一样跑完为止（同意之后就会用掉一次）

## 套餐和在用
- 套餐档位（`_gui state` 账号的 `plan_tier`：`entry` | `standard` | `advanced` | `premium`，不知道是 `""`）由 cca 算，App 不从 `plan` 的文字猜，也不进 `usage_entry`。Claude 的 `claude_plan_tier` 先看结构化信息（`claude_plan_parts`：organizationType + 额度倍数 Nx，`plan_label` 共用它）：free→entry，pro / enterprise / edu→standard，team 5x 起→advanced，max 20x 起→premium、其余 max→advanced；倍数缺失时 planDisplayName 在 `CLAUDE_TIER_NAMES` 里就用它，种类也认不出时只看名字，不在表里（如 "Ultra Plus" 没有倍数）就是 `""`；两边冲突时结构化赢。Codex 的档位和叫法在同一张表里（`cli/src/cmd/codex.rs` 的 `CODEX_PLANS`：原始值 → 叫法、档位；原来是 `CODEX_PLANS`、`CODEX_TIERS` 两张表），按原始值查（和 `plan` 同一个来源）。没登录、登错号、API 账号是 `""`（和 `plan` 同一个闸门）。Anthropic / OpenAI 加了新套餐，叫法和档位一起补
- Claude Code 登录时记下的套餐（凭证里的 `subscriptionType`，`get_usage` / `claude auth status` 回的 `subscription_type`）之后不更新（2.1.322 核实：来源是 `sign_in` 的不拿 profile 覆盖，刷新 token 时资料齐全也不再读 profile）：升降级以后它按旧套餐显示（横幅、`/status` 写 Claude Pro）和处理，要重新登录；`oauthAccount` 照常更新，所以 cca 的 `plan` 是对的。cca 查用量时把它记进 usage.json 顶层的 `login_plan`（不放进 `utilization`：用量可能取 Claude Code 自己那份更新的缓存），按 `accountUuid` 认；`claude_login_plan_outdated` 和 organizationType 的种类比（只比 pro / max / team / enterprise，倍数不比），对不上时 `outdated_login_plan`（`usage --json`、`_gui state` 的 usage，PROTOCOL 3.1）、`cca usage` 表格下面、启动横幅（`py set-last` 顺带输出，不多起进程）都提示 `cca login 账号`；`claude_login` 之前 `py login-plan-forget` 作废。读凭证本身不行（cca 不碰登录凭证）
- 命令行会话登记（`_gui state` 账号的 `cli`：`{running, sessions, since_epoch}`）：`run_account` 在 `trap ':' INT TERM HUP` 之后、启动工具之前 `session_open`（`py session-open`）在账号目录（`adir`）写 `cli-<cca 的进程号>.json`（600：`{v, tool, id, pid, started, since}`，`started` 是 cca 进程的启动时间戳，`ps -o lstart` 固定 `LC_ALL=C` 换算；Linux 上从 /proc 读（`proc_scan`：btime + stat 的 starttime，busybox 的 ps 不认 `-p`、`-x`、`lstart`，`proc_starts`、`presence_procs` 都经它）），工具一退出马上 `session_close`（bash 自己 `rm -f`，早于任何输出）再 `trap -`；顺手清掉这个账号对不上的旧登记。`_gui state` 只读：`cli_marks` 列登记（格式、tool、id 不对的不算），`proc_starts` 只在有登记时跑一次 `ps -p`，进程没了或启动时间对不上（进程号被重用）就不算，**不删文件**（CCA_RO）；只有 cca 被 kill -9 / 断电才会留下旧登记。`cca usage`、登录、`app-server` 起的 claude / codex 不登记（不是在工作）。登记没有凭证，不进 `CCA_DIR_PRIVATE`；restore 的备份照样带着（还原后核对不上就不算；别为它加 `--exclude 'cli-*.json'`：bsdtar 不锚定，会把名字以 cli- 开头的账号目录里的 .json 全排掉）。App 看到 `accounts/*/cli-<数字>.json` 出现、消失就重读 state（`CcaWatcher`）

## API 额度
- 查看 API 额度（`cca [codex] billing 账号`，App 账号菜单的「在控制台查看 API 额度」，`can.billing`）：Claude Max / Ultra / Team、ChatGPT Pro / Business 附带的每月 API 额度，余额只显示在控制台的账单页（2026-11 核实：普通 API Key 没有余额接口，Admin Key 只能查花费），所以这里只给入口，不显示数字。走 `cmd_web` 的全部检查，用账号自己的浏览器实例和出口打开 `T.billing_url`（bash 的 `BILLING_URL`，App 不写死网址）。入口在账号页“用量”一节底部（`InfoRow` + `RowAction.web`「在控制台查看」，和「重置次数和到期日」各一行）和右键菜单。打开后把账号邮箱放进剪贴板（`cmd_web` 的第 4 个参数 `mail`）：实测控制台登录页不认网址里的 `email` / `login_hint`，claude.ai、OpenAI 的登录页对无界面浏览器有人机验证、测不了；浏览器扩展（品牌版 Chrome 137 起不认 `--load-extension`）、远程调试、模拟按键都会削弱账号浏览器的隔离，不用。这笔额度不覆盖 Claude Code 和经 API Key 的 Codex，别假设把这类 Key 加成账号就能花它
