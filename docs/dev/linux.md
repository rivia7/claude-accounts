# Linux 和服务器

整套 Linux 测试（tests/linux.sh）见 tests/CLAUDE.md。

- Linux 上安装：`install.sh` 认 macOS 和 Linux。下载前查的和 `cca install` 的 `need_deps` 是同一份（两边一起改）：命令（ssh、ssh-keygen、nc、curl、perl、gunzip、base64、find；find 管自动更新、Team 的配置多久没同步过和清残留的锁，Amazon Linux、openSUSE 的最小安装没有它；gunzip、base64 是第一次运行时解出辅助程序用的；不再要 python3）、机器的种类（辅助程序只有 x86_64、arm64 的：静态链接 musl，不挑发行版和 glibc 的版本；第一次运行解到 `~/.cache/cca-helper`，见 docs/dev/rust.md）、OpenSSH 8.1 或更新（`ssh -V`；验签的 `ssh-keygen -Y` 8.1 才有，RHEL / Rocky 8 是 8.0；认不出版本时不拦）。缺命令时 `pkg_hint` 认出包管理器（apt、dnf / yum、zypper、pacman、apk；不在 PATH 里、在 /sbin、/usr/sbin 里的也认：Alpine 的 apk 在 /sbin，普通用户的 PATH 里常没有），给出装这些命令的那一行（包名不同的在表里：openssh-client(s)、netcat-openbsd / nmap-ncat / openbsd-netcat、findutils，不是 root 时带 sudo），两份 `pkg_hint` 也一样。别用 `cmp`、`diff`（Arch、openSUSE、Fedora、Rocky 的最小安装没有 diffutils：`! cmp` 恒为真），比文件用 `sha256_of`。`cca restore` 开始前先查有没有 `tar`（没有就什么都不动），打包后看包能不能完整读出来（`tar -tzf`；不看退出码：GNU tar 遇到打包时被改的文件也返回 1），读不出来就不删 `~/.cca`；打包前先停设备统计的上报进程。`path_hint` 在 Linux 上 bash 写 `~/.bashrc`（Ubuntu、Debian 的 `~/.profile`，Fedora、RHEL、Arch 的 `~/.bash_profile` 都读它；新建 `~/.bash_profile` 会让 Ubuntu、Debian 的登录 shell 不再读 `~/.profile`），sh、ash 写 `~/.profile`，生效要重新登录或 `. ~/.bashrc`（macOS 照旧：bash 写 `~/.bash_profile`，别的写 `~/.zshrc`）。要账号专属的 Chrome、桌面 App、界面 App 的命令（`cmd_web`（billing、limit-resets 也经它）、`cmd_app`、`cmd_gui`、`cmd_mail`）开头 `mac_only`：Linux 上说只在 macOS 上、退出，不说"没装 Chrome""要 macOS 26"。`app_pid`（桌面 App、账号的 Chrome 开着没有；`cca rm`、`restore` 先查它）在 Linux 上直接算没开着、不跑 `pgrep`：没装 procps 的机器上没有它，退出码 127 会被当成“查不了进程”挡住删除和还原。`usage` 在 Linux 上不列它们（还有 `login-page`、`cca codex app`、`cca mail`、`dock_tidy` 和 `mail` 两项设置），出门在外那一节换成内置代理的说法；macOS 上的输出和以前逐字一样。有的容器里没有 `hostname` 命令：密钥备注里的机器名用 `short_host`（`hostname -s`，没有就 `uname -n`）。不要 git（3.6.0 以前维护者的映射要它）
- 服务器上登录（`login_remote`：Linux 上，或者 `CCA_REMOTE_LOGIN=1`，只给测试）：服务器上没有账号专属的 Chrome。claude / codex 照常在服务器上跑登录、在本机开回调，要打开的网址经 `cca _browser` 只写进 `CCA_LOGIN_URL_FILE`（`main` 里除了 `_browser` 都清掉这个变量）；`remote_login` 在后台跑登录命令（stdin 是 /dev/null：真 Claude Code 2.1.318（Linux）、2.1.322 都照样等回调），最多等 30 秒拿网址，给出在 Mac 上运行的 `cca [codex] login-page 邮箱 [--alias 别名] --node 节点 [--node-id 摘要] '网址'`（官方账号一定有节点；摘要是 `py node-fp` 按 `node_ids`、内置代理拷来的节点定义、Team 的配置带的节点认的 `node_fp`，认不出就不带）。Mac 上的 `cmd_login_page`：`py login-check` 只收这个工具的登录网址（`login_target`：`login_hosts`、`/oauth/authorize`、PKCE、回到 localhost 的 redirect_uri、state；另一个工具的提示换成 `cca codex login-page`），`py login-page-acct` 按摘要认两边是不是同一个节点（叫法可以不同；没给摘要、这边认不出地址时按名字），不是就停（登录页和换 token 要经同一个出口）；Mac 上还没有这个账号时（邮箱只认全称）问过后用同一个节点（这边的叫法，Team 的配置给这个邮箱固定的节点优先，不在可选节点里就停）加上它（`account_added`，和 `cmd_add` 共用；别名能用才带上），`preflight app` 之后在账号的 Chrome 里打开；`py login-catch` 在 127.0.0.1 和 ::1 上占住 redirect_uri 的端口（最多等 15 分钟，`CCA_LOGIN_WAIT`），只认对的路径和 state，把 `code#state` 放进剪贴板、打到 stdout（端口被占：退出码 4，让用户把地址栏的整个网址贴回去）。贴回服务器后 `py login-forward` 认 `code#state` 或整个回调网址，state 对不上就重问（退出码 2），对上了直连 GET 本机的回调（不经代理、不跟随跳转），换 token 由 claude / codex 照常经账号的端口。实测：Claude Code 收到 state 不对的回调回 400、整个登录失败（所以 cca 先核对），对的马上 302；Codex 0.167 state 不对回 400、继续等，换好 token 才回应。取消、出错时 `remote_login` 的 EXIT trap 用 SIGTERM 停登录命令（非交互 shell 的后台任务忽略 SIGINT；Codex 的 login-flow 把 SIGTERM 当成 Ctrl-C，取消登录、关掉 app-server），所以传给它的要直接是一条命令（`env …`），不能是函数。服务器上的 `cca _browser` 不打开别的浏览器（说一声、退出 1）；`ensure_login` 不说服务器的 WebRTC 结果（登录页在 Mac 上，`login-page` 的 `preflight app` 自己测）。服务器上从来没配置过路由器（config.json 里没有路由器的地址）、只配置了本机的代理（`LOCAL_SET`）而且有可选节点（Team 的配置带的节点、拷来的节点、自定义节点）时，`cmd_add` 不先要求配置路由器（配置过、只是现在用不了的，比如密钥没了，照样先重新配置）；还没有可选节点、直连又不通时走 `builtin_onboard`（见下一条）
- 服务器上不用路由器（bash 的「服务器上不用路由器」一节，`cmd_install` 和 `cmd_add` 里）：`server_builtin`（`login_remote`、config.json 里没有路由器的地址、本机客户端没配置或者是 builtin）先 `direct_probe`：直连（`--proxy '' --noproxy '*'`，两次）`TRACE_HOST` 的 `/cdn-cgi/trace`，拿不到出口或者 `py restricted` 认出受限地区就算不通。不通时不问路由器，`builtin_onboard`：要 `core_possible`；还没有可选节点时先问「有没有 Team 的邀请链接？」（`install.team`，默认没有，标题「节点从哪来」；已经有可选节点时不问，直接 `core_setup`）。有：`builtin_team`——`( TEAM_JOIN_OPTIONAL=1 team_join )`（邀请链接可以留空：先不加入），加入时 `team_settle` 导入 Team 的配置带的节点；有了可选节点就往下走，在 Team 里却还没有节点（配置还没同步下来、管理员没给节点）时说同步下来以后再运行哪条命令（`cca team sync` 马上同步）、停下，没加入的接着走 `builtin_own`。没有：`builtin_own` 粘贴一条自己的代理（`node_add`，内核校验过存成自定义节点），接着 `core_setup`（没就绪只 warn，节点已经有了）。3.6.0 以前还有一支「维护者提供节点」（`builtin_shared`：一键安装带了 `CCA_POLICY_REPO` 时拉映射），跟着映射去掉了（team.md「3.6.0 去掉的旧通道」）。`cmd_install` 随后问一句再 `tool_install proxy`（不先直连、Team 的配置指定的节点不再 consent），有账号就不问新增；跳过了（`onboard=skip`）不装、不问新增。能直连的照旧问路由器。端口池是空的时 `core_setup` 只改客户端、不起内核（BSD 的 `seq 7901 7900` 会倒着数）

## 测试
- `tests/linux.sh` 用的辅助程序是 musl 静态链接的那一份（`cli/target/<x86_64|aarch64>-unknown-linux-musl/release/cca-core`）：`--docker` 时在宿主机上先编（Mac 上是交叉编译，仓库只读挂进容器）；直接在 Linux 上跑时没有就自己编（要 Rust 和这个目标）；那台机器没装 Rust 的，在 Mac 上交叉编译好（`cd cli && . ./musl-env.sh && cargo build --release --locked --target x86_64-unknown-linux-musl`），拷到那台机器上源码目录里同样的路径，或者 `CCA_HELPER=路径` 指一份。Team 的同步服务器的安装脚本那个模块（`hub_deploy`）给安装脚本带的服务端程序就是这一份（`CCA_HELPER`）：真的 Linux 程序经安装脚本解出来（openssl、gzip）、试运行、由假的 systemctl / docker 起成服务，只有在这里测得到——Mac 上的回归拿 Mac 的辅助程序冒充。测试自己用的两个程序也是这样来的：小工具 `cca-test`（假的 claude / codex / netstat 要做的事、读写 JSON、扮演 Team 的管理员）和测试程序 `suite`（远程会话、Team 服务器的安装脚本那几个模块），tests/ 的 Rust 包 `cca-tests`，同一个目标、同样静态链接：`cd cli && . ./musl-env.sh && cargo build --profile kit -p cca-tests --locked --target x86_64-unknown-linux-musl --bins --tests`（`cca-test` 编在 `cli/target/<目标>/kit/` 下；`suite` 的文件名带一串摘要，放在哪一层随 cargo 的版本变，加 `--message-format=json` 时 `"executable"` 那一项写着）。有 cargo 的机器上脚本自己编；没装 Rust 的，把 `cli/target/<目标>/kit/` 整个拷到源码目录里同样的路径（脚本找最新的那个 suite），或者 `CCA_TEST_BIN=路径`、`CCA_SUITE_BIN=路径` 各指一份；`--docker` 时三个程序都在宿主机上编好。假的发布版用 `cca-core pack --only`（就是这一份辅助程序自己）接上它，下面所有的 cca 都像发布的那样自己解到 `~/.cache/cca-helper`；测了解出来、清旧的、第二次不再解，和 PATH 里没有 python3 时照样能用（测试自己也不用 python3，那台机器上没有它也能跑：假的 claude / codex 是两行 sh，要做的交给 `cca-test` 的角色，见 tests/CLAUDE.md）
- 服务器上登录（regress.sh 3b2，Codex 的在「不支持经 app-server 登录」后面）：`run CCA_REMOTE_LOGIN=1 …` 在 macOS 上走服务器的流程。`$T/oauth_flow` 里写着这次的 state 时，假 claude 的 `auth login` 交给 `cca-test fake-oauth`（进程名是 `$T/fake_oauth`）、假 app-server 的登录也照真的走：本机随机端口开回调、经 BROWSER（Codex 是 `cca _browser`）交出网址；state 不对时 claude 回 400 并失败、codex 回 400 接着等；对的记 `OAUTH-EXCHANGE code=… https_proxy=…`，code 以 good 开头才算换到 token。用完 `rm -f "$T/oauth_flow"`。`gone 模式` 等 `pgrep -f` 认不出这个进程（取消后登录命令停了）。Mac 端的 `login-page`：`"$TESTBIN" browser state code` 后台扮演账号的 Chrome（从 open.log 里认出这个 state 的网址、读出 redirect_uri，先试 favicon 和 state 不对的，再带验证码回调），跑 `cca login-page` 时带 `CCA_LOGIN_WAIT=20`（失败也不会干等 15 分钟）。节点摘要用 `fpof '类型|服务器|端口|TLS 域名'` 算（`FPA` 等）；Mac 上还没有的账号用 dora 测（加上后 `cca rm` 掉，账号表要和之前逐字节一样）。服务器上不测 WebRTC 在 3d（`CCA_REMOTE_LOGIN=1` 时 stun.log 不该多出 STUN 行）
- 服务器上安装（回归）：`rs` 在全新的 HOME（`$SH`）里带 `CCA_REMOTE_LOGIN=1` 运行测试版的 cca，第一个答案是「有没有 Team 的邀请链接」：答 n、粘贴 `socks5://` 的代理，再运行时有了可选节点不再问；答 y、到了邀请链接那一步留空是先不加入，接着粘贴代理（答 y、真的加入 Team 的那一支回归里还没有用例）；假 curl 直连 `*/cdn-cgi/trace` 时 `$T/direct_down` 连不上、`$T/direct_loc` 是出口地区（默认 US；直连的 trace 不能落到真的 curl 上）。内核是假的 mihomo（`$CD`），界面 App 是 `$SH/Applications/cca.app` 里只有 Info.plist 的假 App；用完 `core_stop`
