# 邮箱助手（`cca mail`）

- 邮箱助手（`cca mail`，bash 和辅助程序的「邮箱助手」一节；只在 macOS 上、只给 Claude：`Tool.mail_rules` 指向 `MAIL_RULES`，Codex、agy 是空的）：登录时（`claude_login` 不在服务器上的那一支、`cmd_login_page`）`mail_watch_start` 在后台起 `py mail-watch`（带上这次的 `CCA_PROXY`；它打开链接时起的 `cca _mail-open` 不带 `BG_ENV_DROP`），登录命令一结束 `mail_watch_stop` 用 TERM 停它（cca 被 kill 时它看父进程不在了自己走）；没配置、config.json 的 `mail.auto: false` 时它马上退出，出什么错都只说一句、退出码总是 0，绝不影响登录。经 IMAP 只读（imaplib + ssl，照常校验证书，`IMAP4_SSL` 不传 context 时不校验所以不用它；`MailBox` 只有 LOGIN、LIST、EXAMINE、UID SEARCH、UID FETCH 的 BODY.PEEK、LOGOUT，没有通用的命令入口）。连 Gmail 的路照系统代理（`scutil --proxy`：SOCKS 优先，再是 HTTPS、HTTP 代理的 CONNECT；例外里有 Gmail、没开代理、只有 PAC 时直连），不读环境变量（cca 起的进程里 https_proxy 是账号的出口），走不通就报错、不换路；指到账号出口（端口池里的端口、这次的 `CCA_PROXY`）的拒绝。核对（`mail_judge`）只信最上面那条 `mx.google.com` 写的 Authentication-Results 里 Anthropic 域名的 `dkim=pass`（`mail_ar_items` 照 RFC 8601 切：注释、引号里的不算（smtp.mailfrom 的本地部分是发件人写的、Gmail 照抄），写法不对整条不信；名字重复、header.b 不到 8 个字符的那一项不算），按 header.b 对上唯一的 DKIM-Signature，From、To、Subject 各只有一个且都在它的 h= 里，收件人是账号的邮箱，Gmail 收到的时间（INTERNALDATE）不早于登录开始前 `MAIL_SKEW`；链接按 `MailRule.link_ok`（https、主机原样相等、路径在名单里、只有可见 ASCII）。盯邮箱（`MailSource`）：第一轮按日期和规则搜索、再加上最新的 `MAIL_BURST` 封，之后按 UIDNEXT 往后按 UID 取头在本地筛（不靠 Gmail 的搜索：刚到的邮件可能还没进索引）；一轮都成了才记下看过了（中途断了不漏）。来了好几封只开最新的一封，浏览器没打开的过两秒再试、一共三次。链接是一次性的登录凭证：只经 stdin 交给 `cca _mail-open`（`py mail-link-check` 再核对、`open_chrome`），不打印、不记日志、不存盘、不进命令行和环境变量（打开它的 `open` 和 Chrome 那一下除外，和 cca 打开的所有网址一样）；`~/.cca/mail/used.json`（700 目录、600）只记摘要，先认领再打开（两个 cca 同时盯着同一个账号只开一次），只有打开了才记下（没通过核对、没链接的下次照样核对、照实说）。终端上打出的邮件头（`cca mail test`）、Gmail 的回话先 `mail_clean`（转义序列能擦掉、改写前面的输出）。Gmail 回 NO 时只有认得出的密码不对、没开 IMAP 算致命，别的（临时出错、同时连得太多）照连不上重试。应用专用密码存在钥匙串（没有钥匙串的是密钥文件）的 `cca-mail`，账户名是 Gmail 地址（`MAIL_ADDR_RE` 收紧了：它进 `security -i` 的命令行），和 API key 一样经 `ks_read` / `ks_write` / `ks_del`（`kc_*` 也是它们）；换地址时新的存好、设置改好了才删旧的，不进 `api_keys` / `ref_keys`（`secrets-forget` 碰不到它）；`cca mail forget`、`cca restore`（确认清单里说了）删掉。规则（标题、链接的路径）按真实的登录邮件定：Anthropic 改了邮件的格式就改 `MAIL_RULES`，`cca mail test` 逐封说认不认、链接只说样子。测试：辅助程序的单元测试（`cargo test`，`cli/src/cmd/mail.rs` 和 `cli/src/cmd/mail/` 下各文件：规则、路、解析、核对、打开过的记录、盯邮箱的假时钟；期望值取自原来 Python 的在 `cli/tests/vectors/mail.json`，移植时生成的固定数据，有意改了行为就直接改它）；`tests/mail_view.rs`（suite 的 mail_view 模块：`cd cli && cargo test --profile kit -p cca-tests --test suite -- mail_view`）把辅助程序当黑盒（临时 HOME，钥匙串是假的 security，`cca _mail-open` 是记下链接的小脚本），经 `kit::mailfake`（`tests/kit/mailfake.rs`，跑在测试进程自己的线程里）的假 Gmail（真的 TLS、只读 IMAP，会改邮箱的命令回 BAD 并记 VIOLATION，假代理同时认 SOCKS5 和 HTTP CONNECT）走 setup / test / open / 登录时盯邮箱 / forget——改了辅助程序要先 `cd cli && cargo build --release` 再跑；regress 3b3（假 scutil 读 `$T/scutil.txt`；`CCA_MAIL_CAFILE` 只在 HOME 换过（`home_swapped`，测试的沙箱）、连的是本机时才信，`CCA_MAIL_POLL` / `CCA_MAIL_RETRY` 调快；假 Gmail 是 `cca-test mail serve`，同一份 `kit::mailfake`，ctl.json 见 `tests/kit/mailfake.rs` 开头；假 claude 的 `auth login` 在 `$T/mail_send` 在时先跑它放一封登录邮件，等 open.log 里出现 `$T/mail_login` 的链接才算登录好）
- 信任转发中转（`cca mail trust-forwarder <账号> [<中转域名> | off]`，PROTOCOL 4.11，3.3.0-beta.3 起）：登录邮件经转发、别名服务进 Gmail、带的是中转自己的 DKIM 时用。不安全、默认不开、按账号登记，只存在本机 config.json 的 `mail.accounts[acct_id].forwarder`（不同步到别的设备）；Team 给的 Claude 账号（3.7.9 起）不看它：照 Team 的配置的 `mail_forwarders`（可以有几个），这台设备上登记不了（team.md「转发中转」）；有 Team 的配置文件读不出来时（说不准这个账号是不是它给的），Claude 账号这台设备登记的也先不算、一个都不信（`cca mail status` 说是哪个 Team）；Team 不再给这台设备这个账号以后，以前登记的照旧算数；App 里是「信任转发中转（不安全）」开关（提问会话 `mail.forwarder` + `consent.mail_trust_forwarder`）；Team 给的账号没有这个开关：「邮箱」一节照 `mail.team_forwarders` 说是哪个 Team 定的、信任哪些，以前登记的另起一行、可以清掉。From 是 Anthropic 的照严格的路核对；From 是这个账号信任的中转之一（`mail_forwarders(c, key)`：Team 给的照 Team 的名单，别的照本机登记的；按标签认后缀，`mail_fwd_ok`）时走 `mail_judge_fwd`：中转的 DKIM 签名覆盖 From、To、Subject、Reply-To，From 的显示名是这个账号的邮箱（也靠它认是哪个账号的信），Reply-To 是唯一一个 Anthropic 的地址。安全边界只到「信任这个中转 + 别名不泄露」：别名泄露了，知道的人能经中转塞进登录链接。`MAIL_HDRS` 要带 `REPLY-TO`（不带时真的转发信都被拒）；`_gui mail-list` 里经它通过的那封 `via` 是 `"forwarder"`，App 标明不安全。夹具用 `relay.example.com` / `phisher.example.com`，测试时见到的真实中转、钓鱼域名不进仓库。用例在 regress 3b3（`mail trust-forwarder` 那几条、Team 给的账号那几条）
