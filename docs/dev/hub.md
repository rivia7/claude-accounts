# 自己的同步服务器（hub）

维护者共享以外的官方账号，设备统计、记下备查的 API key、折合金额经用户自己部署的服务器和自己的其他设备同步。界面上叫「自己的同步服务器」，命令是 `cca hub`，代码里叫 hub（`cli/src/cmd/hub.rs`）。别叫“中转”“relay”：那是远程会话的（remote.md）。服务器就是设备统计的那个程序，用 `server/cca-presence.py --mode own` 运行，请求和加入链接的格式见 server/README.md「自己的同步服务器」。三条管线本身（上报、API key、折合金额）怎么做见 presence.md、cost.md，这一份只写经哪台服务器、怎么加入。

- 账号走哪台（`route`）：第三方 API 账号、没有邮箱的哪台都不去；维护者映射里的官方账号走维护者的（它的数据是共享这个账号的各台设备的，不上自己的服务器）；别的官方账号走自己的（Antigravity 的官方账号也报设备统计，和维护者的一样；记下的 API key、折合金额只有 Claude、Codex 的）。`hub_of` 再看这台设备用不用得了那台：`hubs()` 里维护者的要共享开着、映射里有 presence 一节、有 deploy key（`presence_load`），自己的要加入了、密钥还在（`own_load`）；config.json 写着 `"presence": false` 时两台都不用。上报进程每台服务器一条线（`Lane`；自己的那一路的配置带着 `rev`，是 hub.json 的修改时间：重新加入以后算新的一路，从头报、不接着被移除那会儿的 10 分钟退避，它盯着 `~/.cca/hub/`，加入、退出马上醒来），`cca devices` 各台各问一次（终端里一台没问成照样显示别的那台，那一台说没问到；`--json` 有一台没成就是退出码 1），记下的 API key、折合金额各台各同步一轮（`cost sync --json` 的 `sync.hubs`，顶层是最要紧的那一台）。两台的状态文件分开：`HubKind::file`，自己的前面加 `own.`（`presence/own.keys.json`、`own.keys-sync.lock`、`own.status.json`，`cost/own.sync.json`、`own.remote.json`），维护者的文件名不变，不用迁移；盐、这台设备的指纹也各是各的，两台服务器上的账号摘要对不上。`presence/status.json`（上报进程没报成的原因）只在原因变了时写
- 加入（`cca hub join [--stdin] [--name 名字]` → `py hub-join`）：加入链接经 `ask_secret` 问（App 里是提问会话的 `hub.join`），或者 `--stdin` 读，经管道交给辅助程序，不进命令行和环境变量。`link_decode` 核对前缀、校验、地址（`url_ok`）、指纹（`PRESENCE_PIN_RE`）、入伙口令（32 个小写十六进制字符）和盐（`PRESENCE_SALT_RE`，和映射里设备统计的盐一样认 32～128 个；生成的是 32 个）。第一次加入时生成这台设备在它上面的 ed25519 密钥（`~/.cca/hub/id_ed25519`；目录 700、文件 600），用它签 `join`（`pub`、`name`、`admit`、`check`）；名字默认是主机名，重新加入时沿用上次的。服务器回 200 以后才写 `hub.json`（`url`、`pins`、`admit`、`salt`、`name`、`joined_at`，600）、`members.json`、config.json 的 `device_id`，再在后台上报、同步一次（`agent_kick`、`keyshare_kick(true)`、`cost_kick_now`：`_cost-sync now`，不看上次同步过多久）；第一次加入没成什么都不留（刚生成的密钥也删掉，`join_post` 之后 `own_forget`）。stdout 一行一项：名字、地址、几台设备、关掉了同步时的原因（`"presence": false` 时照样加入，bash 说现在不经它同步）。已经加入了同一台（地址和盐的校验值一样）是重新加入（改名字、服务器丢了这台的记录时补上）；加入了别的要先 `cca hub leave`。以前加入过、没删干净的（密钥、经它同步来的）在加入新的一台之前删掉
- 失败的原因码：辅助程序的 stdout 是 `原因码\t原因`，bash 里成了 `FAIL_CODE=hub_原因码`（PROTOCOL 4.1）。加入时：`link`（链接不对）、`other`（加入了别的）、`name`、`sign`（生成不了密钥、签不了名）、`denied`（入伙口令不对：服务器对口令不对和签名不对一样回 403）、`salt`（409 `salt_mismatch`：链接里的盐和第一台设备登记的不一样）、`full`（507，最多 64 台）；别的请求和加入共用 `fault`：`pin`、`unreachable`、`old`（404：不是 `--mode own` 的服务器，或者太旧）、`clock`、`busy`（429）、`server`。bash 自己的：`hub_not_joined`、`hub_no_device`、`hub_unavailable`
- 设备标识：同一台设备在两台服务器上的指纹不一样，折合金额要认出是同一台：config.json 的 `device_id`（16 个十六进制字符，`router.rs` 的 `device_id`：几台设备共用一个路由器时早就有它），没有的话第一次加入成功时生成（`ensure_device_id`），以后不变。这台设备传的折合金额的明文里带 `dv`；`CostView` 按 `dv`（没有时按指纹）把各台归到一起，这台设备的 id 是 `device_id`（没有时是 `local`）；撤销了的设备照旧并进同名的新设备，只加新设备有数据以前的那些小时
- 别的命令：`cca hub [status [--json]]` 只读本机记着的、不联网（`hub_view`：三条管线最近一次的结果，`presence/` 的 status.json、keys.json，`cost/` 的 sync.json；`own_entry` 在加入了却用不了时把 state 换成 `off`（关掉了设备统计）或者 `error`，原因在 `error`）。`cca hub devices [--json]` 问服务器（op `members`），这台在前，`members.json` 记下几台（变了才写：App 盯着它）。`devices`、`remove`、`leave` 用 `own_cfg`（不看 `"presence": false`：管设备不是同步）。`cca hub remove 设备`（名字，或者指纹的开头）先问（`consent hub_remove 指纹`，默认不同意），移除以后它现在的密钥作废，是这台自己就是退出。加入链接不变：那台设备上还留着链接的话，拿着它照样能重新加入，所以设备丢了、被人拿走了要换一个加入链接重新部署服务器（别的设备都要重新加入；换链接要等 M6）。`cca hub leave` 先问（`consent hub_leave all`），先请服务器移除这台（连不上、服务器已经不认它了也接着退，说怎么在别的设备上移除），再删 `~/.cca/hub/` 和 `presence/`、`cost/` 里 `own.` 开头的；记下的 API key 留在这台设备上。`cca hub invite` 把加入链接打到 stdout（App 的「复制加入链接」经管道读），在 Claude Code 的会话里（`CLAUDECODE` 而且没有 `CCA_EVENTS`）不给：会进对话记录
- 凭证：`hub/hub.json`（入伙口令、盐）和 `hub/id_ed25519` 在 `CCA_DIR_PRIVATE` 里（cca 启动的 Claude Code 读写不了），`cca restore` 的备份不带它们，也不带 `cost/own.remote.json`（别的设备同步来的）。restore 退出服务器（确认清单里说了；`py hub-leave apply`，连不上时说怎么在别的设备上移除这台）
- 界面 App（PROTOCOL 2.1 hello 的 `hub`；2.2 `config.hubs`、账号的 `hub`、`cost.sync.hub`；3.4 `devices --json` 的 `hubs`、账号的 `hub`；3.5 `sync.hubs`；4.13 `cca hub`；4.2 同意项 `hub_remove`、`hub_leave`；4.6 题号 `hub.join`）：`_gui state` 的 `config.hubs` 是 `hub_entries`（维护者的在前；只有自己的有 `members`、`joined_epoch`、`can_invite`），`can.devices` 就是账号的 `hub` 不是 null。Swift 模型在 `Protocol/Hub.swift`；旧版 cca 没有这些字段时，有「设备」一节的账号当作走维护者的（`Account.hub`、`CostSync.hub` 解码时补上；有这个字段时不认识的值当作 null）。App 盯着 `hub/hub.json`、`hub/members.json`、`presence/status.json`、`presence/own.status.json`、`cost/own.remote.json`、`cost/own.sync.json`（`CcaWatcher`）。卡片、引导页是 M5 的事
- `cca policy off` 停掉上报进程（它告诉维护者的服务器这些会话停了）以后 `py presence-wake`（不带账号）再起一个：自己的同步服务器那一路接着报（中间会有一下子算离线）
- 服务器上最后一台设备退出以后，盐的校验值 `check` 和密文都留着：拿同一个加入链接还能回来；链接丢了要换口令重新部署（换了口令服务器从头开始）
- 还没做的（分阶段，每阶段停下来给维护者看、提交）：M4 一键部署（服务器上的脚本：Docker compose 或者 systemd + python3，脚本自己生成加入链接，盐只在服务器的内存里过一遍、不落盘；从 Mac 部署和托管平台时在本机生成）；M5 App 的卡片和新手引导（先问一句有没有自己的服务器，默认“没有”）；M6 托管平台（Sealos、Railway）、`--behind-proxy`、CA 签的证书、换加入链接、自动重新加入（服务器丢了记录时；要在换加入链接之后做，不然被移除的设备也会自己加回来）
