# 远程会话

目标：一台机器上经 cca 启动的会话（Claude Code / Codex / Antigravity 的界面），能在另一台机器上的界面 App 里实时看和操作。分四个阶段做，这一份跟着写：

| 阶段 | 内容 | 状态 |
|---|---|---|
| M1 | 会话宿主：开关、客户端跑在 pty 里、启动它的终端没了会话照样运行、在同一台机器上接回去 | 做完了 |
| M2 | 中转：两台机器配对、端到端加密、经维护者的服务器转发，跨机器的列表和接入（命令行） | 做完了；服务器要部署成带中转的才用得了（`./policy.sh presence deploy` 默认连中转一起开，要放行数据端口） |
| M3 | 界面 App：内嵌终端（SwiftTerm）、「远程会话」一页、在 App 里配对 | 做完了（演示数据和假的会话上验证过；真的 Claude Code 界面、真的两台机器还没试） |
| M4 | 打磨、发布 | 3.5.2-beta.2 起发成测试版；设备统计认宿主里的会话；Linux 上实跑过（x86_64，宿主机模式）。之后加的：连接断了自己重新接上、`cca remote end`（结束一个会话）。真的界面和真的两台机器还没试 |
| M5 | 网页端：手机不装 cca，在浏览器里（iPhone 上添加到主屏幕）接入会话 | 做完了，还没发布。本机测过：真的服务器、真的 cca 会话，页面在无界面的 Chrome 里（iPhone 的屏幕大小、触摸）走了一遍。**真的 iPhone、真的证书都还没试**；维护者的服务器要带着网页端重新部署（要一张浏览器信得过的证书）才用得了 |
| M6 | 每个 Team 的会话走这个 Team 自己的服务器中转；网页端的证书用 Let's Encrypt 给 IP 地址签的短期证书 | 中转这一半做完了（辅助程序、命令行、App、Team 服务器的安装脚本），3.5.3-beta.2 发布了。证书助手写好了、对着照规范核对的假证书机构测过，2026-11-22 在维护者的服务器上对着真的 Let's Encrypt（先测试环境、再正式的）
签到了一张 IP 地址的短期证书（`./policy.sh presence deploy --web-acme`）；Team 的安装脚本带上了网页端和证书助手（`<服务名>-acme`，team-only 分支，还没发布、只在假的服务器上跑过） |

定下来的（M2 以后照它做，别重新讨论）：经服务器中转、不走 SSH；只有打开了开关的会话能接入，只接入已经开着的会话、不能远程新建；两台机器要先配对（一次性配对码），默认单向：显示配对码的那台是被接入的；端到端加密只用辅助程序已有的库（HMAC-SHA256），服务器只转发密文；数据另走一个只传密文的端口（默认 18444），凭现有的签名 HTTPS 换一次性的票据接入；App 里的终端用 SwiftTerm（`v1.20.0`，源码放进仓库，单独编成一个模块）。

## 会话宿主（M1）

- 开关：config.json 的 `remote`（`cca remote on` 写成 `true`，`off` 删掉这一项；`py remote-set`）。`py env` 多给一行 `CFG_REMOTE`（开着是 `1`，否则空的），不为它多起一次辅助程序。环境变量 `CCA_REMOTE=1` 只这一次用、`CCA_REMOTE=0` 只这一次不用（比 config.json 优先）。不做成命令行参数：账号后面的参数原样交给客户端，Claude Code 自己有 `--remote`。`cca remote` 在 `main` 的最外层分派（和 `cost`、`clients` 一样不经过自动更新、映射拉取；和工具无关，没有 `cca codex remote`），所以 `cca remote` 不会被当成给 claude 的参数
- `run_account` 里只多一步 `remote_prepare`：开关开着、标准输入输出都是终端、不是界面 App 起的（`CCA_GUI`）、找得到辅助程序，才把 `HOSTCMD` 设成 `辅助程序 remote-host 工具 账号的键 账号的名字 --`，加在客户端前面：`env 屏蔽的 设的 HOSTCMD… 客户端 参数… 3<&-`。别的一个字不变：cca 仍然是父进程、等它退出、拿退出码，后面的 `session_close`、`py link`、`py sync`、核对邮箱照旧。条件不满足时 `HOSTCMD` 是空的，走的就是原来那一行（开关没开时启动的命令逐字节和以前一样）
- 宿主（`cli/src/cmd/remote/host.rs`，`remote-host`）：开一对 pty（`pty.rs`：`posix_openpt` 那一套，musl 没有 `forkpty`），从的那头照用户终端现在的 termios 和大小设好，在上面起客户端（自己一个会话、pty 是它的控制终端、标准输入输出错误都是它；环境、参数、当前目录原样，信号的处理方式都是默认的）。宿主**不给客户端加、减任何环境变量**（它要的工具、账号都从参数拿），自己也什么都不往终端上说。用户的终端另开一份（`reopen_tty`：标准输入那一份是和 shell 共用的，在它上面设不阻塞会连 shell 的也改掉）切到原始模式，按键原样写进 pty，pty 的输出原样写回终端。客户端退出后把它最后的输出读完（pty 关了，或者 0.2 秒没有新的——它起的后台进程可能还开着 pty——最多等 2 秒），还原终端，退出码就是客户端的（被信号杀掉是 128 + 信号）
- 宿主起不来（不在终端里、开不了 pty、建不了会话目录、终端另开不了）时照原样直接 `exec` 客户端：开关开着也不能让会话启动不了。客户端找不到时退出码 127（和 `env` 一样）
- 启动它的终端没了（关了窗口、SSH 断了：收到 SIGHUP，或者读写终端出错）：宿主不退出，会话照样运行。bash 那边 `trap ':' INT TERM HUP` 本来就让 cca 接着等，所以收尾照常（这时往终端写的提示写不出去，无妨）。发给宿主的 SIGTERM / SIGINT / SIGQUIT 转给 pty 上的前台进程组
- 接回去：`cca remote attach [-r] [编号前几位]`（`attach.rs`，`remote-attach`；bash 直接 `exec` 辅助程序，中间不留 bash）是一个普通的终端程序，经会话目录里的 socket 接上宿主。只有一个会话时不用写编号；`-r` 只看不操作。断开（会话接着运行）：先按 Ctrl-\，再按 d 或者 .；连按两次 Ctrl-\ 给会话本身发一个；这个终端被关掉、进程收到 SIGTERM / SIGHUP 也是断开（界面 App 的「断开」以后就用它）。退出码：会话结束了是客户端的退出码，自己断开是 0，64 用法不对或者前缀对上了好几个，65 没有这个会话，66 经服务器接入别的机器上的会话没成（M2），68 宿主没了（没说会话结束连接就断了，或者这边太慢被它断开），69 不在终端里
- 会话目录 `~/.cca/remote/`（700，要是自己的、不是链接）：每个会话一个 `<编号前 12 位>.sock`（600）和一份 `.json`（600：`{v, sid, pid, tool, key, name, cwd, since}`，没有密钥，有动静时碰一下修改时间、最多 5 秒一次，以后设备统计算闲置用）。连上来的再核对一遍是不是同一个用户（`SO_PEERCRED` / `getpeereid`）。`~/.cca` 很深、socket 的地址（macOS 最长 104 个字节）放不下整个路径时，先进到目录里用相对路径（`in_dir`：只在还没起客户端、没有别的线程时；先试一下回不回得来，当前目录读得了却进不去时就不去——客户端要在原来的目录里启动）。宿主正常退出时两个文件都删掉；被强行结束留下的由下一次 `cca remote list` / `attach` 清掉（`CCA_RO=1` 时不清）。这里没有凭证，没进 `CCA_DIR_PRIVATE`（挡 Read / Edit 也挡不住连 socket：同一个用户的进程本来就能往彼此的终端里写）；配对的密钥在钥匙串 / `secrets/` 里（`secrets/**` 本来就在 `CCA_DIR_PRIVATE` 里、不进 `cca restore` 的备份），这个目录里的配对表 `peers.json` 没有密钥
- socket 上的帧：`类型(1) 长度(4，大端) 内容`，最长 1 MB（`local.rs`）。接入方 → 宿主：`HELLO`（版本、标志、列数、行数；标志 1 是只看，2 是不算进窗口大小——别的机器上只让看的接入方带着，转接那头加的；宿主只认头一个 HELLO，之后再说一遍改不了“只看”）、`INPUT`、`RESIZE`、`DETACH`、`STATUS_REQ`、`END`（结束这个会话：只有这台机器上的 socket 上说得了，转接那头不替别的机器转）；宿主 → 接入方：`WELCOME`、`OUTPUT`、`EXIT`（退出码）、`STATUS`（JSON：说明里的那些加上现在的大小、有几处接入、启动它的终端还在不在）。不认识的帧不理。中转把同样这几种放进加密的记录里
- 几个终端接着同一个会话：都能看、都能操作（`-r` 的按键不送过去；最多 8 个）。pty 的大小取**各个接入方都画得下的**（列、行各取最小；启动它的终端没了就不算它），有人接入、断开、改了窗口大小就重算。只按最小的算：不模拟屏幕，窗口大的那边客户端只用到左上角那一块
- 谁收到什么（`vt.rs` 的 `Scanner`、`Class`、`Route`）：**主的那个接入方**（最近有输入的；一开始是启动它的终端；只有只看的接着时没有）收到的和直接运行时逐字节一样。**别的接入方和回放只收认得出来、完整、确定不是查询的序列**：
  - 查询（问终端的能力、光标位置、颜色、kitty 的标志、图片协议……，`Class::Query`）只给主的：不然每个终端都答一遍，回答当成按键进了客户端
  - 写剪贴板（OSC 52，`Class::Clip`）只给主的：复制到正在操作的那个人的剪贴板
  - 残缺的、被打断的（ESC 重新开始、CAN / SUB）、太长的（CSI 超过 256 个字节、OSC 超过 4096 个字节而又不是 OSC 52）、认不出的（没有数的 OSC、UTF-8 写法的 C1 控制字符）是 `Class::Junk`，也只给主的。客户端的输出里可能有别人能左右的内容（文件、网页、模型说的话）：不这样的话，去掉中间一条查询以后，前后两截残缺的字节会在别的终端上拼成一条原来没有的序列（`ESC ESC [ c ] 52;… BEL` 去掉 `ESC [ c` 就成了写剪贴板）
  - 状态机照 VT500 的：ESC 在哪都重新开始；序列中间的控制字符终端照常执行、序列接着（认的时候当它们不在）；字符串（OSC、DCS、APC……）遇到 ESC 就结束，`ESC \` 自己是一条。一条字符串自己没带结束符（`Seg::open`）、结束它的那条序列又不发给某个接入方时，`Route` 给它补一个 `ESC \`，不然它后面的字都被当成这条字符串的内容
  - 太长的字符串（图片）不等它完：先交开头、后面一截截交（`Part::Head` / `More`）。开头没收到的（半路接进来的、半路才成了主的），后面那几截也不收
  - 认不出的新查询会漏给所有终端：客户端加了新的查询序列时补进 `csi_class` / `osc_class` / `str_class`。OSC 里单独一个 `?` 的字段一律当查询（Claude Code 启动时发的 `OSC 7501;?` 就不在任何表里），只有内容是给人看的那几种（标题 0 / 1 / 2、通知 9 / 777）除外
- 后接入的看到什么：先是终端现在的模式（`Modes::restore`：光标键、自动换行、光标显隐、备用屏幕、鼠标上报、焦点、括号粘贴……只记 `DEC_TRACKED` 里的，一条乱写的序列占不满这张表，会清屏、换成 VT52 的那几个也不重放；还有 modifyOtherKeys、小键盘模式、光标的样子），再是回放（`Ring`：最近 256 KB，只在内存里；只有普通字节（响铃去掉）、完整的 CSI / ESC 序列和超链接，通知、标题、图片、窗口操作这些不重放；按整段进、整块丢，不会从半条序列或者半个字开始），再是 kitty 键盘协议的标志（`restore_keys`：它是一层层压进去的，回放里又有当时压、弹的那几条，所以放在回放后面，先全弹掉再照现在的压），最后让客户端重画一遍（大小变了它自己会重画；没变就把 pty 的行数减一、80 毫秒后改回来）。回放里的历史是照当时的窗口大小画的，接入的终端大小不一样时可能错位，重画以后界面是对的
- 断开时接入端把会话在这个终端上打开的模式关掉（`Modes::undo`：最后才离开备用屏幕），终端回到原样
- 断开的按键（`keys.rs`）：会话里的程序会让终端换一种办法报按键，Ctrl-\ 不再是一个字节。认：0x1c，kitty 键盘协议的 `CSI 92 ; 5 u`（开了“报松开”时松开的那条不打断；大写锁定、数字锁定加在修饰上的 64、128 不算），modifyOtherKeys 的 `CSI 27 ; 5 ; 92 ~`；后面的 d 也认 `CSI 100 u`。按过前缀以后来了半条序列就等它到齐。括号粘贴的两个标记之间原样送过去，里面碰巧有这两个键不算
- 慢的不拖住别人：一个接入方还没写出去的超过 2 MB 就断开它（它再接入时重新回放）；启动它的终端太慢时，有别的接入方就照读客户端的输出，它待写的攒到 2 MB 丢掉、等它写得动了从头回放（`LOCAL_DROP`，要比一次回放大得多），只有它一个时和直接运行一样让客户端等着（`LOCAL_HIGH`）。客户端退出以后把 pty 里剩下的都读出来、写给终端（只要还写得动就写完），再告诉别的接入方
- 结束一个会话：`cca remote end [编号前几位]`（`manage.rs` 的 `remote-end`；只有一个会话时不用写编号，退出码 64 / 65 照 `attach` 的）。
  等于关掉它的终端：辅助程序在 socket 上说一个 `END`，宿主给 pty 上的前台进程组和客户端自己发 SIGHUP（再发一个 SIGCONT：停着的收不到），
  `END_GRACE`（5 秒）以后还没退出就 SIGKILL，之后和客户端自己退出一样收场（接着的各处收到 `EXIT`，退出码是 128 + 信号）。命令等宿主
  收场才返回：那条连接被关上以后再看一眼 socket 确实没人听了（宿主不收的连接——接着的已经满了——也是一连上就被关，不能当成
  结束了）；宿主没有回应（被挂起了）时等十秒说没结束成。没保存的会丢，所以 bash 那一层先问：
  `consent remote_end 会话的完整编号`（默认不同意；先 `remote-end --show` 找出是哪一个，问的时候说的是列表里那一行），界面 App 走同意事件
  （PROTOCOL 4.2、9.2，要 `hello.remote_end`）。只管这台机器上的：`END` 这一种帧转接进程不转（`link.rs` 的 `bridge` 只放行那四种），
  别的机器上的会话要到那台机器上结束，或者接进去让里面的程序自己退出
- 宿主被强行结束、崩了：pty 关掉，客户端收到 SIGHUP，会话也就没了（要让会话比宿主活得久得另有一个常驻进程，没做）。万一 panic，main 的钩子先把终端从原始模式还原（`pty::restore_on_panic`；辅助程序是 `panic = "abort"`，`Drop` 不跑）
- 列表、接入时怎么算一个会话还在（`local::sessions_in`）：socket 连得上、回了状态就是在；连上了却没回（宿主被挂起了、机器正忙）照说明文件列出来、标成没有回应，**它的文件不动**；只有确实没人在听（连接被拒、文件没了）才算不在了、清掉它留下的文件。`cca restore` 在还有会话时先停下（删掉 `~/.cca` 以后它们照样在跑，却再也接不上）
- `cca codex remote …`、`cxa remote …` 不是这个命令：照旧当成给 codex 的参数（只有第一个参数是 `remote` 才是）
- 终端的内容可能有密钥和源码：只在内存里转，不写文件、不进日志、不进任何进程的命令行和环境变量

### 和直接运行不一样的地方

- Ctrl-Z：客户端在自己的会话里，pty 上的进程组没有管作业的 shell，SIGTSTP 会被内核丢掉（给自己发的也一样）。实测 vim 9.1：按了 Ctrl-Z 它离开备用屏幕、发 SIGTSTP、没停下来，马上又进备用屏幕重画一遍，等于没按。客户端用 SIGSTOP 把自己停下时宿主跟着做（还原终端、连同 cca 一起停下，`fg` 回来再让它接着跑；启动的终端不在了就马上让它接着跑）。真的 claude / codex 按 Ctrl-Z 是哪一种还没核对（要登录了的会话）
- 实测过的真客户端（2026-11-20，Claude Code 2.1.328，临时 HOME、没登录、不联网，只到它报连不上就退出的那一屏）：直接运行和在宿主里运行输出的字节数一样；它启动时发的查询是 `CSI c`、`CSI ? u`、`CSI > 0 q`、`OSC 11 ; ?`、`OSC 7501 ; ?`，都认成了查询。交互界面（后接入、重画、多个终端）是用 vim 验证的：后接入的终端先收到模式、再是回放，vim 跟着窗口大小重画，断开时终端回到原样
- 关了终端会话能不能活下来看终端和系统：宿主不理 SIGHUP，但有的终端关窗口时会再发 SIGKILL，Linux 上 logind 的 `KillUserProcesses=yes` 会在退出登录时杀掉整个会话的进程。都还没实测（M4）
- 设备统计（`presence.rs` 的 `presence_scan`）算命令行会话闲置了多久，原来只看 cca 那个进程所在终端的读写时间。会话在宿主里时
  启动它的终端可能已经没了（那样会一直算在用），别的机器上的输入也不经过那个终端：宿主收到输入、客户端有输出时碰一下会话说明的
  修改时间（最多 5 秒一次），设备统计认出登记的 cca 进程有个子进程是宿主（`local::activity`：宿主的进程号 → 说明的修改时间），
  取终端和它里面晚的那个

## 中转和配对（M2）

两台机器之间不直连：都连维护者的那台服务器（设备统计的那一台，`server/cca-presence.py`），它把两头的连接对接起来。线上的格式、
服务器的接口和限额写在 `server/README.md`「远程会话的中转」（那一节是规范，`tests/spec_wire.py` 照它独立实现了一遍）；这里写 cca 这一头怎么做、为什么。

- 要防的是服务器自己和路上的人：它们看不到终端的内容、敲不进按键、冒充不了配对过的机器。靠两台机器配对时各存的一把密钥 P，
  服务器见不到它。只用 HMAC-SHA256（辅助程序已有的 `sha2`；Linux 那一份没有 TLS，也不加新的依赖）：通道的加密、认证、握手都是它，
  没有前向保密（P 泄露以后，之前录下的流量解得开；取消配对再配一次就换一把）。配对码 80 位，派生密钥时过 PBKDF2 65536 轮
- 用得了中转的前提：这台机器的共享开着（policy.md：默认关着，关着时 `presence_server` 是空的，和没配置映射一样）、映射里有服务器（`presence` 一节）、有 deploy key、维护者把它同步进了设备清单
  （`relay::server` 取 `presence_server`：和设备统计同一份配置，但不看 config.json 的 `"presence": false`——那是关上报，配对是用户自己要的）。
  请求（配对、列表、票据）走设备统计已有的那条路：deploy key 签名、curl 钉住证书公钥、直连（`presence_post`）。服务器没开中转、是旧版时
  那几个接口回 404，说“维护者的服务器还不支持远程会话”（`RELAY_OLD`）
- 数据不走 HTTPS、不经 curl：普通的 TCP 连数据端口（票据里给的端口，默认 18444），连上先说一行可见的 ASCII 开场白（凭一次性的票据，
  服务器也回一行证明它认得票据），之后全是两头之间的密文。直连，不经账号的出口（辅助程序自己连，不看代理的环境变量）
- 配对（`pair.rs`、`crypto.rs`）：一台 `cca remote pair`（先 `consent remote_pair`：输入配对码的那台之后能看和操作这台机器的会话），显示
  `XXXX-XXXX-XXXX-XXXX`，等另一台 `cca remote join` 输入（bash 用 `ask` 读，经 stdin 交给辅助程序，不进命令行）。两边各往服务器放一份
  用配对码封起来的密文（指纹、随机数、机器名），取到对方的就算出同一把 P，各报一次它的编号，服务器看两边报的一样才记下这一对。
  两边都核对“密文里写的指纹”和“服务器验过签名的指纹”是同一个。配对码、P 都不发给服务器
- 配对表 `~/.cca/remote/peers.json`（600，没有密钥）：`{v: 1, peers: {pid: {fp, name, incoming, shown, at}}}`。`name` 是维护者设备清单里那台设备的名字
  （`cca devices` 里看到的也是它；清单里没有才用对方自己说的机器名），只是给人看的，认设备靠指纹。P 存钥匙串（服务名 `cca-remote-<pid>`、
  账户名 `pair`，64 个十六进制字符；没有钥匙串的系统是 `~/.cca/secrets/` 下的文件），经 `ks_write`：不进命令行和环境变量。
  `cca restore` 先 `py remote-forget`（全部取消、告诉服务器、密钥删掉）
- 方向（`incoming`）：对方能对**这台机器**的会话做什么。显示配对码的那台是 `control`（看和操作），输入的那台是 `none`（对方接不进来）；
  `cca remote allow 名字 control|view|none` 改。同两台机器反过来再配一次换成新的 P，以前让的照旧（于是两边都能接入对方）。
  这条规矩由**宿主那头**把关，不靠接入方自觉：只让看的，转接时在 HELLO 上加“只看”和“不算进窗口大小”，按键、改窗口大小的一个都不转
  （它的窗口多小也不该让会话跟着变；比会话小的话它那边画不全）；不让接入的不把会话告诉它（服务器也就不给它票据）。
  显示配对码的那台不再确认“是谁输入的”：配好以后说对方的名字，不对就马上 `unpair`（配对码 10 分钟、只能用一次，只有维护者设备清单里的
  机器输入才算；App 里也是这样，配好以后提示里说对方的名字）。`cca remote peers --check` 问一下服务器，对方已经取消了的标出来；`cca remote unpair 名字` 取消
- 宿主那头的转接（`link.rs`，`remote-link <会话编号>`）：会话宿主自己**不碰网络**。有配对表时它让一个转接进程跑着（`host.rs` 的 `link_tick`：
  自己一个会话，关终端、^Z 都轮不到它；退出了过 5 秒到 1 分钟再起；它说“这台机器用不了中转”（退出码 3）就不再起）。转接进程卡住、崩了，
  会话和这台机器上的接入都不受影响。它的标准输入是宿主留着不写的一根管道：宿主不在了读到头，告诉服务器会话结束了（BYE）就退出
  - 一条控制连接：把会话的说明（工具、账号的短名字、文件夹、开始的时间、对方能做什么；没有邮箱）封给每个允许接入的配对，隔 20 秒说一声，
    断了按退避重连。每 3 秒看一眼配对表变了没有：变了就换一条控制连接（新票据上是新的那几个配对），不该再接着的转接结束掉
  - 服务器说有接入方来了（带一个令牌）：`fork` 一个子进程（不 exec：密钥已经在内存里，不用再传），拿令牌另连一条上去和接入方对接、握手
    （核对它有 P），然后像这台机器上的接入方一样连宿主的 socket，两头对转。一个接入方一个进程：握手是阻塞着做的，慢的、捣乱的拖不住别人。
    两个方向的帧都一个个看过再转：接入方发来的只转头一个 HELLO、INPUT、RESIZE、DETACH（只让看的不转 INPUT、RESIZE；`END` 谁的都不转）；
    宿主发来的只转 OUTPUT、EXIT——它的欢迎帧、状态里有账号的邮箱、完整的路径、进程号，不给（问状态的也不替它问）
  - 转接进程自己被强行结束时，子进程看到父进程换了就走（不然没人管着它们，配对表变了也照转）；宿主过一会儿再起一个。
    服务器一个劲地说“有人来了”也不跟着转：同时最多 4 个子进程，10 秒里最多分出 8 个
  - 辅助程序是单线程的，所以 `fork` 以后接着用自己这一份内存是安全的；子进程最后 `_exit`，不跑父进程的收尾
- 接入端（`attach.rs`）：这台机器上有对得上的会话就接它（不联网，和 M1 一样）；没有才问服务器配对过的机器上有哪些（`far.rs`），
  换票据、连数据端口、握手，之后和本机接入是同一个循环，只是路不一样（`Wire`：socket 或者加密的通道）。对面证明不了它有 P 就什么都不发。
  那边只让看时先说一句、按键不送。退出码多一个 66：经服务器接入没成（连不上、那台机器不在线、对不上密钥）
- `cca remote list` 先列这台机器上的，再列配对过的机器上的（要问服务器；没配对过就不问，没问到的原因写到 stderr，不影响前一半）；
  `--local` / `--far` 只要一半。`cca restore` 查有没有开着的会话用 `--local`（不联网）
- 对方写的、服务器转交的文字（机器名、文件夹、账号名）显示之前去掉控制字符、限制长度（`far::clean`）
- 服务器的数据端口是一条线程管所有连接：哪一条连接上出了没料到的错只断开它自己（`Relay.oops`），控制连接上只发不收的、
  帧不对的断开；一大块小帧不逐帧挪缓冲区（`Decoder` 也是：那样是平方级的，一个接入方能拖住转接它的进程）
- 两头每 20 秒说一声（空的记录），60 秒没听到对面就算断了
- 连接断了（网络断了、这台机器睡了一觉、服务器重启、那边的转接进程没了）接入端自己重新接上（`attach.rs` 的 `reconnect`；只有别的机器上的
  会话，这台机器上的宿主没了就是没了）。做法：
  - 断的那一条先两个方向都关掉（`Tunnel::close`：服务器和那头马上知道，不然那边还替一条死连接占着一处接入）。终端上先写一个 CAN
    （断的时候可能正写到一条序列的半中间）、把会话打开的模式关掉（`modes.undo()`：鼠标上报还开着的话，等的这一阵动一下鼠标就是一串乱码），
    再说一句“连接断了，正在重新接上…”。会话那边还没写到终端上的先扔掉（接上以后有回放），不然关模式的那几个字节排在它后面、
    终端慢的时候写不出去。终端在原始模式里，这些话自己带回车（`say_raw`：排在还没写完的后面，不经 `err!`）
  - 隔 1、2、4、8、15、15…秒试一次（`RETRY_GAP`），一共 `RETRY_FOR`（5 分钟；`CCA_REMOTE_RETRY=秒数` 能改，0 是不试、和以前一样马上退出 68）。
    每次先问一遍服务器这个会话还在不在（`far::fetch`，只问这一个配对）：那台机器没连着服务器、服务器没答就等下一次，不去换票据；
    在、连着才换票据、连数据端口、握手（`dial_far`，和头一次接入是同一段）。服务器给每台设备限了流（每 2 秒 1 次），一次试最多两个请求
  - 服务器答了、却说没有这个会话：多半是真的结束了（这台机器睡了一觉，那边早做完了），等 `MISSING_FOR`（45 秒）就不等了、说清楚。
    留这一阵是因为服务器重启、宿主那头的转接断了一下以后，会话要等那头连上来才又有（它头几次是隔 4、10、20 秒试）。分不出“结束了”
    和“那台机器掉线一分钟以上”（服务器一分钟后就不再留着它的会话）：后一种等不到，过后再 `cca remote attach`
  - 这台机器上的配对没了、服务器上的配对没了（对方取消了）：马上停，不等
  - 接上以后发 HELLO，那边照新接入的来：补模式、回放最近的输出、让客户端重画。这边认序列、记模式的状态也从头来。终端上以前的内容
    不清掉（和手动再 `attach` 一次看到的一样：一行行输出的会话里，回放的那一段会再出现一遍；全屏的界面重画以后是对的）
  - 那边这期间改成只让看了（`allow … view` 就是先把正接着的断开）：接上以后说一句，之后按键不送。用户自己要的只看（`-r`）一直算数
  - 等的这一阵：敲的键读掉不要（攒着等接上了再送会变成一串迟到的按键；每次都读到没有为止，粘贴的一大段也一样），只认断开的键；
    SIGTERM、终端被关掉照样是断开。问服务器、连、握手是阻塞着做的（合起来最多半分钟）：这一步做到一半时按的键、收到的信号，
    最迟等它做完才看到（刚接上那一下也先看一眼，按的是断开的键就不接了）。这几步出了错也不往外抛，当成这一次没问到
  - 接上不到 10 秒又断连着 5 次（`FLAPS`）就不再试；没接上的退出码都是 68，原因写在终端上（“没重新接上：…”）
- `allow … view`、`allow … none`、取消配对以后正接着的那一处是被断开的，所以也走上面这一段：改成只看的自己接回来（只看），不让了的
  试 45 秒（那边不再告诉服务器有这个会话）以后说没接上
- 部署：`./policy.sh presence deploy` 默认连中转一起开（数据端口 18444，`--relay-port` 换、`--no-relay` 不开，记在服务器的 `.env`），
  部署完和 `presence status` 都从这台 Mac 连一下数据端口、说连不连得上。云服务商的安全组里要另外放行这个端口

还没做的：`tests/linux.sh --docker` 的各发行版容器里不跑远程会话的测试（它们用的 `ps -p`、`pgrep -f` 在 busybox 上不一样，没试过；
辅助程序是静态链接的同一份，宿主、接入端不靠发行版里的命令，宿主机模式跑过）；重连时分不出“会话结束了”和“那台机器掉线很久”
（要服务器记下会话是怎么没的才行）；真的两台机器、真的网络上断一次还没试过。

## 界面 App（M3）

接口在 `macos/PROTOCOL.md` 第 9 节（`hello.remote`、`cca remote list --json`、配对的提问会话、界面里的终端），这里写 App 那一头怎么做的和为什么。

- cca 这一头给 App 加的：`cca remote list [--local] --json`（`manage.rs` 的 `list_doc`：没问到服务器不算失败，原因放进 `errors`）；
  `remote end <会话的 id>` 结束这台机器上的一个会话（先发 `consent.remote_end`，同意后重跑才结束，做完是 `remote_updated`；`hello.remote_end`
  告诉 App 有这一条）；`remote pair` 能在提问会话里走（`remote_pair_run`：辅助程序 `remote-pair-show` 在后台跑，它的 stdout 先是 `code 配对码`、配好以后是 `peer 名字`，
  接到只有自己能读的临时文件里；bash 把配对码发成一页只显示的字段（题号 `remote.pair`），然后一圈圈地 `gui_answer_wait … 2` 只为了 App
  取消时马上知道——读到头就 `gui_abort`，`EXIT` 的 trap 把辅助程序停掉，辅助程序收到信号告诉服务器这个配对码作废（`pair_close`），
  另一头这时输入马上知道、不用干等一分钟）；`remote join` 的提问有题号 `remote.code`；`on|off|allow|unpair` 做完发结果事件
  （`remote_updated`），配好是 `remote_paired`；`allow`、`unpair` 认配对的编号（App 一律用它，名字可能重）
- 界面里的终端就是 `cca remote attach` 跑在 App 开的伪终端上（`PtyProcess.swift`），所以远程和本机的会话、只看和操作、断开的按键、
  各种接不上的说法都和命令行是同一份代码。两处和普通终端不一样，都是实测出来的：
  - `posix_spawn` 起的进程（自己一个会话、标准输入是伪终端从的那头）在 macOS 上**没有控制终端**，窗口大小变了收不到 SIGWINCH。
    接入端开头自己认一次（`pty.rs` 的 `adopt_tty`：自己是会话的头、还没有控制终端、标准输入是终端时 `TIOCSCTTY`）。App 没法替它做：
    `posix_spawn` 没有这个动作，改用 `fork` 在多线程的 App 里不安全
  - macOS 上伪终端主的那头要等从的那头被打开过一次才能设窗口大小（之前 `TIOCSWINSZ` 是 ENOTTY）：App 先自己开一下从的那头、设好大小，
    起好进程再关（留着的话进程退出时主的那头读不到头）
- 读伪终端的线程把每一块同步交给主线程（`DispatchQueue.main.sync`）再读下一块：终端画不过来时进程自然被压住，不在内存里越攒越多。
  视图还没接上来时最多攒 4 MB，多的丢最早的
- 终端的大小由视图定：`SizedTerminalView` 每次排版完报一次现在的列数行数（SwiftTerm 自己的 `sizeChanged` 在头一次排出来正好是默认的
  80×25 时不调），`TerminalSurface` 等它停一下（头一次 50 毫秒，之后 120 毫秒）再告诉 `RemoteTerminal`：头一次是起进程（带着这个大小），
  之后是 `TIOCSWINSZ`。拖窗口时不会一路给那台机器发几十次改大小
- 画终端的视图跟着 `RemoteTerminal` 活着（它的 `surface` 留着 `TerminalSurface`），不跟着 SwiftUI 的页面：换到别的页再回来画面还在、
  还接着。主窗口**关了**才断开（被挡住、最小化不算：`WindowObserver` 的 `onClose`），退出 App 也断开——没人看着的终端
  不该一直占着一处接入（会话的窗口大小还得照顾它）
- 可以同时接着几个会话（`AppModel.remoteTerminals`，按接入的先后；`remoteShown` 是正显示的那个，nil 是会话列表）：各是各的
  `cca remote attach` 进程、各有自己的 `TerminalSurface`。开着终端时页顶多出一排（`RemoteTabStrip`：「会话列表」和每个终端各一格，
  × 是断开并关掉），点哪个显示哪个，别的照样接着、照样收输出；显示菜单里「下一个 / 上一个远程会话」（⇧⌘] / ⇧⌘[，`cycleRemote`，
  连同会话列表那一格转着换；SwiftTerm 的视图不接带 ⌘ 的键，所以焦点在终端里时菜单照样收得到）。规矩都在 `attachRemote`：
  - 一个会话在这里只开一个终端：已经接着、要的又是同一种接法（操作 / 只看）就换过去，不再接一次（再接一次只是在那边多占一处）；
    它的终端已经断开、结束了，或者换一种接法：原地换成新的，原来的断开
  - 最多 `remoteTerminalLimit`（8）个：每个是一个进程、在会话那边占一处接入；接着别的机器的那些断线时各自重试，都要问服务器，
    而服务器给每台设备限了流（每 2 秒 1 次）。开满了说一声、不接
  - 关掉正显示的那个：换到它旁边的一个，一个不剩才回到列表。主窗口关了、退出 App：都断开
  - 没在显示的终端不在窗口里，它报给会话的大小停在上次显示时的（和换到别的页一样）：这期间改了窗口大小，要等换回它才重报。
    写剪贴板（OSC 52）本来就只认正看着的那一块，没在显示的不会动剪贴板
- 内容来自别的机器，不让它动这台 Mac。SwiftTerm 是个功能很全的终端，默认开着的好几样在这里都是口子（审查时一条条对着它的源码查的）：
  - **Kitty 图形协议**（`KittyGraphics.swift`，APC `G`）：`t=f` 让终端按给的路径打开本机文件（读到 400 MB）、`t=t` 删路径里带
    `tty-graphics-protocol` 的临时文件、`t=s` 去掉共享内存，成不成还回给对方（`…;OK` / `EINVAL`）——对方能探这台 Mac 上有哪些文件。
    上游没有开关，APC 的分派写死在解析器里。做法：源码原样留着，`macos/build.sh` 编的时候用换过两行的一份 `EscapeSequenceParser.swift`
    （分派 Kitty 图形的那一行、建 sixel 处理器的那一行），两行都得正好各有一处、换上了才编，对不上就停；编好以后 `tools/swiftterm-check`
    拿编出来的那一份喂几条（直接给数据的、读本机文件的、删临时文件的、从 OSC / CSI 中间的 `0x9f` 进来的、分几块到的），有回话就不让
    编过。**不要改成在喂给它之前过滤字节**：它的解析器在任何非初始状态下见到 `0x9f` 都当 APC 的开头（OSC 里、CSI 里都行），
    自己写的过滤器很难和它判得一样
  - sixel（DCS `q`）、iTerm2 的内联图片和传文件（OSC 1337）：也是解码别人给的图。sixel 同上在编译时去掉，OSC 1337 用它公开的
    `registerOscHandler` 换成空的；`enableSixelReported` 关掉（问是什么终端时不说支持）
  - 链接：SwiftTerm 默认的做法会把看着像本机路径的也拿去 `NSWorkspace.open`，这里整个换掉，只开 http / https
  - OSC 52 写剪贴板：Claude Code 的「复制」靠它，但只在用户正看着这块终端时照办（主窗口在最前面、键盘焦点在终端上）——终端换到别的页

## 每个 Team 各用各的中转服务器（M6）

用户定的：**每个 Team 的会话走这个 Team 自己的服务器中转**（2026-11-22）。Team 的同步服务器本来就是这个 Team 的管理员自己部署的，
会话的密文不该绕到别人的服务器上；手机上也就成了每个 Team 的服务器各给一页（各自的地址、各自配对）。

- 中转服务器不止一台（`relay.rs` 的 `servers` / `server_of`）：各个 Team 的同步服务器（照加入的先后），再是维护者的那一台（旧的通道）。
  Team 的服务器是 `--mode team` 加 `--relay-listen` 起的，线上的格式一个字没变（设备是拿邀请加入的那把密钥认的；设备被移除、退出时
  服务器把它的配对一起清掉）
- **会话走哪台照它的账号**（`session_hub`）：账号是哪个 Team 给的（`policy_sources` → `route`），就走那个 Team 的服务器；维护者映射里的
  走维护者的那一台；别的（这台设备自己的、第三方 API 的、账号表里没有的）走这台机器的「家」（`home_hub`：加入的第一个 Team 的服务器，
  照加入的先后、这台机器用得了的；一个 Team 都没有时是维护者的那一台）。宿主那头的转接进程起来时定下来，只连那一台。
  **没有退路**：Team 的服务器没开中转、连不上时，这个 Team 的会话别的机器就是看不到——悄悄改走维护者的服务器等于把用户要的隔离丢了
- **配对记在某一台服务器上**（配对表的 `hub`：Team 的编号；维护者的那一台不写这一项，以前的配对表原样读得了）：经它只看得到走
  这台服务器的会话。同两台设备可以在几台服务器上各配各的（各是配对表里的一项、各有一把密钥；换掉的只是同一台服务器上的那一个）。
  `cca remote pair [--web] [--team 名字 | --maintainer]`：没说在哪台上时在家里那一台上配（`pair.rs` 的 `need_server`）；用得了好几台时
  问之前说清楚记在哪台上、对方经它看得到的是哪些会话、要在别的上面配怎么写（`remote_hub_label`：`py remote-hubs` 标着 `home` 的那一台；
  配对码是在一台服务器上开的，配错了对方看到的就不是他要的那些会话）。`cca remote join` 不用说：用得了的几台挨个试，开过这个配对码的那一台才认它
  （别的马上回“没有这个配对”）
- 列表、接入、看对方取消了没有、取消配对：配对记在哪台就问哪台（`far::fetch_all`）。哪一台没问到，只是它上面的那几个配对这次
  不知道（`remote list --json` 里那几个的 `state` 是 `unknown`，`errors` 里一条），别的照常
- 给界面的：`relay.hubs`（用得了哪几台）、`peers[].team`；App 在有好几台时把「显示配对码…」「和手机配对…」变成点开选在哪台上
- Team 的服务器怎么带上中转：安装脚本（`server/hub-install.sh`）默认开着，数据端口没写时是 HTTPS 那个端口的下一个空着的（直接在服务器上
  运行时 `--relay-port` 指定、`--no-relay` 不开；`cca team deploy` 不带这两个，记在 `.env` 的 `CCA_HUB_RELAY` 里，再运行照旧）；
  `cca team deploy` 装完说要放行哪几个端口（开了网页端的还有它的端口和 80）。
  已经装好的 Team 服务器重新 `cca team deploy` 一次就有了。托管平台上的（Railway、Sealos）只给一个 HTTP 端口，数据端口过不去：不做中转
- 升级以后要知道的：以前的配对都记在维护者的那一台上。账号搬进 Team 以后，它的会话改走 Team 的服务器，老的配对就看不到它了——
  在 Team 的服务器上再配一次（`cca remote pair --team 名字`）
- 证书（给网页端）：`server/cca-acme.py`，见下面「网页端」里“证书从哪来”

## 网页端（手机，M5）

手机上装不了 cca，所以给它一页网页：维护者的服务器（就是做中转的那一台）把 `server/web/` 里的页面发给浏览器，页面自己配对、
自己接入，里面是 xterm.js 的终端。iPhone 上「添加到主屏幕」以后像一个 App（PWA）。线上的格式在 `server/README.md`「网页端」，
页面目录里每个文件是什么、别人的代码从哪来在 `server/web/README.md`。

- 浏览器逼出来的三件事：
  - 开不了普通的 TCP 连接：服务器多一个 `GET /v1/relay/ws?t=票据的编号`，把 WebSocket 里的字节原样交给中转（`ws_pump`：socketpair 的一头
    交给中转的线程，`Relay.adopt`），之后和数据端口上接进来的连接一样对待——同样的开场白、票据、限额。服务器照旧一个字节都不看。
    网址里先带上票据的编号（`ws_claim`）：这个端口是对着整个互联网开的，没有凭证的人拿不到票据，就占不了 WebSocket 的名额
    （一条 WebSocket 占着一个线程；数据端口上没有这一层，那边一条连接不占线程）
  - 只认证书机构签的证书（页面要 HTTPS 才用得了 WebCrypto，WebSocket 也得是 wss）：cca 的设备用的那个端口是自签的证书加公钥钉住，
    浏览器不认，所以**另开一个端口**（`--web-listen`、`--web-cert`、`--web-key`）用浏览器信得过的那一张，原来的端口一个字不变。
    证书会到期、会续上：文件变了服务器自己重新读（`CertCtx`，最多一分钟看一次）。放在托管平台、反向代理后面（`--behind-proxy`）时
    HTTPS 本来就是平台做的，`--web-url` 直接开在同一个端口上
  - 没有 deploy key、不在设备清单里：手机是**访客**。电脑开一次“给网页端的配对”（`pair_open` 带 `web`，`cca remote pair --web`），
    服务器才让一把不认识的密钥来放密文（公钥在请求里；知道 `rid` 就是知道配对码，不知道的到不了验签那一步）；两边报出同一个配对编号
    （都算出了同一把密钥：它确实知道配对码）才把它的公钥记下来（`remote.json` 的 `guests`）。访客只能发接入用的那几个请求
    （`GUEST_OPS`），开不了配对、当不了宿主、碰不到设备统计和同步；一个配对都不剩时删掉；领它进来的设备被撤销了，它跟着没有；
    网页端关掉以后它的请求一律不认（记录留着）。拿着配对码来的签名不对、没有这次配对，回的和不认识的设备一样，分不出是哪种。
    不用 Team、不用管理员点头：手机和自己的电脑配对，和两台机器配对是一回事
- 配对出来的密钥、握手、加密的记录、帧都和两台机器之间**完全一样**（`server/web/core.js` 是第三份实现，和辅助程序、
  `tests/spec_wire.py` 互相握得上手）：宿主那头的转接进程不知道对面是浏览器，对方能做什么照旧由宿主把关
- 页面（`server/web/`，没有构建这一步）：
  - `core.js`：协议和加密。HMAC-SHA256 自己算（记录的密钥流要一块块地出，WebCrypto 每次调用都是异步的，太慢）；PBKDF2、
    Ed25519（请求照 SSHSIG 签名，和 `ssh-keygen -Y sign` 出的一样）、SHA-512 用 WebCrypto。设备的私钥、配对的密钥存成**不可导出**的
    （IndexedDB）：页面只能拿它们算，取不出原样的字节。要 iOS 17 以上（更早的 Safari 没有 Ed25519）
  - 断了自己接上（`Attachment`）：间隔、试多久、“没有这个会话”等多久都照辅助程序的（1、2、4、8、15 秒，一共 5 分钟，45 秒；
    刚接上就断的，间隔从连着断了几次起步）。手机把页面切到后台几秒钟连接就没了，所以这是常态：回到前台马上再试，开着却 25 秒
    没听到对面的也当成断了（`nudge`：不等 60 秒的那次检查）。请求有 25 秒的期限（手机的网络半死不活时不一直挂着）。
    接上以后那边重放模式和最近的输出，页面先把终端清回刚打开的样子（往终端里写 CAN 和 RIS：和后面的输出排着队，不会抢在前面）。
    断着的时候敲的键不送、也不攒着；输入框里的字留着，接上了再发
  - 配对放了密文以后没成（没等到、对不上、存不下）：告诉服务器作废（`pair_close`；已经记下了的是 `pair_drop`），电脑那一头马上知道
  - `app.js`、`app.css`：会话的列表（一台电脑是主干、会话从上面分出去：和 Logo 一个意思）、配对、设置、终端。终端那一屏永远纯黑。
    手机键盘上没有的键在按键条上（Esc、Tab、⇧Tab、Ctrl 是粘的、方向键按住连发、⏎、^C、^D）；这一排比屏幕宽，手指在键上划是滚动它，
    抬起来才算按（`press`：按下时就发的话，划一下就敲出一个键，而且按下时拦掉默认动作会让这一排划不动）。
    「输入」打开一个输入框——中文、听写、长一点的话在那里打，发送时整段送过去（终端开着括号粘贴时带着标记）再回车；
    输入法选字时的回车不算发送（Safari 里那一下 `isComposing` 已经是 false，要看 `keyCode` 是不是 229）。键盘出来时整屏跟着 `visualViewport` 变矮，
    按键条贴在键盘上面，终端重新算行数
  - 终端是 xterm.js 5.5.0（原样取自 npm，校验和在 `server/web/README.md`）。只载入了它和自适应大小的插件：没有图片、
    剪贴板（OSC 52）、网页链接的插件，会话的输出让终端做不了这些事。别人写的字（电脑的名字、会话的说明）一律当文字放进页面
  - 没有 service worker：这一页离线也没用，缓存着旧的代码反而麻烦。文件每次都问一下变了没有（`no-cache` + ETag）
  - 内容安全策略：脚本、样式、图片、请求、WebSocket 只认同一个源，不许 `eval`、不许被别的页面嵌进去
- **这一页靠什么保密，哪里比 cca 弱**（配对前的说明、页面的「设置」里都写着）：终端的内容照样只在手机和电脑之间加密，服务器只转密文。
  但页面本身是服务器给的：管着这台服务器的人（或者攻破它的人）能换掉页面的代码，之后配对的密钥、敲的键它都拿得到——
  cca 自己是签了名才装得上的，这一页没有这一层。所以网页端只该开在自己管的服务器上，这句话也是同意那一步里说的
- iPhone 上要知道的：
  - 主屏幕上的那一份和 Safari 里的是两套数据：要**先添加到主屏幕，再在主屏幕的那一份里配对**（页面在 Safari 里打开时提醒）。
    所以配对码不放进网址：扫了二维码在 Safari 里配好，主屏幕上的那一份还是没配对的
  - 清掉网站数据、删掉主屏幕上的图标：密钥没了，要重新配对（电脑那边 `cca remote unpair` 把旧的删掉）
  - 手机接着的时候会话跟着手机的窗口变窄（大小取各处都画得下的）；只让看的不算
- 电脑这一头：`cca remote pair --web`（bash 的 `remote_pair_run web`、辅助程序的 `remote-pair-show --web`）。同意的范围是 `web`
  （和两台机器配对分开问，说明里多了上面那段）。辅助程序在 `code 配对码` 后面紧跟一行 `web 网页端的地址`（服务器回的，是它配置里
  `--web-url` 写的那个）：终端里打印出来，App 里是一页（题号 `remote.pair_web`：地址画成二维码，`kind` 是 `qr`）。服务器没开网页端、
  是旧版（不认 `web` 这一项，照普通的配对开了）时辅助程序把那次配对作废、说清楚（`NO_WEB`）。配对表里这一项记着 `web`
  （只是给人看的：`cca remote peers` 里标「手机上的网页端」，App 里一个「手机」的标签），它能做什么照旧是 `incoming`
- 部署：`./policy.sh presence deploy 主机 --web-url https://地址[:端口]/ [--web-acme | --web-cert 证书 --web-key 私钥]`。
  `--web-acme`：证书由证书助手（下面「证书从哪来」）向 Let's Encrypt 要、到时候续上——另一个容器 `cca-acme`（`compose.acme.yaml`，
  `.env` 的 `CCA_ACME=on`、`CCA_ACME_ID` 是网页端地址里的那个 IP 或者域名，`COMPOSE_FILE` 带上它），占着服务器的 80 端口应答验证
  （80 被别的程序占着时部署停下、说清楚；网页端自己的端口不能是 80），证书写进 `webcert/`，账户在 `acme/`（都是 700、交给 10001）。
  头一次部署等它拿到证书（最多 3 分钟；没拿到不算部署失败，它自己接着试），说什么时候到期。`--web-cert`、`--web-key`、`--no-web`
  关掉它（下次 `docker compose up --remove-orphans` 把那个容器删掉）；什么都不写照上次的。页面的文件传到
  `app/web/`，证书在 `webcert/`（`fullchain.pem`、`privkey.pem`），多出来的几项在另一个文件 `compose.web.yaml` 里
  （`.env` 的 `COMPOSE_FILE` 把它带上）：没开网页端时原来那一套一个字不变。`--no-web` 关掉；部署完和 `presence status` 都从这台 Mac
  照证书机构验一次证书、说连不连得上。私钥传上去时落盘就是 600、目录 700，马上交给容器里的用户（后面哪一步停下它都不是别人读得了的）；
  传之前在这台 Mac 上先看证书和私钥是不是一对、私钥带没带密码。网页端是上次部署开的、这一次只改别的时，服务器上那段脚本照样查：
  开着网页端不能关中转（服务端会起不来，连设备统计一起停），端口不能和另外两个撞
- 证书从哪来：用户定了用 **Let's Encrypt 给 IP 地址签的证书**（2026-11-22；不用域名）。`server/cca-acme.py` 是为它写的证书助手
  （只用标准库和 openssl 命令的 ACME 客户端）：
  - 照 Let's Encrypt 现在的规矩（2026-11 查的）：给 IP 签的只有约 6 天（160 小时）的短期证书这一种，下单时写 `"profile": "shortlived"`；
