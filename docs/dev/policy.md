# 维护者的映射

参考节点（映射仓库里的 nodes.json）见 fill.md；设备统计的服务器见 presence.md。

- `./policy.sh 映射仓库的目录 ["提交说明"]` — 发布维护者的账号 → 节点映射：检查格式（`cca _policy-check`）、确认仓库是私有的，用发布密钥签名（命名空间 `cca-policy`），提交并推送。目录里有 `custom.yaml` 时顺带发布参考节点（抽成 `nodes.json`，`cca _fill-check`，命名空间 `cca-nodes`）；`./policy.sh nodes 参考配置 [策略组]` 只打印不发布
- `./policy.sh key [ls | add [公钥文件 | - | '公钥'] [别名] | rm 别名 | mv 别名 [新别名]] [-R 仓库] [-y]` — 维护者管理各台机器的 deploy key（经 `gh api`）：别名就是 GitHub 上 key 的标题，不许重复（命令里写的重复了、有终端时另问一个）；cca 给维护者的是一整行 `./policy.sh key add '公钥' 机器名`（`policy_prepare`；带空白和 `AAAA` 的参数当公钥），add 不写文件也不写公钥就读剪贴板，不写别名就提示（默认取公钥备注 `cca-policy@机器名` 里的机器名），总是加成只读；GitHub 的 deploy key 不能修改，mv 是删掉后用同一把公钥重新加（新的没加上时给出补回去的那一行 `./policy.sh key add -R 仓库 '公钥' '别名'`）。默认仓库从 `cca` 的 `POLICY_REPO_DEFAULT` 读（`CCA_POLICY_DEFAULT` 同样能换掉）
- 维护者的账号 → 节点映射（`cca policy`）：映射在维护者的私有 GitHub 仓库里，每台机器一把只读 deploy key（`~/.cca/policy/id_ed25519`），`policy_clone` 拉取时 `ssh -F /dev/null`、`IdentitiesOnly`、`IdentityAgent=none`、`GIT_CONFIG_GLOBAL=/dev/null`，主机公钥钉死（`GITHUB_HOST_KEYS`，`StrictHostKeyChecking=yes`）：ssh 先拿用户自己的 GitHub 密钥登录上的话，私有仓库只会回"不存在"。验签用 `RELEASE_KEY`、命名空间 `cca-policy`，通过才换上 `~/.cca/policy/policy.json`。强制在 辅助程序的 `reconcile`（每条命令读账号表都经过它）：映射里的官方账号节点不一致就改回并写回账号表；映射和账号表合并（`policy_merge`）：映射里有、这台机器上还没有的官方账号自动加进来（别名取映射可选的顶层 `aliases`，和本机别的账号重名就只写邮箱；已经在表里、键只是邮箱的映射账号，映射里有别名时补上（`policy_alias_fill`，只改键，端口、上次使用按邮箱跟着走）），这台机器自己的账号、起过的别名都不动。不加的（`policy_missing` 给原因，`cca policy` 列出来）：删掉过的（工具状态里的 `policy_skip`：`cmd_rm`、`cca edit`（`policy-have` / `policy-forget`，要在 `py validate` 之前记，否则 ctx 又加回来了）记下，`cmd_add` 清掉）、节点不在可选节点里的（加进来整张表就校验不过）、这台机器还没用过的工具（`policy_in_use`：当前工具或已有账号表；Codex 账号第一次用 cca codex 时才加，免得白占端口）。映射格式只能加旧版本会忽略的东西：客户端的 `policy_problems` 不查未知字段和 `aliases`（不合规的别名不用），只有维护者发布前的 strict 检查报错；改成旧版本认不出的格式，没自动更新的机器会一直用旧映射、跟不上节点调整。只有配置了映射仓库，config.json 才有 `policy` 这一项；每天的后台拉取（`policy_hook`）和自动更新的开关、开发模式无关。默认仓库是 `POLICY_REPO_DEFAULT`（`cca policy setup` 不写仓库时用它；环境变量 `CCA_POLICY_DEFAULT` 可以换掉，设成空就不引导）。终端里启动账号（`launch` 开头的 `policy_offer`，非交互时不问）还没配置映射、也没选过「不用映射」（config.json 的 `policy_declined`，`py policy-set` 会清掉）时，手把手引导：`policy_guide` 生成 key，显示给维护者的那一行 `./policy.sh key add '公钥' 机器名`（仓库不是默认的那个时带 `-R`；Mac 上复制到剪贴板），`policy_wait` 马上拉一次、之后每 5 秒自动再拉（`CCA_POLICY_POLL`，测试用；回车马上再拉，s 先跳过，最多 30 分钟；GitHub 不认 deploy key（`POLICY_DENIED`）时不每次都说）。`policy_wait` 直接从 fd 3 读（`read -t`：超时接着拉，读到头当跳过），不用 `ask`：`ask` 分不出回车和读到头
- 锁定请求（把账号的节点锁进映射）：别的机器只有只读 deploy key，改不了映射。`cca [codex] policy request 账号`（App 账号菜单的「请求维护者锁定节点」，`can.policy_lock`：官方账号、配置了映射、还没被映射固定）写一条维护者直接运行的命令 `./policy.sh lock claude|codex 邮箱 节点`（值经 `shlex.quote`，不带别名），不能请求时 `py policy-request` 退出码 2、stdout 是原因；在 App 里（有 `CCA_EVENTS`）stdout 就是那条命令，App 自己复制。维护者在 cca 的仓库里运行它（映射目录：`-C`、环境变量 `CCA_POLICY_DIR`，默认 cca 仓库旁边的 `cca-policy`）：`cca _policy-lock plan` 列出会改什么，问过才 `apply` 写进 policy.json（邮箱不分大小写，`-y` 不问），然后走照常的发布流程（检查、确认私有、签名、推送）。命令多半是别人发来的：控制字符、不合规的值不收也不原样显示（`cmd_policy_lock`）；节点不在 nodes.json 里时提醒（路由器上没有这个节点的机器，账号会用不了）；写进去了但没发布成时，再运行会提醒还有没发布的改动
- 映射的定时拉取（PROTOCOL 4.9）：`cca policy pull --json`，App 开着时一小时一次（`POLICY_POLL_INTERVAL`；`state.config.policy.next_check_epoch` 是 cca 算的，App 不重算，`PolicyPolling`、`Scheduler.updatePolicyPolling`）。拉到了马上照映射改账号表、同步路由器；要重载的不问（`consent` 事件忽略，留着 `pending`，用户点“同步”时再问）；拉不到不打扰，原因在 `$POLICY_DIR/log`（只留最后 200 行）。手动拉取（`AppModel.pullPolicyNow`，节点分流页的「拉取映射」、账号菜单的「现在拉取映射」）是同一条命令，不降优先级，结果照实提示，要重载时接着走 `syncRouter`（这次是用户点的，可以问）。`policy_pull` 会 `touch checked`，启动时的 `policy_hook` 不用再拉

## 测试
- 映射：假 `git` 只管 `clone`，把 `$T/policy_repo` 里的文件拷过去，网址和 `GIT_SSH_COMMAND` 记在 `$T/git.log`；`touch "$T/policy_denied"` 模拟 deploy key 还没加上，`policy_offline` 模拟连不上 GitHub（带 git 自己的套话）。验签要用测试发布密钥，所以映射的用例放在自动更新那一节后面（那时装着的是 `mkver` 换成测试密钥的版本），映射用 `pol` 写进假仓库并签名
- 启动时的映射引导：`run` 里 `CCA_POLICY_DEFAULT=` 是空的（平时的用例不引导），测引导时给 `CCA_POLICY_DEFAULT=example/cca-policy`；`$T/policy_denied_n` 让假 `git` 先拒绝这么多次（模拟维护者中途才加上公钥）；假 `pbcopy` 把内容写进 `$T/clipboard`
- 映射和账号表合并（regress.sh 11b2）：`edit_table` 加一个映射里没有的账号当作用户自己的；Codex 账号"第一次用 cca codex 时才加"靠把 `codex.json` 挪开模拟，测完连 config.json 一起还原（挪开期间对账会回收 Codex 的端口）
- 维护者管理 deploy key（`policy.sh key`，regress.sh 11b3）：假 `gh`（`$T/fake_gh.py`）只模拟 `gh api` 里 deploy key 的列出、添加、删除，key 存在 `$T/deploy_keys.json`，调用记在 `ghcli.log`；`touch "$T/policy_keys"` 后假 `git` 按它认 deploy key（没加上就拒绝，认出来了记下 `last_used`）；`gh_down` 模拟连不上 GitHub，`gh_post_fail` 让添加一律 502；假 `pbpaste` 读 `$T/clipboard`
- 把账号锁进映射（regress.sh 11b3b）：假的维护者目录 `$T/maint`（policy.sh + 测试发布密钥的 cca，policy.sh 从旁边的 cca 读发布公钥），映射仓库是它旁边的 `$T/cca-policy`（真的 git 仓库，默认的位置）；`runcmd 答案文件 命令` 像维护者那样在 `$T/maint` 里运行发来的命令；假 git 的 `-C 目录 push` 只记在 git.log，假 gh 的 `repo view` 回 PRIVATE（`$T/gh_public` 模拟公开仓库）；这一节结束时账号表、配置、映射、假的映射仓库都还原
