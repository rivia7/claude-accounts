# 设备统计和共享记下的 API key

折合金额也经这台服务器同步，见 cost.md；钥匙串那一侧见 secrets.md。服务器是各个 Team 的同步服务器（辅助程序的 `cca-core team-server --mode team`：`cli/src/server/`，装到 Linux 服务器上的就是 Linux 的那一份；部署见 team.md「部署」），远程会话的中转（配对、数据端口）也在它上面，见 remote.md 和 server/README.md。Team 给的官方账号经那个 Team 的服务器走下面这三条管线（账号走哪台、各台分开的状态文件见 team.md「同步经 Team 的服务器」）：请求拿这台设备在这个 Team 里的密钥签名（`~/.cca/teams/<编号>/id_ed25519`），盐是 Team 的配置里的。别的官方账号（这台设备自己的）、第三方 API 账号哪台都不去。3.6.0 以前维护者的映射里的账号报给维护者的服务器（`./policy.sh presence deploy` 部署的，服务端的 `--mode maintainer`），跟着映射去掉了（team.md「3.6.0 去掉的旧通道」）。

- 设备统计（presence，App 账号页的「设备」、`cca [codex] devices [账号…] [--json]`，PROTOCOL 3.4）：Team 给的官方账号经 cca 用的时候（命令行会话、`cca app` 打开的桌面 App；网页版、不经 cca 的 claude / codex 不算）报告给那个 Team 的服务器，config.json 的 `presence: false` 关掉（不报也不查）。每台 Mac 一个上报进程 `cca _presence-agent`（`main` 里 exec 成 `py presence-agent`；`presence_wake` 用 `/usr/sbin/taskpolicy -c background` 起它，`presence/agent.lock` flock 保证只有一个）：`cmd_session_open` 写完登记后在同一个进程里调 `presence_wake`（不多起进程），`cmd_app` 打开 / 切到 App 后 `py presence-wake`。它报全量快照（不是开始 / 结束事件，丢一次下次自己纠正），之后 60 秒一次心跳，其余时间睡在 kqueue 里（会话的 cca 进程和 App 进程 NOTE_EXIT、Team 给的账号的目录 NOTE_WRITE；每次至少睡 1 秒），
每台用得了的服务器一条线（`Lane`：各报各的账号，各有自己的 `due`、退避、上次报成的样子；加入、退出以后下一圈换，重新加入 Team、Team 换了服务器也算新的一路（配置里的 `rev` 是 team.json 的修改时间），见 team.md），报不出去时只看一个截止时间 `due`（报成了是下一次心跳，没报成是退避结束：5 秒起翻倍、最多 2 分钟，403 是 10 分钟），心跳到期、会话变了都等它，绝不每圈重发；最后一个会话关掉时报 `end:"none"`，先放锁再扫一次才退出（刚开的会话不会漏）；读不了账号表、ps 失败的那一轮不报（不能当成“没开”）；cca 文件换了就 execv 自己；SIGTERM 报 `end:"down"`；`cca restore` 删 ~/.cca 之前 `py presence-stop`。动静：命令行会话看它 tty 的 atime / mtime（最后输入、输出，和 w 一样；没有 tty 的算在干活），桌面 App 看进程树的 CPU（`PRESENCE_APP_CPU`；第一次见到的老 App 先当作刚好闲置满 10 分钟）；只报相对秒数，in_use / idle / none / offline 由服务器按自己的时钟算（ttl 150、闲置 600），两边时钟差多少不影响状态。服务器在哪、证书公钥的指纹、盐都在 Team 的配置里（`server`、`salt`，见 team.md「设备拿到的配置」）。账号只报 `HMAC(salt, 工具\0邮箱)`；请求用这台设备在 Team 里的密钥签（`ssh-keygen -Y sign`，命名空间 `cca-presence`，body 带 op、key、ts、nonce，服务器要 ts 在 ±5 分钟内、nonce 不重复）；curl 一律直连（`--proxy '' --noproxy '*'`，不经账号的出口）、`-k --pinnedpubkey`（macOS 的 SecureTransport 只给 RSA、P-256/P-384 做钉住，证书要 P-256；部署到托管平台、没有指纹的照系统的证书机构验）。服务端照 RFC 8032 自己验 SSHSIG（不调 ssh-keygen：容器直接用官方 python 镜像），只认这个 Team 登记了的设备（拿邀请加入的、管理员 `team_enroll` 的），名字是设备在 Team 里的名字；同一个 IP 最多 8 个连接、每个连接从接进来起最多 15 秒（握手 5 秒），按设备的限流在验签之后才扣；证书公钥的指纹在服务器上用 openssl 算（服务端不解析证书）；`end:"down"` 只让开着会话的账号算离线；Docker 方式的安装按顺序试官方镜像的几个同步源（国内连不上 Docker Hub；安装脚本的 `IMAGES`，见 team.md「安装脚本」）。真实服务器的地址不进这个仓库。"device" 在 cca 里另有所指（账号目录的 `device.json`），这一套内部一律叫 presence
- 共享记下的 API key（keyshare，辅助程序的「共享 API key」一节；`_gui state` 的 `api_key` 加 `shared`、`saved_epoch`、`from_device`、`sync_error`，PROTOCOL 2.2 / 4.10）：Team 给的 Claude、Codex 官方账号、开着设备统计时，记下备查的那一把经那个 Team 的服务器（op `keys`，`data/keys.json`）同步给登录了这个账号的其他设备。服务器只存密文：`keyshare_keys` 由 Team 的盐、`工具\0邮箱小写\0身份` 派生两把 HMAC 密钥，身份是 `Tool.share_ident`（Claude 的 `accountUuid`、Codex id_token 的 `chatgpt_user_id`；Antigravity 没有，不同步）；只用标准库：HMAC-SHA256 按块计数当密钥流，另一把 HMAC 认证（带着账号摘要），明文 `{"v":1,"key":key|null,"at":时间}` 补齐到 `KEYSHARE_PAD`，格式在 server/README.md，`tests/kit/spec.rs` 照文档独立实现一遍核对（`tests/presence.rs`、`tests/cost_view.rs` 共用）。设备被移除时服务器上它传的那一份留着（是账号的），只是不再记着是它传的（`forget_gone`：之后取到的没有 `from`）。新的胜出（`keyshare_round` 按认证过的 `at` 比）：旧的、认证不过的不认，服务器上没有、认不出、比本机旧时传本机的（自己修好）；没登录这个账号的设备不问也不传。只有在这台设备上记下、删掉（`keyshare_edit`：拿着这台服务器的 `keys.lock` 改钥匙串再记时间，同步照服务器改 key 时也拿着它、只在这一项没变时才改，免得拿旧的盖掉刚记下的）才算改了；`cca rm`、`cca edit`、`restore` 只删这台设备上的（`secret-del` 不记时间），钥匙串里的被删了下次从服务器取回来。同步来的删除要读回来确认钥匙串里真的没了才记（`kc_del` 删不掉也照样去掉记录：锁着的钥匙串里会留下一把没人记着的 key），没删掉就下一轮再删。本机记在它走的那个 Team 的 `presence/team.<编号>.keys.json`（600：`工具:账号目录名` → `at`、`sum`）；哪台都不走的账号（这台设备自己的）不记、不同步（3.6.0 以前退到维护者的服务器）；没有记录的按 `key_hints` 的 `at`、再按钥匙串这一条的修改时间（`keystore_mtime`）算；`kc_put` 的 `extra` 把 `at`、同步来的 `from`（设备名）记进 `key_hints`。什么时候同步：记下、`--forget` 后 `keyshare_kick(True)`（后台 `cca _key-sync force`），`cca usage`、`cca devices` 之后和上报进程里最多 `KEYSHARE_EVERY` 一次（上报进程里同步出什么错都吞掉，包括 die 的 `SystemExit`，只有 SIGTERM 的 `Stop` 照常往外抛：要报 `end:"down"`；Claude 的 `share_ident` 每次用 `load_quiet` 现读 `.claude.json`，不经 `acct_json`：它读不了时 die，一个进程里又只读一次，上报进程一开好几天）；`key --show` 这台设备上没有时先 `py key-sync now`（每个请求 8 秒）再读。同步不成的原因进 `sync_error` 和 `cca devices`（以前只对维护者那台旧服务器说的 `KEYSHARE_OLD` 3.6.0 去掉了：Team 的服务器都有这个 op）

## 测试
- 设备统计：`tests/presence.rs`（suite 的一个模块：回归开头起在后台、unit 一节收结果；服务器用哪一份照 `CCA_TEST_SERVER`）起真的服务器（Team 的，127.0.0.1 随机端口，openssl 生成的 P-256 证书，ttl 2 秒、闲置 3 秒），验签和 ssh-keygen 交叉核对；客户端是辅助程序（每台设备一个临时 HOME、它在 Team 里的密钥，每个用例一个新的服务器进程：限流的配额从头算；服务器、Team、设备、开会话、起上报进程这些夹具在 `tests/kit/fleet.rs`、密钥和证书在 `tests/kit/pki.rs`，别的几份测试共用）：上报进程照假 `ps` 的进程表上报（命令行会话的闲置时间：开一个真的伪终端、设它的输入 / 输出时间），记下的 API key、折合金额经真 curl 钉住证书公钥同步，curl 包了一层把请求记下来；后台起的 `cca`（`CCA_SELF`）是只记一笔的假脚本，它经 `taskpolicy -c background` 起、机器的核都占满时一直轮不到跑，所以 `Device::kicks()` 把进程表里起了还没轮到的也算上（只等它记那一笔的话，机器忙时会偶发失败），用例结束时还没轮到的由 `Device::sweep()` 停掉。直接调服务端内部的那几段（存储的上限和清理、几个解析函数、自己验 SSHSIG）在服务端的单元测试里（`cli/src/server/store/tests.rs`、`wire.rs`、`sshsig.rs`）。桌面 App 的 CPU 采样、隔多久再报在 `cli/src/cmd/presence.rs` 的单元测试里。回归里另有端到端的一遍（真的服务器、Team 给的账号）：`cca devices`、上报的在用 / 没在用、记下的 API key 和折合金额照 server/README.md 的格式（`tests/kit/spec.rs`，回归里是 `cca-test spec`）和服务器直接交换（解开、伪造、封好）
