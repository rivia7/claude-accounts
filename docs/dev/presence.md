# 设备统计和共享记下的 API key

折合金额也经这台服务器同步，见 cost.md；钥匙串那一侧见 secrets.md。

- `./policy.sh presence deploy root@主机 [-p SSH 端口] [-i 私钥] [--port 端口] [--dir 服务器上的目录] [-C 映射目录]` — 经 SSH 用 docker compose 部署设备统计的服务器（`server/`：`compose.yaml` + 只用标准库的 `cca-presence.py`，默认 `/root/projects/cca-presence`、端口 18443），第一次在服务器上生成自签的 P-256 证书，把 presence 一节（地址、证书公钥指纹、盐）写进映射目录的 policy.json、推送设备清单；之后照常发布映射。`./policy.sh presence sync | status`：把仓库上的只读 ed25519 deploy key 用发布密钥签名（命名空间 `cca-devices`）推给服务器 / 看服务器状态；`key add/rm/mv` 之后自动 sync（映射目录：`-C`、`CCA_POLICY_DIR`，默认 cca 仓库旁边的 `cca-policy`；只推映射目录 origin 对应的那个仓库的 key，`-R` 别的仓库时不推，免得服务器不再认原来的机器）。`presence_health` 的结果在 `P_HEALTH`，别放在 `$(…)` 里调（`P_ERR` 会留在子 shell 里）
- 设备统计（presence，App 账号页的「设备」、`cca [codex] devices [账号…] [--json]`，PROTOCOL 3.4）：映射里的官方账号经 cca 用的时候（命令行会话、`cca app` 打开的桌面 App；网页版、不经 cca 的 claude / codex 不算）报告给维护者的服务器，只有配置了映射、有 deploy key 的 Mac 报，config.json 的 `presence: false` 关掉（不报也不查）。每台 Mac 一个上报进程 `cca _presence-agent`（`main` 里 exec 成 `py presence-agent`；`presence_wake` 用 `/usr/sbin/taskpolicy -c background` 起它，`presence/agent.lock` flock 保证只有一个）：`cmd_session_open` 写完登记后在同一个进程里调 `presence_wake`（不多起进程），`cmd_app` 打开 / 切到 App 后 `py presence-wake`。它报全量快照（不是开始 / 结束事件，丢一次下次自己纠正），之后 60 秒一次心跳，其余时间睡在 kqueue 里（会话的 cca 进程和 App 进程 NOTE_EXIT、映射账号的目录 NOTE_WRITE；每次至少睡 1 秒），
报不出去时只看一个截止时间 `due`（报成了是下一次心跳，没报成是退避结束：5 秒起翻倍、最多 2 分钟，403 是 10 分钟），心跳到期、会话变了都等它，绝不每圈重发；最后一个会话关掉时报 `end:"none"`，先放锁再扫一次才退出（刚开的会话不会漏）；读不了账号表、ps 失败的那一轮不报（不能当成“没开”）；cca 文件换了就 execv 自己；SIGTERM 报 `end:"down"`；`cca restore` 删 ~/.cca 之前 `py presence-stop`。动静：命令行会话看它 tty 的 atime / mtime（最后输入、输出，和 w 一样；没有 tty 的算在干活），桌面 App 看进程树的 CPU（`PRESENCE_APP_CPU`；第一次见到的老 App 先当作刚好闲置满 10 分钟）；只报相对秒数，in_use / idle / none / offline 由服务器按自己的时钟算（ttl 150、闲置 600），两边时钟差多少不影响状态。映射里的 `presence` 一节（`{"url", "pins", "salt"}`）：客户端完全合格才启用（`presence_problems`，不合格就当没有，映射照用），维护者的严格检查放行它。账号只报 `HMAC(salt, 工具\0邮箱)`；请求用 deploy key 签（`ssh-keygen -Y sign`，命名空间 `cca-presence`，body 带 op、key、ts、nonce，服务器要 ts 在 ±5 分钟内、nonce 不重复）；curl 一律直连（`--proxy '' --noproxy '*'`，不经账号的出口）、`-k --pinnedpubkey`（macOS 的 SecureTransport 只给 RSA、P-256/P-384 做钉住，证书要 P-256）。服务端照 RFC 8032 自己验 SSHSIG（不调 ssh-keygen：容器直接用官方 python 镜像），只认发布密钥签的设备清单（`cca-devices`，序号只增），名字是 deploy key 的标题；同一个 IP 最多 8 个连接、每个连接从接进来起最多 15 秒（握手 5 秒），按设备的限流在验签之后才扣；证书公钥的指纹在服务器上用 openssl 算（服务端不解析证书）；`end:"down"` 只让开着会话的账号算离线；部署时按顺序试官方镜像的几个同步源（国内连不上 Docker Hub），拉到的写进 `.env`。真实服务器的地址只在私有映射里，不进这个仓库。"device" 在 cca 里另有所指（账号目录的 `device.json`），这一套内部一律叫 presence
- 共享记下的 API key（keyshare，辅助程序的「共享 API key」一节；`_gui state` 的 `api_key` 加 `shared`、`saved_epoch`、`from_device`、`sync_error`，PROTOCOL 2.2 / 4.10）：映射里的 Claude、Codex 官方账号、开着设备统计时，官方账号记下备查的那一把经维护者的设备统计服务器（op `keys`，`data/keys.json`）同步给登录了这个账号的其他设备。服务器只存密文：`keyshare_keys` 由映射的盐、`工具\0邮箱小写\0身份` 派生两把 HMAC 密钥，身份是 `Tool.share_ident`（Claude 的 `accountUuid`、Codex id_token 的 `chatgpt_user_id`；Antigravity 没有，不同步）；只用标准库：HMAC-SHA256 按块计数当密钥流，另一把 HMAC 认证（带着账号摘要），明文 `{"v":1,"key":key|null,"at":时间}` 补齐到 `KEYSHARE_PAD`，格式在 server/README.md，`tests/spec_wire.py` 照文档独立实现一遍核对（`tests/presence.py`、`tests/cost_view.py`、regress 的 `dkey` / `dcost` 共用）。新的胜出（`keyshare_round` 按认证过的 `at` 比）：旧的、认证不过的不认，服务器上没有、认不出、比本机旧时传本机的（自己修好）；没登录这个账号的设备不问也不传。只有在这台设备上记下、删掉（`keyshare_edit`：拿着 `presence/keys.lock` 改钥匙串再记时间，同步照服务器改 key 时也拿着它、只在这一项没变时才改，免得拿旧的盖掉刚记下的）才算改了；`cca rm`、`cca edit`、`restore` 只删这台设备上的（`secret-del` 不记时间），钥匙串里的被删了下次从服务器取回来。同步来的删除要读回来确认钥匙串里真的没了才记（`kc_del` 删不掉也照样去掉记录：锁着的钥匙串里会留下一把没人记着的 key），没删掉就下一轮再删。本机记在 `presence/keys.json`（600：`工具:账号目录名` → `at`、`sum`，没开设备统计时不记；没有记录的按 `key_hints` 的 `at`、再按钥匙串这一条的修改时间（`keystore_mtime`）算）；`kc_put` 的 `extra` 把 `at`、同步来的 `from`（设备名）记进 `key_hints`。什么时候同步：记下、`--forget` 后 `keyshare_kick(True)`（后台 `cca _key-sync force`），`cca usage`、`cca devices` 之后和上报进程里最多 `KEYSHARE_EVERY` 一次（上报进程里同步出什么错都吞掉，包括 die 的 `SystemExit`，只有 SIGTERM 的 `Stop` 照常往外抛：要报 `end:"down"`；Claude 的 `share_ident` 每次用 `load_quiet` 现读 `.claude.json`，不经 `acct_json`：它读不了时 die，一个进程里又只读一次，上报进程一开好几天）；`key --show` 这台设备上没有时先 `py key-sync now`（每个请求 8 秒）再读。旧的服务器回 404：`KEYSHARE_OLD`（要维护者 `./policy.sh presence deploy`），`KEYSHARE_RETRY` 后再试，原因进 `sync_error` 和 `cca devices`

## 测试
- 设备统计：`tests/presence.py`（regress 开头跑）起真的服务器（127.0.0.1 随机端口，openssl 生成的 P-256 证书，ttl 2 秒、闲置 3 秒），验签和 ssh-keygen 交叉核对；客户端是辅助程序（每台设备一个临时 HOME、自己的 deploy key，每个用例一个新的服务器进程：限流的配额从头算）：上报进程照假 `ps` 的进程表上报（命令行会话的闲置时间：`pty.openpty` + `os.utime` 设真的伪终端的输入 / 输出时间），记下的 API key、折合金额经真 curl 钉住证书公钥同步，curl 包了一层把请求记下来；后台起的 `cca`（`CCA_SELF`）是只记一笔的假脚本，它经 `taskpolicy -c background` 起、机器的核都占满时一直轮不到跑，所以 `Device.kicks()` 把进程表里起了还没轮到的也算上（只等它记那一笔的话，机器忙时会偶发失败）。桌面 App 的 CPU 采样、隔多久再报在 `cli/src/cmd/presence.rs` 的单元测试里。regress.sh 11b3c 端到端：同样起真的服务器（ttl 是 `STTL` 秒（10）：上报进程 60 秒一次心跳，「在用」只在每次上报后的这几秒里看得到，要看在用的马上问；发布密钥是测试的 `$T/relkey`），`pol` 发布带 presence 的映射，维护者在 `$T/maint` 里 `./policy.sh presence sync`（假 gh 的 deploy key，这台机器的要在上面），会话用 `$T/hold` 开着（测试里没有终端：在跑就算在用），`dwait 名字:状态:会话数` 等服务器上的状态；结束时停掉服务器，映射、配置、账号表、假 GitHub 上的 key 都还原。11b3 里调仓库里那份 `policy.sh` 时带 `CCA_POLICY_DIR` 指到沙箱（`$NOPD`）：`key add/rm/mv` 之后会去看映射目录，默认是仓库旁边真的 `cca-policy`。记下的 API key 的同步：`dkey get|junk|put KEY|- 时间` 用 dan-air 的 deploy key（`$T/dan`）照 server/README.md 的格式（`tests/spec_wire.py`：密文、签名的请求）和服务器直接交换（解开、伪造、封好；alice 的登录身份由 `setoa` 设成 `u-alice-0001`，这一节结束时 `.claude.json` 还原），`dkwait 值` 等服务器上的变成这样（后台同步是 background 优先级），`cca _key-sync force` 直接同步一次；`$T/guifx3/state_keys.json`（同步来的 key）交给契约测试
